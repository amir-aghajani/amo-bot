# رابط Store API: مدیران سایت

برای توسعه‌دهنده وب‌سایت فروشگاه که بخش مدیریت هم در آن می‌سازد: مدیران سایت — همان مدیران ربات فروشگاه — کار روزانه
فروشگاه را آنجا انجام می‌دهند، با حساب‌های خودشان در وب‌سایت، همان‌طور که در پنل انجام می‌دادند. همه اندپوینت‌ها، با
بدنه و پاسخ‌هایشان: [مرجع API مدیران (انگلیسی)](../Store-Admin-API-Reference.md).

## این API چیست

رابط API مدیران همان عملیات‌های خود پنل‌ها برای کار روزانه فروشگاه است، زیر آدرس پایه وب‌سایت و <code dir="ltr">/admin</code>:

```text
{APP_URL}/api/store/v1/{store-key}/admin
GET {base}/admin/payments?status=awaiting_review      the panels' GET /api/{panel}/payments, the same answer
```

| بخش | کاری که مدیران سایت آنجا انجام می‌دهند |
|---|---|
| داشبورد، صف‌ها، فهرست تغییرات | `GET /admin/dashboard` (`attention` آن اول کارهای منتظر پشتیبانی را می‌شمارد — صف‌ها، پرداخت‌های آنلاینی که برای پشتیبانی نگه داشته شده‌اند در `held_payments`، سرورهایی که پنلشان خطا داده — و بعد کارهای منتظر کاربران را؛ `agency_standing` آن همیشه null است: شرایط نماینده با فروشگاه اصلی به خود نماینده مربوط است)، <code dir="ltr">/admin/queues</code>، <code dir="ltr">/admin/changes</code> (با پولینگ آن فروشگاه را زنده دنبال کنید: فقط فروشگاه خود وب‌سایت را می‌شمارد، به‌علاوه آنچه همه فروشگاه‌ها مشترک دارند) |
| پرداخت‌ها | فهرست — که میان وضعیت‌ها تب `held` را هم دارد (<code dir="ltr">?status=held</code>: پرداخت‌های آنلاینی که برای پشتیبانی نگه داشته شده‌اند و هنوز منتظرند، که `meta.held` با هر فیلتری آن‌ها را می‌شمارد) — و هر پرداخت با رسیدش؛ تایید، رد، لغو، یادآوری، تلاش دوباره، پرسیدن وضعیت پرداخت آنلاین از درگاهش (`POST /admin/payments/{id}/check`) — بازپرداخت با مجوز `refunds`، رد یکجای رسیدها با `payments` |
| سفارش‌ها | فهرست و هر سفارش؛ تلاش دوباره برای تحویل، لغو سفارش پرداخت‌نشده |
| سرویس‌ها | فهرست و هر سرویس؛ خواندن آن از پنلش، خاموش یا روشن کردن، انتقال به سرور دیگر — روز و حجم با `extend`، حذف یا انتقال به کاربر دیگر با `delete` |
| کاربران | فهرست (با فیلتر نقش هم) و صفحه هر کاربر، دفتر کیف پول، گروه‌هایش (افزودن به گروه «همکار» با `catalog`)، مسدود کردن — هرگز حساب یک مدیر یا نماینده ([ردها](#ردها))؛ تغییر کیف پول با `wallet`؛ ثبت دستی سفارش برایش با `manual_orders`؛ خاموش کردن ورود دومرحله‌ای و خارج کردن از همه دستگاه‌ها با `account_security` |
| گروه‌های کاربران | فهرست — افزودن، تغییر نام، مرتب‌سازی، حذف، و روشن یا خاموش کردن «همکار» با `catalog`؛ اما هرگز روشن کردن آن برای گروهی که یک مدیر در آن است |
| تیکت‌های پشتیبانی | فهرست و هر تیکت — هر پیام پشتیبانی با نام مدیری که آن را نوشته ([آنچه فروشگاه ثبت می‌کند](#آنچه-فروشگاه-ثبت-می‌کند))؛ پاسخ (با تصویر هم)، بستن، باز کردن دوباره |
| نظرات | فهرست؛ تایید، رد، حذف ([نظرات](Reviews.md)) |
| پلن‌ها و دسته‌بندی‌ها | فهرست‌ها — افزودن، تغییر، مرتب‌سازی، روشن یا خاموش کردن، کپی، تغییر یکجای قیمت‌ها و حذف با `catalog` |
| زیرمجموعه‌گیری | آمار و چهار فهرست (معرف‌ها، دعوت‌شده‌ها، پورسانت‌ها، هشدارها)؛ رفع هشدار |
| ارسال‌های همگانی | اجراها؛ توقف، ادامه، لغو، برداشتن پین (نوشتن ارسال همگانی همچنان با <code dir="ltr">/broadcast</code> ربات است) |

هر چیز دیگری فقط در پنل‌هاست و اینجا `404` می‌گیرد: پیکربندی فروشگاه — روش‌های پرداخت، تنظیمات، متن‌ها و کیبوردهای ربات،
گروه گزارش‌ها، خود وب‌سایت، **اینکه مدیرانش چه کسانی هستند**، تخفیف اختصاصی هر کاربر، تخفیف‌ها و جایزه‌ها (کدهای تخفیف،
فروش‌های ویژه، کدهای هدیه، گردونه، وفاداری، کش‌بک، قرعه‌کشی)، اکانت‌های تست — و بخش‌های مالک فروشگاه (سرورها، نمایندگی،
تنظیمات نصب).

پاسخ‌ها دقیقا همان شکل پاسخ‌های پنل‌ها را دارند: همان JSON، که همان‌طور خوانده می‌شود، با همان نامی که پنل‌ها برای
کاربران نشان می‌دهند.

**تغییری که دوباره فرستاده می‌شود.** شارژ یا برداشت کیف پول (`POST /admin/users/{id}/wallet`) و پاسخ تیکت
(`POST /admin/tickets/{id}/messages`) یک `Idempotency-Key` اختیاری می‌گیرند، همان‌طور که پنل‌ها می‌فرستند: کلیدی که سایت
برای هر تغییر می‌سازد (یک UUID؛ ۱ تا ۶۴ حرف و رقم لاتین، `-` و `_`)، که تا وقتی همان تغییر دوباره امتحان می‌شود ثابت
می‌ماند و وقتی تغییر انجام شد یا فرم ویرایش شد کلید تازه ساخته می‌شود. اگر درخواست با همان کلید دوباره فرستاده شود (پاسخ
گم شده بود)، نتیجه همان کار قبلی را برمی‌گرداند — خط کیف پول (با `200`، در حالی که پاسخ اول `201` بود)، یا تیکتی که
پاسخ فقط یک بار در آن است — و هیچ‌وقت دو بار شارژ یا برداشت نمی‌کند، دو بار پاسخ نمی‌دهد و دو بار به کاربر خبر نمی‌دهد.
همان کلید با `type`، `amount` یا `description` دیگر (برای پاسخ تیکت، `body` یا تصویر دیگر) `422` روی `idempotency_key`
می‌گیرد (`این Idempotency-Key پیش‌تر برای درخواست دیگری به کار رفته است؛ برای هر تغییر کلید تازه‌ای بسازید.`). بدون کلید،
هر درخواست تغییر جداگانه‌ای است. ثبت دستی سفارش همیشه کلید می‌خواهد ([مجوزها](#مجوزها)).

## راه دادن مدیران

مالک فروشگاه — یا نماینده، برای فروشگاه خودش — این را در پنل، در «تنظیمات وب‌سایت › مدیران سایت» تنظیم می‌کند
([وب‌سایت](Website.md#مدیران-سایت)):

- **«کار مدیران از وب‌سایت»** — به‌طور پیش‌فرض خاموش: تا روشن نشود، هر درخواست <code dir="ltr">/admin</code> رد می‌شود.
- **«ورود امن مدیران»** — به‌طور پیش‌فرض روشن: مدیران باید با ورود قوی وارد شده باشند ([پایین‌تر](#ورود)).
- **«کارهای بیشتر»** — یک کلید برای هر مجوز، همه به‌طور پیش‌فرض خاموش ([مجوزها](#مجوزها)).

**چه کسی مدیر است**: کاربرانی از فروشگاه که نقششان مدیر است — نقشی که در «کاربران» پنل، از منوی ردیف با «مدیر ربات
کردن» داده می‌شود ([کاربران](Customers.md#مدیران-ربات)). نقش مال حساب کاربر است: مدیر با همان حسابی وارد وب‌سایت می‌شود
که این نقش را دارد — با تلگرامش، یا روش ورودی که به همان حساب اضافه شده
([روش‌های ورود](Store-API-Account.md#روش‌های-ورود-افزودن-و-حذف)). حساب وب‌سایتی که خودش فقط با یک ایمیل ساخته کاربر دیگری
است و مدیر نیست.

## ورود

مدیر مثل هر کاربری وارد می‌شود ([ورود](Store-API-Sign-In.md)) و توکن Bearer او API مدیران را هم باز می‌کند. `GET /me` (و
`PATCH /me`) در `staff` می‌گویند این توکن چه کارهایی را برایش باز می‌کند — برای کاربری که مدیر نیست، و تا وقتی وب‌سایت
هیچ مدیری را راه نمی‌دهد، `null`:

```json
"staff": {
  "grants": ["refunds", "extend"],
  "strong_sign_in": true,
  "signed_in_strongly": true,
  "signed_in_until": "2026-10-08T23:45:00+00:00",
  "recent_until": "2026-10-08T12:00:00+00:00"
}
```

| فیلد | چه می‌گوید |
|---|---|
| `grants` | مجوزهایی که وب‌سایت فراتر از کار روزانه به مدیرانش داده |
| `strong_sign_in` | اینکه وب‌سایت از مدیرانش ورود قوی می‌خواهد یا نه |
| `signed_in_strongly` | اینکه این Session با ورود قوی است یا نه: با تلگرام، گوگل، یا رمز عبور همراه مرحله دوم وارد شده |
| `signed_in_until` | تا کی این Session اصلا می‌تواند با API مدیران کار کند — ۱۲ ساعت بعد از آخرین باری که یک روش ورود روی آن ثابت شده؛ `null`: اول دوباره یک روش ورود را ثابت کنید |
| `recent_until` | تا کی ورود این Session تازه حساب می‌شود — چیزی که عملیات مجوزدار و تایید پرداخت لازم دارند؛ `null`: اول دوباره یک روش ورود را ثابت کنید |

- **ورود قوی.** تا وقتی وب‌سایت آن را می‌خواهد، Sessionی که فقط با رمز عبور وارد شده برای همه عملیات‌های مدیریتی رد می‌شود،
  با <code dir="ltr">WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="telegram google password_2fa"</code>.
  ثابت کردن یک روش قوی روی Session — `POST /me/reauthenticate` با تلگرام، با گوگل، یا با رمز عبور و کد حسابی که ورود
  دومرحله‌ای‌اش روشن است ([ورود تازه](Store-API-Account.md#ورود-تازه)) — آن را تا آخر عمرش قوی می‌کند. ثابت کردن دوباره
  رمز عبور به‌تنهایی چیزی را عوض نمی‌کند؛ مدیری که با رمز عبور وارد می‌شود باید ورود دومرحله‌ای را روشن کند، یا تلگرام یا
  گوگل را اضافه کند.
- **یک روز کاری.** هر عملیات مدیریتی لازم دارد که یک روش ورود در **۱۲ ساعت** گذشته روی Session ثابت شده باشد — هنگام
  ورود، یا بعد از آن با `POST /me/reauthenticate` —، وگرنه `403` با `برای این کار دوباره وارد شوید.` و چالش ورود تازه
  برمی‌گردد: توکن مدیری که لو رفته فقط چند ساعت کار می‌کند، نه ماه‌ها مثل Session یک کاربر.
- **ورود تازه.** عملیاتی که مجوز می‌خواهد — افزودن کاربر به گروه «همکار» هم از آن‌هاست — و **تایید پرداخت** (که فقط با
  تایید مدیر سرویس تحویل می‌دهد) علاوه بر این لازم دارند که ورود Session حداکثر **۱۵ دقیقه** پیش باشد، مثل تغییر روش‌های
  ورود خود کاربر: وگرنه `403` با
  `WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age=900`. `POST /me/reauthenticate` پانزده
  دقیقه بعدی (و ۱۲ ساعت بعدی) را باز می‌کند؛ `recent_until` و `signed_in_until` می‌گویند کی تمام می‌شوند.
  [مرجع (انگلیسی)](../Store-Admin-API-Reference.md) برای هر عملیات می‌گوید که این را لازم دارد یا نه.
- **توکن مدیر را در حافظه یا `sessionStorage` نگه دارید — هرگز در `localStorage`**، که آنجا بعد از بسته شدن تب هم می‌ماند
  و هر اسکریپتی در سایت تا وقتی توکن معتبر است می‌تواند آن را بخواند. [کلاینت ساده](Store-API.md#یک-کلاینت-ساده) توکن
  کاربر را در `localStorage` نگه می‌دارد و توکن مدیر را در `sessionStorage`: بخش مدیریت ورودش را با
  <code dir="ltr">keepToken(token, adminTokens)</code> نگه می‌دارد و <code dir="ltr">admin()</code> را صدا می‌زند.

## مجوزها

| مجوز | چه چیزی را باز می‌کند |
|---|---|
| `catalog` | پلن‌ها و دسته‌بندی‌هایشان: افزودن، تغییر، مرتب‌سازی، روشن یا خاموش کردن، کپی، حذف — و تغییر هم‌زمان قیمت چند پلن (`POST /admin/plans/prices`، با پیش‌نمایش `POST /admin/plans/prices/preview`). گروه‌های کاربران هم: افزودن، تغییر، مرتب‌سازی، حذف — و افزودن کاربر به گروه «همکار» (`PUT /admin/users/{id}/groups`)، که اعضایش قیمت‌های نماینده را می‌پردازند؛ گروه‌های ساده، و گروه «همکار»ی که کاربر از قبل در آن است، مجوزی نمی‌خواهند |
| `wallet` | شارژ یا برداشت دستی کیف پول یک کاربر (با `Idempotency-Key` اختیاری: [تغییری که دوباره فرستاده می‌شود](#این-api-چیست)) |
| `refunds` | بازپرداخت یک پرداخت |
| `payments` | «رد یکجای رسیدها»: رد یکجای رسیدهای منتظر بررسی (`POST /admin/payments/dismiss`)، هر کدام درست مثل رد تکی، با پاک شدن تصویر آپلودشده ([رسیدها](Orders-And-Payments.md#رسیدها)) |
| `extend` | دادن روز و حجم به یک سرویس |
| `manual_orders` | «افزودن سفارش برای مشتری»: ثبت دستی سفارش برای یک کاربر (`POST /admin/users/{id}/orders`، با `Idempotency-Key`) — یک پلن یا عددهای دلخواه مدیر، رایگان، از کیف پول کاربر یا پرداخت‌شده بیرون از فروشگاه — که همان لحظه تحویل می‌شود ([سفارش‌هایی که پشتیبانی ثبت می‌کند](Orders-And-Payments.md#سفارش‌هایی-که-پشتیبانی-ثبت-می‌کند)) |
| `delete` | «حذف یا انتقال سرویس»: حذف همیشگی یک سرویس، از پنلش و از فروشگاه — یا انتقال آن به کاربر دیگری از فروشگاه (`GET` و `POST …/subscriptions/{id}/transfer`، مثل پنجره سرویس در پنل‌ها): هر دو سرویس را از کاربرش می‌گیرند |
| `account_security` | رسیدگی به حساب وب‌سایت یک کاربر: خاموش کردن ورود دومرحله‌ای و خارج کردن از همه دستگاه‌ها |

بقیه کار روزانه مجوزی نمی‌خواهد. [مرجع (انگلیسی)](../Store-Admin-API-Reference.md) برای هر عملیاتی که مجوز می‌خواهد نام
مجوز را می‌گوید.

## ردها

همه ردها همان شکل خطای Store API را دارند ([خطاها](Store-API.md#خطاها)). در ورودی، یک `403`:

| پیام | چرا | سایت |
|---|---|---|
| `این بخش فقط برای پشتیبانی فروشگاه است.` | کاربر مدیر فروشگاه نیست — هر چه وب‌سایت بگوید | بخش مدیریت را نشان ندهید |
| `این وب‌سایت فعلا مدیران فروشگاه را راه نمی‌دهد.` | وب‌سایت الان هیچ مدیری را راه نمی‌دهد | همین را بگویید |
| `برای کار مدیریت، با تلگرام، گوگل یا رمز عبور همراه کد ورود دو مرحله‌ای وارد شوید.` | فقط رمز عبور، در حالی که ورود قوی خواسته شده (`acr_values` در `WWW-Authenticate`) | روش‌های قوی را با `POST /me/reauthenticate` پیشنهاد کنید |
| `فروشگاه این کار را به مدیران وب‌سایت نسپرده است.` | عملیاتی که وب‌سایت مجوزش را نداده | کنترل را پنهان کنید (`staff.grants` را بخوانید) |
| `برای این کار دوباره وارد شوید.` | ورود Session بیش از ۱۲ ساعت پیش بوده — یا، برای عملیات مجوزدار یا تایید پرداخت، بیش از ۱۵ دقیقه پیش (`WWW-Authenticate` با `max_age=900`) | یک روش ورود را دوباره ثابت کنید و دوباره بفرستید |
| `حساب کاربری شما مسدود شده است.` | مدیر مسدود است | او را خارج کنید |

و بعد از ورودی، کارهایی که هیچ مدیری درباره‌شان تصمیم نمی‌گیرد، هر چه وضعیت ردیف اجازه دهد — این‌ها هم `403`:

| پیام | چرا |
|---|---|
| `پرداخت خودتان را نمی‌توانید تایید یا بازپرداخت کنید؛ این کار با مدیر دیگری است.` | تایید یا بازپرداخت پرداخت خودش |
| `موجودی کیف پول خودتان را نمی‌توانید تغییر دهید؛ این کار با مدیر دیگری است.` | کیف پول خودش |
| `سرویس خودتان را نمی‌توانید تغییر دهید؛ این کار با مدیر دیگری است.` | سرویس خودش: روز و حجم، خاموش یا روشن کردن، انتقال به سرور دیگر، حذف، انتقال به کاربر دیگر (خواندنش از پنل اشکالی ندارد) |
| `نظر خودتان را نمی‌توانید تایید، رد یا حذف کنید؛ این کار با مدیر دیگری است.` | تایید، رد یا حذف نظر خودش |
| `هشدار زیرمجموعه‌گیری خودتان را نمی‌توانید رفع کنید؛ این کار با مدیر دیگری است.` | رفع هشدار زیرمجموعه‌گیری روی خودش |
| `برای خودتان نمی‌توانید سفارش ثبت کنید؛ این کار با مدیر دیگری است.` | ثبت دستی سفارش برای حساب خودش |
| `حساب مدیران فروشگاه فقط از پنل تغییر می‌کند.` | حساب یک مدیر — مسدود کردن، گروه‌ها، ورود دومرحله‌ای، دستگاه‌ها —، چه حساب خودش و چه مدیر دیگر |
| `گروه «همکاران» حساب یکی از مدیران فروشگاه را دارد؛ «همکار» کردن آن فقط از پنل ممکن است.` | روشن کردن «همکار» برای گروهی که یک مدیر در آن است (پیام نام گروه را می‌گوید): اعضای گروه «همکار» قیمت‌های نماینده را می‌پردازند |
| `فروشگاه گذاشتن مشتری در گروه «همکار» را به مدیران وب‌سایت نسپرده است.` | افزودن کاربر به گروه «همکار» وقتی وب‌سایت مجوز `catalog` را نداده (اگر داده باشد، ورود قدیمی‌تر از ۱۵ دقیقه به جای این، همان `403` ورود تازه را می‌گیرد) |
| `حساب نماینده‌ها فقط از پنل تغییر می‌کند.` | حساب یک نماینده، به همین شکل (مسدود کردن، گروه‌ها، ورود دومرحله‌ای، دستگاه‌ها): شرکای مالک فروشگاه فقط در پنل مدیریت می‌شوند |
| `از وب‌سایت فقط پرداختی تایید می‌شود که رسیدش رسیده و در انتظار بررسی است.` | تایید پرداختی که رسید در حال بررسی ندارد |

مدیر سرویس یک کاربر را به حساب خودش هم منتقل نمی‌کند: `422` روی `telegram_id`
(`سرویس را به حساب خودتان نمی‌توانید منتقل کنید؛ این کار با مدیر دیگری است.`).

**این بررسی‌های امنیتی فقط جلوی کار مدیر روی حساب خودش را می‌گیرند: دو مدیر می‌توانند این کارها را برای هم انجام دهند**
— پرداخت‌های همدیگر را تایید کنند، کیف پول همدیگر را شارژ کنند. این نقش را فقط به کسانی بدهید که به آن‌ها اعتماد دارید.

درخواست‌های مرتب‌سازی — `POST /admin/plans/reorder`، `POST /admin/plans/categories/reorder`،
`POST /admin/customer-groups/reorder` — فیلد `ids` را با شناسه ردیف‌ها، به شکل عددهای JSON، می‌فرستند: لیست خالی `422`
روی `ids` می‌گیرد (`لیست شناسه‌ها خالی است.`)، و همین‌طور لیستی که چیزی جز شناسه ردیف در آن باشد — یک متن، یک boolean،
یک لیست (`یکی از شناسه‌ها درست نیست؛ صفحه را دوباره باز کنید.`).

کلاینت فقط وقتی روی پنلش باقی گذاشته می‌شود (سرویسی که فقط از فروشگاه حذف می‌شود، انتقال بدون حذف کلاینت قدیمی) که آن
پنل پاسخ ندهد: وگرنه `422` روی `status` (`پنل سرور «…» در دسترس است؛ …`). درخواست‌های مدیران از پنل‌های VPN — خواندن،
خاموش و روشن کردن، انتقال، دادن روز، حذف یک سرویس — در هر فروشگاه به ۶۰ عملیات در دقیقه محدود است، برای همه مدیران با
هم (در فروشگاه نماینده، همراه خود نماینده)، و بعد از آن `429` با زمان انتظار
(`درخواست زیادی به پنل سرورها فرستاده‌اید؛ …`)؛ و خطای پنل — عملیاتی که رد کرده، دلیل ناموفق بودن تحویل یک سفارش — برای
آن‌ها در چند کلمه کوتاه نشان داده می‌شود، هرگز با جزئیات عیب‌یابی‌ای که مالک فروشگاه می‌بیند.

## آنچه فروشگاه ثبت می‌کند

- **هر تغییری که مدیر درخواست می‌کند با نام او لاگ می‌شود** — چه انجام شود چه رد شود —، و تصمیم‌ها نام تصمیم‌گیرنده را
  نگه می‌دارند (نتیجه بررسی پرداخت، خط کیف پول، پاسخ تیکت): <code dir="ltr">@handle</code> او، وگرنه
  <code dir="ltr">tg:&lt;id&gt;</code>، وگرنه <code dir="ltr">user#&lt;id&gt;</code>. تصمیم‌های خود مالک فروشگاه برای
  مدیران «پشتیبانی» نشان داده می‌شود. کنار همان `reviewer`، ردیف پرداخت، ردیف نظر، خط کیف پول، پیام پشتیبانی در تیکت و
  ارسال همگانی (`GET /admin/broadcasts`، برداشتن پینی که مدیری شروع کرده) `reviewer_name` هم دارند: نام و نام خانوادگی مدیر
  همان‌طور که در حسابش هست، برای نمایش — برای مالک فروشگاه، نماینده، حسابی که دیگر نیست یا حسابی که نامی نشان نمی‌دهد
  (نامی که فقط فاصله یا کاراکتر نامرئی باشد نام حساب نمی‌شود)، و یوزرنیمی که الان مال هیچ مدیری از فروشگاه نیست `null`
  است. سفارشی که پشتیبانی دستی ثبت کرده هم همین را کنار ثبت‌کننده‌اش دارد: `manual.by_name` کنار `manual.by`. پنل‌ها نام را
  به جای یوزرنیم یا «کاربر #12» نشان می‌دهند، و مدیران را در ردیف‌هایی که فقط پنل‌ها دارند (درخواست‌های نمایندگی، خط‌های
  حجم نماینده، هدیه زمان و حجم، انتقال سرویس به سرور دیگر) هم همین‌طور نام می‌برند.
- **کاربر «پشتیبانی» می‌بیند**: پاسخ مدیر به تیکت در پنل‌ها با نویسنده «مدیریت وب‌سایت» نشان داده می‌شود، و برای کاربر
  مثل هر پاسخ دیگری پاسخ پشتیبانی است.

## ساخت بخش مدیریت

1. هنگام ورود، و بعد از هر `403` در ورودی، `GET /me` را بخوانید: اگر `staff` برابر null است بخش مدیریت را پنهان کنید.
2. فقط آنچه را `staff.grants` دارد نشان دهید: کنترلی که مجوزش نیست فقط رد می‌شود.
3. بعد از `staff.signed_in_until`، پیش از هر کاری از مدیر بخواهید دوباره یک روش ورود را ثابت کند؛ پیش از عملیات مجوزدار
   یا تایید پرداخت، `staff.recent_until` را هم همین‌طور بررسی کنید (`POST /me/reauthenticate`).
4. با توکن مدیر، که در `sessionStorage` نگه داشته می‌شود، از راه تابع <code dir="ltr">admin()</code> در
   [کلاینت ساده](Store-API.md#یک-کلاینت-ساده) بخوانید و بنویسید — همان <code dir="ltr">store()</code> با توکن مدیر:
   ```ts
   const queue = await admin<S['PaymentsResponse']>('/admin/payments?status=awaiting_review')
   await admin('/admin/payments/' + id + '/reject', { method: 'POST', json: { note: 'مبلغ رسید با سفارش نمی‌خواند' } })
   ```
5. تصویرها — رسید یا تصویر تیکت — هم با توکن درخواست می‌شوند: آن را fetch کنید و به شکل blob نشان دهید —
   <code dir="ltr">picture('/admin/payments/' + id + '/receipt', adminTokens)</code>
   ([گفتگو](Store-API-Support-Tickets.md#گفتگو) این تابع را دارد).
6. درخواست `GET /admin/changes` را هر چند ثانیه بفرستید (پولینگ) تا بدانید کدام فهرست‌ها تغییر کرده‌اند — عدد هر بخش
   وقتی ردیف‌هایش عوض شوند بزرگ‌تر می‌شود — و فقط همان‌ها را دوباره بخوانید. این عددها فقط فروشگاه خود وب‌سایت را
   می‌شمارند: تغییرهای فروشگاه دیگر اینجا چیزی را عوض نمی‌کنند، ولی آنچه همه فروشگاه‌ها مشترک دارند (سرورها) عوض می‌کند.
