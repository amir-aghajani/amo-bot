# رابط Store API

برای توسعه‌دهنده وب‌سایت اختصاصی یک فروشگاه: یک صفحه فرود و یک داشبورد کاربر، با Next.js یا هر چیز دیگری که HTTPS و
JSON بفهمد. فروشگاه خود AmoBot است — ربات تلگرام، پنل‌ها و همین API یک دیتابیس و یک مجموعه قاعده دارند — پس هر کاری که
کاربر در وب‌سایت می‌کند (ورود، خرید، تمدید، پرداخت کارت به کارت، خواندن اعلان‌ها، پیام به پشتیبانی) همان چیزی است که
ربات و پنل پشتیبانی می‌بینند. سایت فقط نمایش می‌دهد؛ تصمیم با AmoBot است.

قرارداد API فایل [`resources/api/openapi.yaml`](https://github.com/amir-aghajani/amo-bot/blob/main/resources/api/openapi.yaml)
است: هر عملیات زیر <code dir="ltr">/api/store/v1/{store}</code>، پارامترها، بدنه درخواست و پاسخ‌هایش. تست‌های خود سرور
هر درخواست و پاسخ را با آن می‌سنجند. هر جا این صفحه‌ها با فایل YAML نخوانند، حق با YAML است.

- مرجع [Store API (انگلیسی)](../Store-API-Reference.md)، که از روی کد ساخته می‌شود، همه عملیات‌ها را همان‌طور که YAML
  توصیف می‌کند در بر دارد، و [مرجع API مدیران (انگلیسی)](../Store-Admin-API-Reference.md) عملیات‌های مدیران سایت را.
- همین توصیف، همراه مسیرهای مدیران، یک فایل JSON هم هست:
  [`docs/openapi.json`](https://github.com/amir-aghajani/amo-bot/blob/main/docs/openapi.json). نام نوع‌ها در نمونه‌ها
  (<code dir="ltr">S['StoreSignInResponse']</code>) نام اسکیماهای همین فایل است.

صفحه‌ها: همین نمای کلی (آدرس، CORS، قراردادها، خطاها، یک کلاینت ساده و پیام‌هایی که بهتر است بشناسید)،
[ورود](Store-API-Sign-In.md)، [حساب کاربری](Store-API-Account.md)، [فروشگاه](Store-API-Shop.md) (عمومی)،
[خرید](Store-API-Buying.md)، [بعد از خرید](Store-API-After-Buying.md)، [اعلان‌ها](Store-API-Notifications.md)،
[تیکت‌های پشتیبانی](Store-API-Support-Tickets.md)، [نظرات](Store-API-Reviews.md) و [مدیران سایت](Store-API-Admins.md).

## از نگاه فروشگاه

- **یک فروشگاه، سه در.** ربات، پنل‌ها و وب‌سایت سه رابط روی همان سرویس‌ها هستند. هر قاعده کسب‌وکار — چه کسی می‌تواند
  تمدید کند، پیش‌فاکتور چقدر حساب می‌کند، سفارش کی قابل پرداخت است، بازپرداخت چه چیزی را برمی‌گرداند — در یک سرویس دامنه
  (domain service) است که همه رابط‌ها آن را صدا می‌زنند؛ هیچ رابطی نسخه‌ای از آن را برای خودش نگه نمی‌دارد.
- **کاربر همان کاربر است.** برای هر نفر در هر فروشگاه یک حساب، از هر دری که آمده باشد: حساب تلگرام، آدرس ایمیل و حساب
  گوگل همه راه‌های ورود به همان حساب‌اند. سفارش‌ها، سرویس‌ها، کیف پول، تیکت‌ها و اعلان‌ها مال حساب‌اند، هرگز مال یک روش
  ورود.
- **ادغام، نه رد کردن.** کسی که در وب‌سایت ثبت‌نام می‌کند و بعد حساب تلگرامی را اضافه می‌کند که از قبل سرویس دارد، یک
  حساب خواهد داشت: حساب جدیدتر در قدیمی‌تر ادغام می‌شود و هر چه داشت همراهش منتقل می‌شود
  ([پیشنهاد ادغام](Store-API-Account.md#پیشنهاد-ادغام)).
- **هر فروشگاهی می‌تواند وب‌سایت داشته باشد** — فروشگاه اصلی و فروشگاه هر نماینده (نماینده فروشنده‌ای است که ربات و
  فروشگاه خودش را دارد). وب‌سایت برای هر فروشگاه جدا تنظیم می‌شود و کلید فروشگاه در آدرس، همان فروشگاه را مشخص می‌کند:
  کاربران، پلن‌ها، قیمت‌ها و متن‌ها فقط مال همان فروشگاه‌اند، و کاربر یک فروشگاه برای فروشگاه دیگر ناشناخته است.
- **بدون کنسول و بدون بیلد برای مالک فروشگاه.** همه چیز از پنل تنظیم می‌شود؛ ایمیل فروشگاه با حساب SMTP هاست، تابع mail
  خود PHP یا API سرویس Resend فرستاده می‌شود؛ به queue worker هم نیازی نیست.

## آنچه API پوشش می‌دهد

| دسترسی | چه چیزی |
|---|---|
| **عمومی** (فقط کلید فروشگاه) | خود فروشگاه (<code dir="ltr">GET /</code>)، آنچه می‌فروشد (`GET /plans`، <code dir="ltr">GET /plans/{id}</code> — توکن کاربر واردشده اختیاری است و آن‌وقت کاتالوگ خود او خوانده می‌شود: [خواندن با توکن کاربر](Store-API-Shop.md#خواندن-با-توکن-کاربر))، آنچه کاربر می‌تواند بسازد (`GET /custom-services`)، وضعیت سرورهایش (`GET /status`)، نظرهایی که نشان می‌دهد و ثبت نظر، تا وقتی وب‌سایت نظر می‌گیرد (<code dir="ltr">/reviews</code> — توکن کاربر واردشده اختیاری است، و نظر مهمان پشت کپچا)، همه روش‌های ورود (<code dir="ltr">/auth/\*</code>، به جز `POST /auth/logout`)، و کپچای وب‌سایت (<code dir="ltr">/captcha/\*</code>) |
| **مال خود کاربر** (توکن Bearer او) | حسابش (<code dir="ltr">/me/\*</code>)؛ سرویس‌هایش (<code dir="ltr">/subscriptions/\*</code>)، از جمله سرویسی که با لینکش اضافه شده یا به کاربر دیگری سپرده می‌شود؛ خرید (<code dir="ltr">/payment-methods</code>، <code dir="ltr">/orders</code>، سرویسی که خودش می‌سازد، تمدیدها، حجم، زمان و کاربر اضافه، شارژ کیف پول، بررسی کد تخفیف، رسیدها، پرسیدن وضعیت پرداخت‌های آنلاین)؛ سفارش‌ها و پرداخت‌هایش؛ کیف پول، دفتر تراکنش‌هایش، انتقال موجودی به کاربر دیگر و کدهای هدیه؛ برنامه زیرمجموعه‌گیری؛ هر اعلانی که فروشگاه برایش فرستاده؛ و تیکت‌های پشتیبانی‌اش (<code dir="ltr">/tickets/\*</code>) |
| **مدیران سایت** (توکن Bearer یک مدیر، تا وقتی وب‌سایت راهشان می‌دهد) | کار روزانه فروشگاه همان‌طور که در پنل‌ها انجام می‌شود — رسیدها و پرداخت‌ها، سفارش‌ها، سرویس‌ها، کاربران، تیکت‌ها، نظرات، پلن‌ها، زیرمجموعه‌گیری، ارسال‌های همگانی — زیر <code dir="ltr">/admin/\*</code> ([مدیران سایت](Store-API-Admins.md)) |

آنچه پوشش داده نمی‌شود: محتوای خود سایت (وبلاگ، سوال‌های متداول، دانلود برنامه‌ها). همه راه‌هایی که فروشگاه با آن‌ها پول
می‌گیرد از همین API می‌گذرند: کیف پول، کارت به کارت با رسید، و درگاه‌های آنلاینی که مالک فروشگاه راه می‌اندازد
([پرداخت آنلاین](Store-API-Buying.md#پرداخت-آنلاین)).

## ساخت وب‌سایت، قدم به قدم

درخواست‌هایی که یک وب‌سایت فروشگاهی معمولی می‌فرستد، به همان ترتیبی که لازمشان دارد. هر قدم به صفحه خودش لینک دارد.

1. **فروشگاه.** درخواست <code dir="ltr">GET /</code>، روی سرور شما: نام فروشگاه، ربات و لینک پشتیبانی‌اش، اینکه الان
   سفارش می‌گیرد یا نه، روش‌های ورود و کپچا ([آنچه سایت اول می‌پرسد](Store-API-Shop.md#آنچه-سایت-اول-می‌پرسد)).
2. **کاتالوگ.** درخواست‌های `GET /plans`، `GET /status`، `GET /reviews` و، اگر فروشگاه ارائه کند،
   `GET /custom-services`. این‌ها عمومی‌اند: روی سرور خودتان رندرشان کنید و یک دقیقه کش کنید ([فروشگاه](Store-API-Shop.md)).
3. **ورود.** تلگرام، گوگل، یا ایمیل و رمز عبور، هر کدام که `sign_in` در پاسخ <code dir="ltr">GET /</code> ارائه کند.
   توکنی را که پاسخ ورود می‌دهد نگه دارید ([ورود](Store-API-Sign-In.md)).
4. **کاربر.** درخواست `GET /me` برای حساب و عدد زنگوله اعلان‌ها ([حساب کاربری](Store-API-Account.md)). `GET /plans` را
   با توکن دوباره بخوانید: کاربر واردشده ممکن است قیمت‌های دیگری بپردازد
   ([خواندن با توکن کاربر](Store-API-Shop.md#خواندن-با-توکن-کاربر)).
5. **پیش‌فاکتور.** درخواست `GET /payment-methods` برای روش‌های پرداخت، `POST /discount-codes/check` برای کدی که کاربر
   وارد می‌کند، و بعد درخواست سفارش — `POST /orders` برای یک پلن — با یک `Idempotency-Key` تازه
   ([خرید](Store-API-Buying.md)).
6. **پرداخت.** پاسخ ثبت سفارش می‌گوید قدم بعدی چیست: سرویسی که با کیف پول تحویل شد؛ کارتی برای پرداخت و رسیدی برای
   آپلود؛ یا صفحه درگاه آنلاین برای باز کردن ([پاسخ درخواست سفارش](Store-API-Buying.md#پاسخ-درخواست-سفارش)).
7. **داشبورد کاربر.** سرویس‌ها، تمدیدها و خریدهای اضافه، سفارش‌ها، کیف پول و برنامه زیرمجموعه‌گیری
   ([بعد از خرید](Store-API-After-Buying.md))، اعلان‌ها ([اعلان‌ها](Store-API-Notifications.md)) و تیکت‌های پشتیبانی
   ([تیکت‌های پشتیبانی](Store-API-Support-Tickets.md)).
8. **بخش مدیریت**، اگر آن را هم می‌سازید: کار روزانه فروشگاه برای مدیرانش ([مدیران سایت](Store-API-Admins.md)).

بقیه این صفحه چیزهایی است که در همه درخواست‌ها مشترک است: آدرس، CORS، قراردادها، خطاها، یک کلاینت ساده، و پیام‌هایی که
بهتر است بشناسید.

## آدرس پایه

```text
{APP_URL}/api/store/v1/{store-key}
https://panel.example.com/api/store/v1/c4859b5b660377ef517299cf
```

- مالک فروشگاه (یا نماینده، برای فروشگاه خودش) آن را از پنل کپی می‌کند: «تنظیمات وب‌سایت › اتصال»، کارت «آدرس API».
  مقدار `APP_URL` هر جایی است که AmoBot نصب شده، همراه زیرپوشه.
- کلید فروشگاه — ۲۴ کاراکتر هگز با حروف کوچک — فقط فروشگاه را مشخص می‌کند. محرمانه نیست: هر درخواست مرورگر آن را همراه
  دارد. دکمه «ساخت کلید جدید» در همان کارت آن را عوض می‌کند و آدرس قبلی همان لحظه از کار می‌افتد.
- مسیرهای این صفحه‌ها نسبت به آدرس پایه‌اند: `GET /plans` یعنی `GET {base}/plans`، و <code dir="ltr">GET /</code> خود
  آدرس پایه است، بدون اسلش در انتها.
- وب‌سایت در ابتدا خاموش است. تا مالک فروشگاه آن را با آدرس سایت روشن نکند — و همین‌طور بعد از عوض شدن کلید، یا وقتی
  فروشگاه یک نماینده بسته شود — همه اندپوینت‌ها `404` با `این فروشگاه وب‌سایت فعالی ندارد.` برمی‌گردانند. در این حالت هیچ
  Originی مجاز نیست، پس `fetch` در صفحه اصلا پاسخی نمی‌بیند (یک `TypeError`، [پایین‌تر](#فراخوانی-از-مرورگر))؛ فقط
  درخواستی که از سرور شما برود آن `404` را می‌بیند. آدرسی که اندپوینت نیست — کلیدی که ۲۴ کاراکتر هگز با حروف کوچک نیست،
  مسیری با اسلش در انتها — `404` خود مسیریاب را می‌گیرد (`صفحه مورد نظر پیدا نشد.`). اندپوینتی که با متدی صدا زده شود
  که نمی‌پذیرد `405` می‌دهد (`این روش درخواست پشتیبانی نمی‌شود.`)، و هدر `Allow` آن متدهای پذیرفته را می‌گوید (که از سرور
  شما خواندنی است: CORS آن را در اختیار صفحه نمی‌گذارد).

## فراخوانی از مرورگر

صفحه می‌تواند API را از Origin آدرس وب‌سایت (فیلد آدرس در «اتصال») و از حداکثر ده Origin دیگری که آنجا وارد شده صدا
بزند — مثلا `http://localhost:3000` در زمان ساخت. Origin یعنی scheme، هاست و پورت:
`https://shop.example.com`، `https://www.shop.example.com` و `http://shop.example.com` سه Origin جدا هستند، و
`http://127.0.0.1:3000` همان `http://localhost:3000` نیست.

برای Origin مجاز، درخواست preflight (`OPTIONS`) پاسخ `204` می‌گیرد — متدهای `GET, POST, PUT, PATCH, DELETE`، هدرهای
درخواست `Authorization, Content-Type, Idempotency-Key`، با اعتبار ۶۰۰ ثانیه — و هر پاسخ، حتی پاسخ خطا،
`Access-Control-Allow-Origin` و `Access-Control-Expose-Headers: X-Request-Id, Retry-After, WWW-Authenticate` را دارد.
پس:

- هیچ هدر سفارشی دیگری نفرستید (`X-Requested-With`، هدر tracing): preflight آن را رد می‌کند و مرورگر هیچ‌وقت درخواست را
  نمی‌فرستد؛
- هیچ‌وقت از <code dir="ltr">credentials: 'include'</code> استفاده نکنید — API کوکی نمی‌گیرد و درخواست credentialed را
  مجاز نمی‌کند؛
- صفحه‌ای روی هر Origin دیگر هیچ هدر CORSی نمی‌گیرد: مرورگر پاسخ را پنهان می‌کند و `fetch` با `TypeError` شکست می‌خورد.
  وقتی همه درخواست‌ها این‌طور شکست می‌خورند، «اتصال» را بررسی کنید — کلید روشن و خاموش، آدرس، Originها.

بدنه درخواست JSON است ([قراردادها](#قراردادها) را ببینید)، که مرورگر فقط بعد از preflight می‌فرستد: صفحه‌ای از سایت دیگر
نمی‌تواند مرورگر بازدیدکننده‌هایش را وادار کند ثبت‌نام، ورود یا بازنشانی رمز را برای فروشگاه بفرستد.

## فراخوانی از سرور شما

درخواست بدون هدر `Origin` — از server component در Next.js، یک route handler، یک بیلد — عادی پاسخ می‌گیرد.
این برای کاتالوگ عمومی مناسب است: <code dir="ltr">GET /</code>، <code dir="ltr">/plans</code>، <code dir="ltr">/status</code>
و <code dir="ltr">/reviews</code> را روی سرور رندر و مدت کوتاهی کش کنید
(<code dir="ltr">fetch(url, { next: { revalidate: 60 } })</code>). همه پاسخ‌ها `Cache-Control: no-store` دارند، پس هیچ
مرورگر یا CDNی خودش پاسخ را نگه نمی‌دارد: هر کشی، کش خود سایت است.

سرور شما می‌تواند داده‌های کاربر واردشده را هم با توکن او بخواند. ولی <code dir="ltr">/plans</code> که با توکن خوانده شود
فقط مال همان کاربر است ([خواندن با توکن کاربر](Store-API-Shop.md#خواندن-با-توکن-کاربر)): هیچ‌وقت آن را در کشی که دیگران
می‌خوانند نگذارید. فرم‌های خود سایت که کپچا دارند هم از سرور شما سنجیده می‌شوند ([کپچا](Store-API-Sign-In.md#کپچا)).

ورودها فرق دارند. API ورودهای ناموفق و هزینه هر ورود برای فروشگاه (nonceها، stateها، کدهای ایمیل) را برای هر آدرس
کلاینت می‌شمارد، و دستگاه (از `User-Agent`) و آدرس هر Session را از درخواست ورود ثبت می‌کند. اگر این درخواست‌ها از سرور
شما بگذرند، همه بازدیدکننده‌ها آدرس سرور شما را خواهند داشت: اشتباه تایپی یک کاربر همه را قفل می‌کند، و همه دستگاه‌ها
سرور شما دیده می‌شوند. پس این درخواست‌ها را از مرورگر بازدیدکننده بفرستید:
<code dir="ltr">/auth/\*</code>، <code dir="ltr">/me/reauthenticate</code>، <code dir="ltr">/me/telegram/authorize</code>، <code dir="ltr">/me/identities/\*</code>، `PUT /me/password`، `POST /me/2fa/disable`
— و `POST /reviews`، که سرعتش هم با آدرس شمرده می‌شود. اگر ناچارید این‌ها را
از سرورتان رد کنید، مالک فروشگاه باید آدرس سرور شما را در `TRUSTED_PROXIES` بگذارد (در
[config.php](../Config-Reference.md#keys-and-secrets) فروشگاه)، و پراکسی شما باید آدرس بازدیدکننده را به
`X-Forwarded-For` اضافه کند و `User-Agent` او را هم منتقل کند.

## قراردادها

- **بدنه JSON** در هر دو جهت. با هر بدنه‌ای `Content-Type: application/json` بفرستید: درخواست `POST`، `PUT` یا `PATCH`
  که بدنه‌اش چیز دیگری باشد — فرم، متن، بدنه‌ای که نوعش را نمی‌گوید — با `415` رد می‌شود
  (`بدنه این درخواست باید JSON باشد؛ آن را با Content-Type: application/json بفرستید.`). بدنه JSON یک شیء (یا یک لیست)
  است؛ بدنه‌ای که parse نشود مثل نبودن بدنه خوانده می‌شود، پس پاسخ همان `422` خود عملیات برای چیزی است که نیامده.
  عملیاتی که بدنه نمی‌گیرد بدون بدنه فرستاده می‌شود. بدنه JSON حداکثر ۱ MiB است
  (`413` با `درخواست بزرگ‌تر از حد مجاز است.`).
- **تصویر با فرم فرستاده می‌شود** (`multipart/form-data`):
  - رسید فرم است ([رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید)) — اگر با JSON فرستاده شود تصویری ندارد و `422`
    می‌گیرد؛
  - باز کردن تیکت (`POST /tickets`) و نوشتن در آن (`POST /tickets/{id}/messages`) هم JSON می‌پذیرند و هم فرم
    ([باز کردن تیکت](Store-API-Support-Tickets.md#باز-کردن-تیکت))، و پاسخ مدیر هم همین‌طور
    (`POST /admin/tickets/{id}/messages`)؛
  - بدنه دیگری در این درخواست‌ها `415` می‌گیرد (`بدنه این درخواست باید JSON یا فرم چندبخشی (multipart/form-data) باشد.`).
    فیلدهای متنی فرم مثل فیلدهای بدنه JSON خوانده می‌شوند و باید UTF-8 باشند: فیلدی که نباشد روی همان فیلد `422` می‌گیرد
    (`متن این فیلد درست نیست؛ آن را با کدگذاری UTF-8 بفرستید.`؛ `FormData` مرورگر همیشه UTF-8 است). فرم به ۱ MiB محدود
    نیست: تصویرش می‌تواند تا ۱۰ مگابایت باشد (بیشتر از آن، `422` روی `file`). فایلی بزرگ‌تر از حدی که PHP هاست برای یک
    فایل می‌پذیرد `422` روی `file` می‌گیرد (`فایل بزرگ‌تر از حد مجاز سرور است.`)، و فرمی بزرگ‌تر از حد کل یک درخواست
    `413` — هیچ‌وقت مثل فرمی که چیزی نفرستاده خوانده نمی‌شود.
- **مبلغ‌ها** به تومان و به شکل رشته اعشاری با دو رقم اعشارند: `"120000.00"`. هیچ‌وقت با float حساب نکنید؛ برای نمایش
  قالب‌بندی کنید، مثلا <code dir="ltr">Math.trunc(Number(amount)).toLocaleString('fa-IR')</code>. موجودی منفی یعنی بدهی
  نماینده. مبلغی که خود API نوشته، همان‌طور که نوشته پذیرفته می‌شود (مثل مبلغ پیش‌فرض شارژ،
  [شارژ کیف پول](Store-API-Buying.md#شارژ-کیف-پول)).
- **حجم** به بایت و به شکل عدد صحیح است؛ هر گیگابایت ۱۰۲۴³ بایت است (`traffic_gb: 50` یعنی ۵۳٬۶۸۷٬۰۹۱٬۲۰۰ بایت).
  حجم `0` یعنی نامحدود، مدت `0` ساعت یعنی هیچ‌وقت تمام نمی‌شود، و `0` دستگاه یعنی بدون محدودیت.
- **مدت** دقیقا `duration_hours` است: ممکن است پلنی ساعتی فروخته شود (مثلا یک تست یک‌ساعته). کنار آن، `duration_days`
  همان مدت به روز کامل است، رو به بالا گرد شده (پلن یک‌ساعته `1`)، که برای سایت‌هایی که پیش از پلن‌های ساعتی ساخته شده‌اند
  نگه داشته شده: مدت را از روی ساعت‌ها بنویسید.
- **زمان‌ها** با قالب ISO 8601 و به UTC هستند: `"2026-10-07T12:00:00+00:00"`. آن‌ها را با منطقه زمانی فروشگاه نشان دهید —
  API آن را نمی‌گوید: از مالک فروشگاه بپرسید (همان `APP_TIMEZONE` است، «تنظیمات پنل › برنامه») —، مثلا با
  <code dir="ltr">new Intl.DateTimeFormat('fa-IR-u-ca-persian', { timeZone: 'Asia/Tehran', dateStyle: 'medium' })</code>
  برای تاریخ شمسی به وقت ایران. مقدار `created_at` یا `updated_at` یک ردیف وقتی null است که آن ردیف بیرون از AmoBot و
  بدون آن نوشته شده باشد (وارد شده، یا دستی در دیتابیس اضافه شده): آن را نامعلوم نشان دهید.
- **آنچه کاربر تایپ می‌کند** می‌تواند رقم فارسی یا عربی داشته باشد: کدهای ایمیل (شش رقم و هیچ چیز دیگر — پیش از فرستادن،
  فاصله یا خط تیره را بردارید)، کدهای برنامه احراز هویت (آنجا فاصله و خط تیره اشکالی ندارد)، کد دعوت، شناسه تلگرام، و
  مبلغ‌های زیر.
  - **مبلغ** — شارژ، پولی که برای کاربر دیگری فرستاده می‌شود، `amount` در `GET /payment-methods`، `expected_amount` یک
    سفارش — تومان کامل است و جداکننده هزارگان (`۱۵۰٬۰۰۰`، `150,000`، `150 000`)، «هزار» یا «میلیون» (`۵۰ هزار` یعنی
    ۵۰٬۰۰۰) و «تومان» بعد از عدد را می‌پذیرد. هر کلمه دیگری بعد از عدد (`۵۰۰ ریال`) رد می‌شود و هیچ‌وقت با واحد اشتباه خوانده
    نمی‌شود.
  - **حجم، زمان یا کاربر اضافه** گیگابایت، روز یا دستگاه کامل است: فقط رقم (جداکننده مجاز است)، بدون کلمه واحد.
- **شناسه‌ها و کلیدهای روشن و خاموش**: شناسه هر ردیف (`plan_id`، `server_id`، `method_id` …) را به شکل عدد JSON بفرستید —
  `true` شناسه نیست — و کلید روشن و خاموش را به شکل boolean در JSON.
- **طول‌ها** در این صفحه‌ها به کاراکتر است، همان‌طور که فروشگاه می‌شمارد — code pointهای یونیکد: `😀` یک کاراکتر است
  (حداکثر طول رمز عبور، ۷۲، به بایت است). <code dir="ltr">.length</code> در JavaScript واحدهای UTF-16 را می‌شمارد و `😀`
  را دو: طول فیلد را با <code dir="ltr">\[...text\].length</code> بشمارید. فقط آنچه ربات می‌فرستد به روش تلگرام، با
  واحدهای UTF-16، اندازه‌گیری می‌شود — دلیل اینکه اعلان `ticket_answered` ممکن است کوتاه شود
  ([انواع اعلان](Store-API-Notifications.md#انواع-اعلان)).
- **فیلدهای اختیاری**: آنچه به کار نمی‌آید را نفرستید (`JSON.stringify` مقدار `undefined` را حذف می‌کند)؛ فقط فیلدهایی
  را بفرستید که در قرارداد آمده‌اند.
- **فهرست‌ها صفحه‌بندی دارند**: ۲۵ ردیف در هر صفحه، جدیدترین اول (تیکت‌ها: تازه‌ترین فعالیت اول). صفحه را با
  <code dir="ltr">?page=</code> بخواهید — از ۱؛ صفحه‌ای که نیامده یا خوانا نیست ۱ حساب می‌شود، و صفحه‌ای بعد از آخرین صفحه،
  آخرین صفحه را برمی‌گرداند. هر پاسخ <code dir="ltr">meta: { page, per_page, total, last_page }</code> دارد: «صفحه ۲ از ۷»
  را نشان دهید و در `last_page` متوقف شوید. `meta` اعلان‌ها و تیکت‌ها `unread` را هم دارد، برای عددی که کنار لینک نشان می‌دهید؛ و `meta`
  نظرات `summary` را.
- **مقدارهای enum** رشته‌هایی با حروف کوچک هستند (`active`، `awaiting_review`). ممکن است مقدارهای تازه‌ای اضافه شود: برای
  مقداری که نمی‌شناسید چیز معقولی نشان دهید.
- **متن‌هایی** که API می‌فرستد — پیام‌های خطا، اعلان‌ها، برچسب روش‌های پرداخت، نام پلن‌ها و سرورها — فارسی‌اند و برای
  کاربر نوشته شده‌اند. همان‌طور که هستند نشانشان دهید، در چیدمان راست به چپ یا با <code dir="ltr">dir="auto"</code>.

## خطاها

همه ردها و خطاها یک شکل دارند:

پاسخ `422` به `POST /auth/register`:
```json
{
  "message": "اطلاعات واردشده معتبر نیست.",
  "errors": {
    "email": ["ایمیل درست نیست؛ آن را مثل name@example.com بنویسید."],
    "password": ["رمز عبور دست‌کم 8 کاراکتر است."]
  },
  "request_id": "a47fde7a40fa8ca1"
}
```

- فیلد `message` — همیشه هست، به فارسی: نشانش دهید.
- فیلد `errors` — فقط وقتی رد به فیلدهای درخواست مربوط باشد: پیام‌های هر فیلد. آن‌ها را زیر همان ورودی‌ها نشان دهید.
  بعضی فیلدها ورودی‌ای نیستند که کاربر تایپ کند — `status`، `plan_id`، `server_id`، `method_id`، `for`،
  `idempotency_key`، `expected_amount`، `panel`، `captcha`، `ids`، تایید سرویس ورود و بخش‌هایش (`id_token`، `nonce`،
  `code` ریدایرکت، `state`، `code_verifier`، `code_challenge`، `redirect_uri`)، و `token` و `action` در بررسی کپچا — پس
  پیام آن‌ها را پیام کل فرم نشان دهید. ردی که به کل درخواست مربوط است `errors` ندارد.
- فیلد `request_id` — ۱۶ کاراکتر هگز، که در هدر `X-Request-Id` همه پاسخ‌ها هم هست (از Origin دیگر هم خواندنی است). در
  خطاهای 5xx، آن را به‌عنوان «کد پیگیری» نشان دهید تا پشتیبانی بتواند درخواست را در لاگ فروشگاه پیدا کند.

| وضعیت | در این API | سایت |
|---|---|---|
| `200` | انجام شد | — |
| `201` | ساخته شد: تیکتی باز شد ([باز کردن تیکت](Store-API-Support-Tickets.md#باز-کردن-تیکت))، نظری ثبت شد ([ثبت نظر](Store-API-Reviews.md#ثبت-نظر))، یا سرویسی با لینکش اضافه شد ([افزودن سرویس با لینک](Store-API-After-Buying.md#افزودن-سرویس-با-لینک)) | — |
| `202` | پذیرفته شد، یک قدم دیگر مانده: کدی ایمیل شد، حساب مرحله دوم را می‌خواهد، یا ادغامی پیشنهاد شده | طبق شکل پاسخ پیش بروید |
| `204` | انجام شد، بدون بدنه: خروج انجام شد، یک Session تمام شد | — |
| `401` | روی اندپوینت کاربر: توکنی نیامده، یا Session آن تمام شده — و روی `GET /plans`، <code dir="ltr">GET /plans/{id}</code> و `POST /reviews`، توکنی آمده که Session آن تمام شده ([توکن‌ها و Sessionها](Store-API-Sign-In.md#توکن‌ها-و-sessionها)) — آنجا معنای دیگری ندارد، و تنها `401` با `WWW-Authenticate: Bearer` است. روی <code dir="ltr">/auth/\*</code>: تایید ورود معتبر نبود (بدون این هدر) | توکن را کنار بگذارید و صفحه ورود را نشان دهید؛ روی <code dir="ltr">/auth/\*</code>، بگذارید دوباره امتحان کند |
| `403` | کاربر مسدود است (`حساب کاربری شما مسدود شده است.`) — یا، روی تغییر روش‌های ورود به حساب یا دادن سرویس یا پول به کاربر دیگر، ورود به اندازه کافی تازه نیست: `WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age=900` ([ورود تازه](Store-API-Account.md#ورود-تازه)). روی `POST /reviews`: نظر مهمان وقتی وب‌سایت کپچا نمی‌خواهد. روی <code dir="ltr">/admin/\*</code>: ورودی API مدیران، یا تصمیمی که هیچ مدیری نمی‌گیرد ([مدیران سایت](Store-API-Admins.md#ردها)) | پیام و لینک پشتیبانی را نشان دهید؛ یا دوباره یک روش ورود را ثابت کنید و دوباره بفرستید |
| `404` | کلید فروشگاه هیچ وب‌سایتی را باز نمی‌کند (فقط از سرور دیده می‌شود: مرورگر هیچ پاسخی نمی‌گیرد)؛ ردیفی که مال این کاربر نیست یا دیگر وجود ندارد؛ پلنی که الان فروخته نمی‌شود؛ نظرات وقتی وب‌سایت نظری نشان نمی‌دهد؛ چالش کپچا از وب‌سایتی که کپچای آن چالشی از فروشگاه نمی‌گیرد؛ آدرسی که هیچ مسیری ندارد | — |
| `405` | اندپوینتی که با متدی صدا زده شده که نمی‌پذیرد | — |
| `409` | چیزی در همان لحظه عوض شد: آدرس صاحب حساب شد، سفارش جای دیگری پرداخت یا بسته شد، سرویس در حال تغییر است — یا درخواست سفارشی که دوباره فرستاده شده می‌بیند سفارشش لغو شده ([هدر Idempotency-Key](Store-API-Buying.md#هدر-idempotency-key))، یا قیمت درخواست سفارش دیگر همان `expected_amount` نیست که با آن فرستاده شده ([قیمت نمایش‌داده‌شده](Store-API-Buying.md#قیمت-نمایش‌داده‌شده)). روی `POST /auth/google`: آدرس مال حسابی است که تایید گوگل به‌تنهایی نمی‌تواند بازش کند ([گوگل](Store-API-Sign-In.md#گوگل)). روی `POST /subscriptions/claim`: سرویس در حساب کاربر دیگری است. روی `POST /captcha/verify`: وب‌سایت کپچا نمی‌خواهد | دوباره بخوانید و وضعیت جدید را نشان دهید |
| `413` | بدنه JSON بیشتر از ۱ MiB، یا فرمی بزرگ‌تر از آنچه PHP هاست برای کل یک درخواست می‌پذیرد ([قراردادها](#قراردادها)) | فرم: تصویرش را کوچک کنید |
| `415` | بدنه‌ای که JSON نیست — و جایی که تصویر فرستاده می‌شود، فرم هم نیست ([قراردادها](#قراردادها)) | `Content-Type: application/json` بفرستید |
| `422` | رد شد: فیلدها زیر `errors` — روی <code dir="ltr">/me/\*</code>، تایید تلگرام یا گوگلی هم که معتبر نبود —، یک وضعیت زیر `errors.status`، یا کل درخواست (روش ورودی که خاموش شده، گرفتن nonce وقتی نه ورود با تلگرام روشن است و نه ورود با گوگل) | پیام‌ها را نشان دهید |
| `429` | تلاش‌های زیاد ([محدودیت‌ها و مدت اعتبار](Store-API-Sign-In.md#محدودیت‌ها-و-مدت-اعتبار))، یا گذشتن از یکی از سقف‌های خود کاربر ([هدر Idempotency-Key](Store-API-Buying.md#هدر-idempotency-key)، [رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید)، [پرسیدن وضعیت پرداخت آنلاین](Store-API-Buying.md#پرداخت-آنلاین)، [خواندن لحظه‌ای سرویس](Store-API-After-Buying.md#خواندن-لحظه‌ای-سرویس)، [لینک جدید](Store-API-After-Buying.md#لینک-جدید)، [انتقال موجودی](Store-API-After-Buying.md#انتقال-موجودی-به-کاربر-دیگر)، [محدودیت‌های تیکت‌ها](Store-API-Support-Tickets.md#محدودیت‌ها)) — یا کار مدیران روی پنل‌های VPN ([مدیران سایت](Store-API-Admins.md#ردها))؛ به اندازه ثانیه‌هایی که `Retry-After` می‌گوید صبر کنید | همان کار را تا آن موقع غیرفعال نگه دارید |
| `500` | سرور خطا داد (با `request_id` لاگ شده) | پیام و «کد پیگیری» |
| `502` | سرویسی که فروشگاه به آن وابسته است پاسخ نداد: تلگرام، گوگل، پنل یک سرور VPN، سرور ایمیل | بعدا دوباره امتحان کنید |
| `503` | ایمیل فروشگاه فرستاده نمی‌شود — یا سهمیه ایمیل‌های ورودش فعلا تمام شده —، نشد کپچا را سنجید، نشد از درگاه پرداخت آنلاین پرسید، دیسک سرور برای گرفتن تصویر بیش از حد پر است یا فروشگاه سهمیه تصویرهای امروزش را گرفته، فروشگاه الان سفارش نمی‌گیرد (رباتش خاموش است — یا در فروشگاه نماینده، فروشگاه اصلی فروشش را متوقف کرده، که در این حالت رسید هنوز پذیرفته می‌شود و درخواست‌هایی که فقط قیمت سفارش را حساب می‌کنند `422` روی `status` می‌گیرند: [خرید](Store-API-Buying.md#روند-خرید))، فروشگاه به اندازه ظرفیتش ورود نیمه‌کاره — یا نظر منتظر پشتیبانی — نگه داشته، دیتابیس فروشگاه در دسترس نیست، یا فروشگاه نصب نشده | روش ورود دیگر، یا بعدا |

## نسخه‌بندی

بخش `v1` در مسیر نسخه API است و `resources/api/openapi.yaml` قرارداد آن. در v1 پاسخ‌ها فقط فیلد تازه می‌گیرند — هیچ
فیلدی حذف یا تغییر نام داده نمی‌شود یا نوعش عوض نمی‌شود — و درخواست‌ها همان چیزی را که می‌پذیرفتند همچنان می‌پذیرند؛
تغییری که وب‌سایتی را خراب کند در v2، کنار v1، می‌آید. کلاینت را طوری بنویسید که با چیزهای اضافه کنار بیاید — فیلد تازه،
مقدار enum تازه، نوع اعلان تازه — و آنچه را نمی‌شناسد نادیده بگیرد. شیءهای قرارداد برای تست‌های خود فروشگاه بسته‌اند
(`additionalProperties: false`): سایتی که پاسخ‌ها را با نسخه‌ای از آن اعتبارسنجی می‌کند باید با به‌روزرسانی فروشگاه
نسخه‌اش را هم تازه کند، وگرنه نسخه قدیمی‌تر پاسخ جدیدتر را رد می‌کند.

## یک کلاینت ساده

نوع‌ها از قرارداد می‌آیند — فایل `docs/openapi.json` همان نسخه‌ای که فروشگاه اجرا می‌کند
(`npx openapi-typescript openapi.json -o lib/store-api.ts`) —؛ بقیه‌اش فقط `fetch` است:

```ts
// lib/store.ts — browser side
import type { components } from './store-api'
export type S = components['schemas']

const BASE = process.env.NEXT_PUBLIC_STORE_API! // https://panel.example.com/api/store/v1/c4859b5b660377ef517299cf

/** Where a bearer token is kept: read, written and forgotten in one place. */
export type Tokens = { get(): string | null; keep(token: string): void; clear(): void }
const keptIn = (storage: () => Storage, key: string): Tokens => ({
  get: () => storage().getItem(key),
  keep: (token) => storage().setItem(key, token),
  clear: () => storage().removeItem(key),
})
/** A customer's: in localStorage, so they stay signed in across visits. */
export const customerTokens = keptIn(() => localStorage, 'store-token')
/** An admin's: in sessionStorage, gone with the tab — never in localStorage (see the shop's admins). */
export const adminTokens = keptIn(() => sessionStorage, 'store-admin-token')

export class StoreError extends Error {
  constructor(
    readonly status: number,
    readonly body: S['ErrorResponse'],
    readonly retryAfter: number | null,
    readonly challenge: string | null, // WWW-Authenticate
  ) {
    super(body.message)
  }
  /** The first message under a request field, when the refusal names one. */
  on(field: string): string | undefined {
    return this.body.errors?.[field]?.[0]
  }
  /** The session ended: a 401 with `WWW-Authenticate: Bearer` — a sign-in's refused proof (/auth/*) has none. */
  get signedOut(): boolean {
    return this.status === 401 && /^Bearer\b/i.test(this.challenge ?? '')
  }
  /** A change of how the account is signed in to, refused for a sign-in that is not recent. */
  get needsRecentSignIn(): boolean {
    return this.status === 403 && /insufficient_user_authentication/.test(this.challenge ?? '')
  }
}

type Call = {
  method?: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'
  json?: unknown // a JSON body
  form?: FormData // a request with a picture: a receipt, a ticket's message
  key?: string // Idempotency-Key, for a request that orders
  signal?: AbortSignal
  tokens?: Tokens // whose token goes: the customer's, unless the call says otherwise
}

export async function store<T>(path: string, { method = 'GET', json, form, key, signal, tokens = customerTokens }: Call = {}): Promise<T> {
  const token = tokens.get()
  const headers: Record<string, string> = {}
  if (token) headers.Authorization = `Bearer ${token}`
  if (key) headers['Idempotency-Key'] = key
  if (json !== undefined) headers['Content-Type'] = 'application/json'

  const res = await fetch(BASE + path, { method, headers, body: json !== undefined ? JSON.stringify(json) : form, signal })
  if (res.status === 204) return undefined as T
  const body = await res.json().catch(() => null)
  if (res.ok) return body as T

  const wait = res.headers.get('Retry-After')
  const error = new StoreError(
    res.status,
    body ?? { message: `HTTP ${res.status}`, request_id: res.headers.get('X-Request-Id') ?? '' },
    wait === null ? null : Number(wait),
    res.headers.get('WWW-Authenticate'),
  )
  if (error.signedOut) tokens.clear() // the session ended: show the sign-in
  throw error
}

/** The admin area's calls — `/admin/*`, and `/me` as its admin — with the admin's token. */
export function admin<T>(path: string, call: Call = {}): Promise<T> {
  return store<T>(path, { ...call, tokens: adminTokens })
}

export const keepToken = (token: string, tokens: Tokens = customerTokens) => tokens.keep(token)

export async function signOut(tokens: Tokens = customerTokens) {
  await store<void>('/auth/logout', { method: 'POST', tokens }).catch(() => undefined)
  tokens.clear()
}
```

کاربر با <code dir="ltr">keepToken(token)</code> وارد می‌شود و سایت <code dir="ltr">store()</code> را صدا می‌زند؛ بخش
مدیریت، مدیر را با <code dir="ltr">keepToken(token, adminTokens)</code> وارد می‌کند، <code dir="ltr">admin()</code> را
صدا می‌زند و با <code dir="ltr">signOut(adminTokens)</code> خارج می‌شود — توکن مدیر هیچ‌وقت به `localStorage` نمی‌رسد
([مدیران سایت](Store-API-Admins.md#ورود)). تابع <code dir="ltr">store()</code> برای مرورگر است: storage را هنگام فراخوانی
می‌خواند، پس import کردن ماژول روی سرور ضرری ندارد، ولی کاتالوگ عمومی را آنجا با یک `fetch` ساده رندر کنید
([فراخوانی از سرور شما](#فراخوانی-از-سرور-شما)).

## همه اندپوینت‌ها

هر عملیات — چه کسی می‌تواند صدایش بزند، پارامترها، بدنه فیلد به فیلد، پاسخ‌ها — در
[مرجع Store API (انگلیسی)](../Store-API-Reference.md) آمده که از روی کد ساخته می‌شود: اول عملیات‌های عمومی، بعد عملیات‌های
کاربر واردشده؛ عملیات‌های مدیران سایت در [مرجع API مدیران (انگلیسی)](../Store-Admin-API-Reference.md) است. در همه آن‌ها:
عملیات کاربر بعد از تمام شدن Session `401` با `WWW-Authenticate: Bearer` می‌دهد، و به کاربر مسدود `403`؛ عملیاتی که
روش‌های ورود به حساب را عوض می‌کند، یا سرویس یا پولی را به کاربر دیگری می‌دهد، `403` با چالش
[ورود تازه](Store-API-Account.md#ورود-تازه) می‌دهد، مگر اینکه ورود حداکثر ۱۵ دقیقه پیش بوده یا بعد از آن دوباره ثابت
شده باشد؛ هر درخواست سفارش، و انتقال موجودی به کاربر دیگر، [Idempotency-Key](Store-API-Buying.md#هدر-idempotency-key)
خودش را دارد — تغییر کیف پول به دست مدیر، و پاسخ او به تیکت، هم می‌توانند کلید داشته باشند
([تغییری که دوباره فرستاده می‌شود](Store-API-Admins.md#این-api-چیست))؛ و هر کدام ممکن است با شکل خطا پاسخ دهد
([خطاها](#خطاها)).

## پیام‌هایی که بهتر است بشناسید

تصمیم را بر اساس کد وضعیت و فیلد `errors` بگیرید؛ متن‌ها برای کاربرند و ممکن است عوض شوند. این‌ها پیام‌هایی هستند که شاید
سایت بخواهد از هم تشخیصشان دهد، یا بهتر توضیحشان دهد.

| وضعیت | پیام | کجا، و چه معنایی دارد |

| 404 | `این فروشگاه وب‌سایت فعالی ندارد.` | همه اندپوینت‌ها، وقتی از سرور خوانده شوند: کلید فروشگاه هیچ وب‌سایتی را باز نمی‌کند — خاموش است، کلید عوض شده، یا فروشگاه یک نماینده بسته شده |

| 401 | `برای دسترسی باید وارد شوید.` | اندپوینت کاربر: توکنی نیست، یا Session تمام شده — تنها 401 آنجا، تنها 401 با `WWW-Authenticate: Bearer` |
