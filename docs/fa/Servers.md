# سرورها

«سرورها»، فقط در پنل مدیریت: پنل‌های VPN که فروشگاه روی آن‌ها می‌فروشد — 3X-UI v3، PasarGuard 3.1+، HMPanel 2.5+،
Marzban 0.8+، Rebecca 1.0+ یا Remnawave 2.1+. همه فروشگاه‌ها روی همین سرورها می‌فروشند: پلن‌های هر نماینده هم روی آن‌ها ساخته می‌شوند، و سرویس‌های یک سرور مال همه فروشگاه‌هاست.
پنل نمایندگی صفحه سرورها ندارد.

## فهرست

همه سرورها، به ترتیب افزوده شدن: نامش — لینکی به [صفحه آن](#صفحه-سرور) —، کانکتور و آدرس پنلش، و به رنگ نارنجی دلیل
اینکه نمی‌تواند بفروشد، اگر نمی‌تواند؛ بعد «وضعیت»، «اینباندها» («۳ از ۵ برای فروش»)، «اشتراک‌های فعال» — مال همه
فروشگاه‌ها، با « / 200» وقتی ظرفیت دارد — و «آخرین بررسی».

| «وضعیت» | یعنی |
|---|---|
| «غیرفعال» | شما خاموشش کرده‌اید — هر وضعیت دیگری هم که داشته باشد |
| «خطا در اتصال» | آخرین تماس با پنلش ناموفق بود؛ ⓘ کنار آن دلیلش را می‌گوید: چه چیزی را باید درست کرد، و زیر آن، در خطی جدا، جزئیات فنی (پیام خود پنل، یا پیام cURL) |
| «متصل» | آخرین تماس موفق بود |
| «بررسی نشده» | هرگز با آن تماس گرفته نشده |

## افزودن سرور

«افزودن سرور» می‌پرسد چه نرم‌افزاری پنل را اجرا می‌کند — «3X-UI»، «PasarGuard»، «HMPanel (HMray)»، «Marzban»، «Rebecca» یا
«Remnawave»، هر کدام با توضیحاتش و لینکی به پروژه‌اش —، بعد فرمش را نشان می‌دهد:

| فیلد | چه می‌گیرد |
|---|---|
| «نام سرور» | حداکثر ۱۰۰ کاراکتر. **کاربران آن را می‌بینند**: این «لوکیشن» سرور در ربات، در وب‌سایت فروشگاه و صفحه وضعیت آن است — آن را همان‌طور نام بگذارید که کاربر باید بخواند («آلمان ۱») |
| «ایموجی پرمیوم نام» | اختیاری: یک ایموجی پرمیوم از فهرست ربات ([متن‌ها و کیبوردهای ربات](Bot-Texts-And-Keyboards.md#ایموجی-پرمیوم)). وقتی انتخاب شود، ایموجی معمولی آن اولین ایموجی نام می‌شود و ربات همان را پرمیوم نشان می‌دهد: دکمه لوکیشن آن را به‌صورت آیکون می‌گیرد — به جای «🌍» که متن دکمه با آن شروع می‌شود —، و متن‌هایی که لوکیشن را نام می‌برند (`%server%`) آن را سر جای خودش نشان می‌دهند. وب‌سایت، صفحه وضعیت و پنل‌ها همان ایموجی معمولی را نشان می‌دهند. تا وقتی انتخاب شده، نام باید با یک ایموجی شروع شود |
| «آدرس پنل» | آدرس خود پنل، حداکثر ۲۵۵ کاراکتر، با http یا https: برای 3X-UI همراه مسیر پایه وب آن (`https://host:2053/AbCdEf`)، بدون <code dir="ltr">/panel</code> یا <code dir="ltr">/login</code> صفحه‌هایش بعد از آن؛ برای PasarGuard آدرس داشبوردش بدون <code dir="ltr">/dashboard</code> (`https://panel.example.com:8000`)، و بدون <code dir="ltr">/api</code>؛ برای HMPanel آدرسی که صفحه ورودش با آن باز می‌شود (`https://panel.example.com`)، بدون <code dir="ltr">/api</code>، <code dir="ltr">/dashboard</code>، <code dir="ltr">/clients</code> یا هر صفحه دیگرش؛ برای Marzban آدرس داشبوردش بدون <code dir="ltr">/dashboard</code> (`https://panel.example.com:8000`)، و بدون <code dir="ltr">/api</code> یا <code dir="ltr">/docs</code>؛ برای Rebecca هم همین‌طور؛ برای Remnawave آدرس https ریورس‌پراکسی آن، همان دامنه‌ای که داشبوردش با آن باز می‌شود (`https://panel.example.com`)، بدون <code dir="ltr">/dashboard</code>، <code dir="ltr">/auth</code> یا <code dir="ltr">/api</code> — پورت خودش با http ساده فقط روی هاست خود فروشگاه یا شبکه خصوصی آن ([Remnawave](#کانکتورها)). بدون <code dir="ltr">user:pass@</code>، `?` یا `#` |
| «احراز هویت» | «توکن API» (3X-UI، Remnawave) یا «کلید API» (PasarGuard، HMPanel، Rebecca) — پیشنهادی —، یا «نام کاربری و رمز». HMPanel، Rebecca و Remnawave فقط کلید یا توکنشان را می‌گیرند: API آن‌ها رمز ادمین نمی‌پذیرد. Marzban فقط «نام کاربری و رمز» را می‌گیرد: API آن کلید ندارد |
| «توکن API» / «کلید API» | برای 3X-UI از *Settings → Security → API Token*، یک توکن **Admin** (توکن Monitor یا Node فقط وضعیت را می‌خواند). برای PasarGuard از *API Keys* (نسخه 5.1 به بعد): کل کلید <code dir="ltr">pg_key_…</code>، که پنل فقط یک بار نشان می‌دهد، ساخته‌شده با *Inherit admin permissions* — یا با دسترسی‌های کاربران (ایجاد، مشاهده، ویرایش، حذف، بازنشانی مصرف و لغو اشتراک) و مشاهده گروه‌ها (فهرست ساده‌شان کافی است) و سیستم —، بهتر است بدون تاریخ انقضا و سقف درخواست. برای HMPanel از «تنظیمات ← API» آن: کل کلید <code dir="ltr">hmp_…</code>، که پنل فقط یک بار نشان می‌دهد، ساخته‌شده با دسترسی `*` — یا با `clients.read`، `clients.write`، `clients.renew` و `inbounds.read`. برای Rebecca از «حساب من ← کلیدهای API» آن: کل کلید <code dir="ltr">rk_…</code>، که پنل فقط یک بار نشان می‌دهد — کلید یک ادمین full access یا sudo ([Rebecca](#کانکتورها)). برای Remnawave از *Remnawave Settings → API Tokens*: کل توکن — <code dir="ltr">eyJ…</code>، سه بخش که با نقطه از هم جدا شده‌اند —، که پنل فقط یک بار نشان می‌دهد، ساخته‌شده با دسترسی‌های <code dir="ltr">users:*</code>، <code dir="ltr">internal-squads:read</code> و <code dir="ltr">system:read</code> (دسترسی `*` هم کار می‌کند، ولی همه پنل را باز می‌کند) |
| «نام کاربری» / «رمز عبور» | ادمین پنل که با آن وارد می‌شوید (در PasarGuard: ادمینی که در داشبورد ساخته شده و همه کاربرها را می‌بیند — ادمین فایل env آن فقط در حالت debug وارد می‌شود ([PasarGuard](#کانکتورها))؛ در Marzban: یک ادمین sudo، که همه کاربرها را می‌بیند — ادمین دیگر فقط کاربرهایی را می‌بیند که خودش ساخته) |
| «کلید TOTP» | فقط 3X-UI، وقتی ورود دومرحله‌ای آن روشن است: کلید محرمانه Base32 که هنگام روشن کردنش نشان داد. فروشگاه کد هر ورود را از آن می‌سازد |

زیر «تنظیمات پیشرفته»:

| فیلد | چه می‌گیرد |
|---|---|
| «کلید دروازه» | فقط Remnawave، برای پنلی پشت دروازه ورود (Caddy یا TinyAuth): کلید API همان دروازه — در TinyAuth کل مقدار <code dir="ltr">Basic …</code> —، که با هر درخواست فرستاده می‌شود. برای پنل بدون دروازه، خالی ([Remnawave](#کانکتورها)) |
| «بررسی گواهی TLS» | روشن. برای پنلی با گواهی خودامضا، خاموش |
| «تایم‌اوت اتصال (ثانیه)» | ۵ تا ۱۲۰، پیش‌فرض ۳۰: یک درخواست به پنل حداکثر چقدر طول بکشد (برقراری اتصال حداکثر بعد از ۱۰ ثانیه رها می‌شود) |
| «آدرس اشتراک» | خالی: لینک‌های اشتراک همان لینک‌های خود پنل‌اند. پر: پیشوند کامل پیش از توکن لینک، وقتی لینک‌ها باید از آدرس دیگری بیایند (یک پراکسی معکوس): `https://sub.example.com/sub` (برای لینک‌های HMPanel: `https://sub.example.com/s`؛ برای Remnawave، پیشوند پیش از شناسه کوتاه کاربر: `https://sub.example.com`) |
| «اتصال از طریق پراکسی SOCKS5» | خاموش: فروشگاه مستقیم با پنل حرف می‌زند. روشن: هر درخواستی که فروشگاه به این پنل می‌فرستد از یک پراکسی SOCKS5 می‌گذرد ([پایین‌تر](#پنل-پشت-پراکسی-socks5))، و این فیلدها ظاهر می‌شوند: |
| «آدرس پراکسی» | نام هاست یا آدرس IP پراکسی، بدون <code dir="ltr">socks5://</code> و بدون پورت: `proxy.example.com`، `203.0.113.10` (IPی که با رقم فارسی تایپ شود همان IP خوانده می‌شود) |
| «پورت پراکسی» | 1 تا 65535، پیش‌فرض 1080 |
| «نام کاربری پراکسی» / «رمز پراکسی» | برای پراکسی بدون ورود، خالی. رمز فقط همراه نام کاربری |
| «ظرفیت» | چند سرویس **فعال** می‌تواند داشته باشد — مال همه فروشگاه‌ها روی هم، اکانت‌های تست هم. خالی یعنی نامحدود؛ **`0` یعنی پر** |
| «یادداشت» | یادداشت خود شما، حداکثر ۱۰۰۰ کاراکتر؛ جز همین فرم هیچ جا نشان داده نمی‌شود |
| «فعال» | خاموش: چیز تازه‌ای روی آن فروخته یا به آن منتقل نمی‌شود |
| «رنگ دکمه در ربات» | دکمه آن میان لوکیشن‌های یک پلن در ربات: آبی، سبز، قرمز، یا «پیش‌فرض تلگرام». ربات همه فروشگاه‌ها آن را همین‌طور نشان می‌دهد |
| «جای دکمه در ربات» | یک ردیف جدا، یا دوتا یا سه‌تا در یک ردیف: لوکیشن‌های هم‌عرضی که در ترتیب یک پلن پشت سر هم می‌آیند، در یک ردیف کنار هم قرار می‌گیرند |

**«تست اتصال»** فرم را همان‌طور که هست امتحان می‌کند و چیزی ذخیره نمی‌کند: اینکه پنل پاسخ می‌دهد و اطلاعات ورود را
می‌پذیرد یا نه، وضعیتش (هسته، CPU، RAM، دیسک)، اینباندهایش، و اینکه لینک اشتراک می‌دهد یا نه. لازم است کل فرم درست پر
شده باشد، نام هم. خطا با زبان ساده می‌گوید چه چیزی را باید درست کرد — دامنه، پورت یا فایروال، تایم‌اوت، گواهی، توکن یا
رمزی که رد شده، ریدایرکتی که باید دنبال شود، آدرس اشتباه — و پاسخ خود پنل را زیر آن.

**«افزودن سرور»** آن را ذخیره می‌کند، بعد همان لحظه بررسی‌اش می‌کند — چه تست شده باشد چه نه — و صفحه‌اش را با آنچه
بررسی پیدا کرده باز می‌کند. **حتی وقتی آن بررسی ناموفق باشد هم ذخیره می‌شود**: اتصال را در صفحه‌اش درست کنید. بررسی،
اینباندهایش را فهرست می‌کند، و **هیچ‌کدام برای فروش نیستند** تا وقتی علامتشان بزنید ([اینباندها](#اینباندها)).

**اطلاعات محرمانه** — توکن یا کلید، رمز عبور، کلید TOTP، کلید دروازه Remnawave، رمز پراکسی — رمزنگاری‌شده نگه داشته
می‌شوند و هرگز دوباره نشان داده نمی‌شوند: مقدار نگه‌داشته‌شده به شکل نقطه نشان داده می‌شود — توکنی با ۱۲ کاراکتر یا
بیشتر با چهار کاراکتر آخرش؛ رمز عبور، کلید TOTP، کلید دروازه و رمز پراکسی بدون هیچ کاراکتری. اگر در ویرایش خالی بماند، همان می‌ماند؛ «پاک کردن مقدار
ذخیره‌شده» مقداری را پاک می‌کند که اتصال بدون آن هم کار می‌کند — مقداری که لازم دارد (توکن یا رمز پنل) چنین دکمه‌ای
ندارد: مقدار تازه را تایپ کنید. **اطلاعات محرمانه فقط تا وقتی می‌ماند که راه رسیدن به پنل همان بماند**: مبدا
(origin) آدرس — همان http یا https، هاست و پورت (مسیر می‌تواند تغییر کند) —، آدرس و پورت پراکسی، و «بررسی گواهی TLS».
اگر یکی عوض شود، توکن، رمز یا کلید دروازه نگه‌داشته‌شده هرگز از راه تازه فرستاده نمی‌شود، حتی با «تست اتصال»: فرم دوباره آن را
می‌خواهد («آدرس پنل، پراکسی یا بررسی گواهی TLS عوض شده است؛ … را دوباره وارد کنید.»). خاموش کردن پراکسی آن را نگه
می‌دارد — آن‌وقت مستقیم به همان پنلی می‌رود که برایش داده شده بود. رمز پراکسی هم به همین شکل فقط تا وقتی می‌ماند که
آدرس و پورت پراکسی همان باشند. ذخیره با یک روش ورود دیگر، اطلاعات ورود روش قبلی را پاک می‌کند.

### پنل پشت پراکسی SOCKS5

بعضی هاست‌ها اصلا به پنل نمی‌رسند — هاست اشتراکی در خارج که کشور پنل شبکه‌اش را فیلتر می‌کند، پنلی که فقط از داخل
شبکه خودش پاسخ می‌دهد. زیر «تنظیمات پیشرفته»، «اتصال از طریق پراکسی SOCKS5» را روشن کنید و یک پراکسی SOCKS5 بدهید که
هاست فروشگاه به آن برسد و خودش به پنل برسد (انتخاب معمول، پراکسی‌ای روی سرور خود پنل، یا سروری در شبکه آن است):

- **فقط این پنل از آن می‌گذرد.** تلگرام، ایمیل، کپچا، ورود با Google، بررسی به‌روزرسانی و همه سرورهای دیگر مثل قبل
  مستقیم با اینترنت حرف می‌زنند؛ هر سرور پراکسی خودش را دارد، یا هیچ.
- **پراکسی نام پنل را پیدا می‌کند** (SOCKS5 با DNS از راه دور)، پس نامی که فقط شبکه پراکسی آن را می‌شناسد کار می‌کند.
  «آدرس پنل» همان آدرس خود پنل می‌ماند، همان‌طور که پراکسی آن را می‌بیند.
- **«تست اتصال»، «بررسی اتصال» و هر فروش، تمدید، همگام‌سازی، هدیه، انتقال و افزودن سرویس با لینک** به همین شکل از
  آن می‌گذرند: پیش از ذخیره، با «تست اتصال» امتحانش کنید.
- **خطای پراکسی به نام خود پراکسی گفته می‌شود**: «اتصال از طریق پراکسی SOCKS5 سرور برقرار نشد؛ …» — آدرس یا پورتش
  اشتباه است، پراکسی خاموش است، نام کاربری یا رمزش رد شده، یا پراکسی به پنل نمی‌رسد —، همراه پیام cURL زیر آن، و هرگز
  رمز پراکسی. آن‌وقت پنل هم مثل هر پنل دیگری که در دسترس نیست ۱۰ دقیقه کنار گذاشته می‌شود ([سلامت](#سلامت)).
- با خاموش کردن آن، آدرس، پورت، نام کاربری و رمز پراکسی فراموش می‌شوند.

صفحه سرور «پراکسی SOCKS5» — آدرس و نام کاربری پراکسی — را میان مشخصات اتصالش نشان می‌دهد.

## امکان فروش

سرور فقط وقتی به کاربران پیشنهاد می‌شود — در ربات، در وب‌سایت، به‌عنوان مقصد انتقال — که هیچ‌کدام از این‌ها مانعش
نباشد؛ فهرست و صفحه سرور اولین مانع را می‌گویند:

1. «کانکتور این سرور در این نصب وجود ندارد.» — کانکتور نرم‌افزار آن در این نصب نیست.
2. «سرور غیرفعال است.»
3. «سرور هنوز بررسی نشده است؛ …» — هنوز هیچ بررسی‌ای نفهمیده که لینک اشتراک می‌دهد یا نه (سرور تازه‌ای که اولین
   بررسی‌اش نتوانسته وصل شود هم همین را می‌گوید).
4. «سرور لینک اشتراک نمی‌دهد؛ …» — هر سرویس یک لینک اشتراک می‌گیرد و نه چیز دیگر، پس پنلی که سرویس اشتراکش خاموش است
   نمی‌تواند بفروشد. آن را در پنل روشن کنید، بعد «بررسی اتصال» را بزنید.
5. «ظرفیت سرور پر است.»

پلنی که روی سروری فروخته می‌شود که نمی‌تواند بفروشد، فقط آنجا پیشنهاد نمی‌شود؛ پلنی که دیگر جایی برای فروش ندارد از
ربات کنار می‌رود ([پلن‌ها](Plans.md)).

## صفحه سرور

**«بررسی اتصال»** در بالای صفحه، سرور ذخیره‌شده را بررسی می‌کند و آنچه را فهمیده نگه می‌دارد: سلامتش، اینکه لینک
اشتراک می‌دهد یا نه، اینباندهایش. بعد از تغییر هر چیزی در پنل یا در تنظیمات سرور آن را بزنید. سروری که کانکتورش دیگر
در این نصب نیست بررسی نمی‌شود: «کانکتور این سرور در این نصب وجود ندارد.»

- **«وضعیت»** — زمان آخرین بررسی، وضعیتش، اینکه چرا آخرین تماسش ناموفق بود، اگر ناموفق بود — چه چیزی را باید درست
  کرد، و زیر آن، در خطی جدا، جزئیات فنی (پیام خود پنل، یا پیام cURL) —، و اینکه چرا نمی‌تواند بفروشد، اگر نمی‌تواند.
  بررسی‌ای که در همین صفحه انجام شود نتیجه خودش را به جای آن خطا نشان می‌دهد. CPU، RAM، دیسک و آپتایم پنل
  فقط برای بررسی‌ای نشان داده می‌شوند که همین حالا در همین صفحه انجام شده (یا درست بعد از افزودنش): هیچ‌کدام نگه داشته
  نمی‌شوند. بعد، روش ورود فروشگاه، جایی که لینک‌ها از آن می‌آیند («از تنظیمات پنل»، یا پیشوند شما)، پراکسی SOCKS5 وقتی
  پنل از راه یک پراکسی در دسترس است، بررسی TLS، تایم‌اوت، و سرویس‌های فعالش: مال همه فروشگاه‌ها — همان که ظرفیتش
  می‌شمارد —، و وقتی کاربران نماینده‌ها هم اینجا سرویس دارند، اینکه چندتایشان مال فروشگاهی است که باز است (با لینکی به
  آن‌ها در «اشتراک‌ها»، که فقط سرویس‌های فروشگاه باز را فهرست می‌کند).
- **«اینباندها»** — [پایین‌تر](#اینباندها).
- **«اکانت تست»** — اکانت‌های تست رایگانی که کاربران می‌توانند روی آن بگیرند ([پایین‌تر](#اکانت-تست)).
- **«تنظیمات اتصال»** — دوباره همان فرم، با «تست اتصال»، «بازگردانی تغییرات» و «ذخیره تغییرات» (هر دو تا وقتی یک فیلد با
  مقدار ذخیره‌شده فرق نکند غیرفعال‌اند). همه فیلدها جز کانکتور اینجا قابل تغییرند (نوع دیگری از پنل، سرور دیگری است).
  **ذخیره کردن آن را دوباره بررسی نمی‌کند**: بعدش «بررسی اتصال» را بزنید. کلید «فعال» اینجاست، زیر «تنظیمات پیشرفته».
  اگر سرور در این میان جای دیگری (تبی دیگر) ذخیره شود، آنچه تایپ کرده‌اید می‌ماند و فرم همین را می‌گوید؛ «دیدن نسخه
  تازه» به جای آن نسخه ذخیره‌شده را نشان می‌دهد.
- **«افزودن زمان و حجم»** — روز و حجم برای سرویس‌هایش ([پایین‌تر](#افزودن-زمان-و-حجم)).
- **«انتقال سرویس‌ها»** — انتقال سرویس‌های همه فروشگاه‌ها روی آن به سرور دیگر، برای خالی کردنش یا نجات آن‌ها از پنلی که
  از دست رفته ([پایین‌تر](#انتقال-سرویس‌ها)).
- **«حذف سرور»** — [پایین‌تر](#حذف-سرور).

### اینباندها

اینباندهای پنل همان‌طور که فروشگاه آخرین بار خوانده — در PasarGuard گروه‌ها نقش آن‌ها را دارند؛ در HMPanel اینباندهای
پنل‌های 3X-UI زیرمجموعه‌اش هستند، هر کدام با نام پنلش («Germany · DE»)؛ در Marzban اینباندهای تنظیمات Xray آن، هر
کدام با تگش؛ در Rebecca سرویس‌هایش، که پلن یکی از آن‌ها را انتخاب می‌کند؛ در Remnawave اسکوادهای داخلی‌اش، که هر کلاینت
می‌تواند هم‌زمان در چند تا از آن‌ها باشد —، هر کدام با پروتکل، پورت، کلاینت‌ها و کلید
«فروش». پلنی که روی کل سرور فروخته می‌شود، در لحظه هر خرید، همه اینباندهایی را به کار می‌برد که
کلید «فروش» آن‌ها روشن است و روی پنل فعال‌اند؛ پلنی که اینباندهایش را مشخص کرده، همان‌ها را به کار می‌برد، هر چه کلید بگوید
([پلن‌ها](Plans.md))؛ سرویسی که به اینجا منتقل شده، روی پلنی که این سرور را ندارد، اینباندهای علامت‌خورده را می‌گیرد.
هر سرویس یک کلاینت روی پنل است، وصل به اینباندهایش.

فروشگاه فقط با «به‌روزرسانی از پنل»، «بررسی اتصال» و بررسی سرور تازه آن‌ها را می‌خواند — هرگز خودبه‌خود. اینباندهای
تازه برای فروش نیستند. اینباندی که پنل دیگر فهرستش نمی‌کند خاموش می‌شود و با انتخاب شما نگه داشته می‌شود، برای وقتی
که برگردد؛ در این مدت نمی‌شود روشنش کرد، همان‌طور که اینباندی را که روی پنل غیرفعال است. اگر remark یا tag خیلی بلند
باشد، کوتاه‌شده نگه داشته می‌شود (۲۵۵ کاراکتر از remark، ۱۲۸ از tag).

### اکانت تست

کارت «اکانت تست» تعیین می‌کند که اکانت تست رایگان روی این سرور، در همه فروشگاه‌ها — ربات اصلی و ربات هر نماینده —،
چه بگیرد، و جداگانه ذخیره می‌شود: اینکه سرور اصلا تست می‌دهد یا نه («اکانت تست روی این سرور»، در ابتدا خاموش)، حجم و
ساعت‌های یک تست، و اینکه ساعت‌ها از اولین اتصال کاربر شمرده شوند یا نه. هر فیلد در
[اکانت‌های تست](Test-Accounts.md#آنچه-اکانت-تست-می‌گیرد-شرایط-هر-سرور) توضیح داده شده است.

هر اکانت تست یک کلاینت است — روی پنلی که اینباند دارد، روی همه اینباندهایی که کلید «فروش» آن‌ها روشن است —، و فقط تا وقتی ساخته
می‌شود که سرور می‌تواند بفروشد. مثل هر سرویس فعالی، از «ظرفیت» سرور جا می‌گیرد. تغییر برای تست‌هایی اعمال می‌شود که از
آن به بعد ساخته شوند. نماینده‌ها این شرایط را در صفحه اکانت‌های تست خود می‌بینند و نمی‌توانند تغییرشان دهند. قوانین خود
فروشگاه — کلید، سهمیه، پاک‌سازی — در «فروشگاه › اکانت تست» هستند ([اکانت‌های تست](Test-Accounts.md#قوانین-فروشگاه)).

### افزودن زمان و حجم

«افزودن زمان و حجم» › «افزودن به سرویس‌ها» به سرویس‌های این سرور روز و حجم می‌دهد — جبران یک قطعی، یک هدیه:

- «تعداد روز» (۰ تا ۳۶۵) — به پایان هر سرویس اضافه می‌شود، یا برای سرویسی که هنوز شروع نشده مدت بلندتری می‌شود؛
  «حجم (گیگابایت)» (۰ تا ۱۰۰۰۰) — روی سقف حجم آن. دست‌کم یکی بیشتر از صفر.
- «دلیل» — اختیاری، حداکثر ۳۰۰ کاراکتر: کاربران آن را زیر هدیه می‌خوانند («توضیح پشتیبانی: …»).
- «سرویس‌های در انتظار اولین اتصال هم شامل شوند» — خاموش: قطعی برای سرویسی که زمانش شروع نشده هزینه‌ای نداشته است.
- «پیام به مشتری‌ها» — روشن: به هر کاربر با ربات فروشگاه خودش خبر داده می‌شود، یا با ایمیل وقتی تلگرام به او نمی‌رسد، و
  این اطلاعیه در وب‌سایتش نگه داشته می‌شود.

**چه کسی می‌گیرد**: سرویس‌های همه فروشگاه‌ها که وقتی هدیه را دادید روی این سرور بودند — نه سرویس‌هایی که بعدا خریده
شده‌اند، و نه اکانت‌های تست — و در حال کارند. در حال کار بودن را پنل تعیین می‌کند و در نوبت هر سرویس از آن پرسیده
می‌شود: سرویسی که با تمام شدن زمان یا حجم تمام شده، یا خاموش شده — توسط پشتیبانی یا روی پنل —، رد می‌شود؛ روز فقط به
سرویسی می‌رسد که روزی تمام می‌شود، و حجم فقط به سرویسی که سقف حجم دارد. سرویسی که روزها پایانش را بعد از
[آخرین روزی](Services.md#مراقب-باشید) که فروشگاه می‌تواند نگه دارد ببرند، کامل رد می‌شود، حجمش هم. پنجره، کسانی را که
هدیه به آن‌ها می‌رسد از روی نسخه فعلی فروشگاه می‌شمارد؛ پیشرفت کارت می‌گوید چند سرویس بررسی شدند، هدیه گرفتند، رد شدند
یا ناموفق ماندند.

**چطور اجرا می‌شود**: یک سرویس در هر بار، توسط کارت تا وقتی صفحه باز است، وگرنه توسط زمان‌بند به‌طور پیش‌فرض هر دقیقه. روی هر سرور هر
بار یک هدیه اجرا می‌شود — سهم یک [هدیه همگانی](Broadcasts.md#هدیه-همگانی) روی آن هم همین‌طور.

- **پنلی که در دسترس نیست** هدیه را روی همان سرویس نگه می‌دارد، با یادداشتی نارنجی که دلیلش را می‌گوید، و وقتی پنل
  پاسخ بدهد ادامه پیدا می‌کند.
- **درخواستی که پاسخ روشنی نگرفت** — تایم‌اوت شد، اتصال قطع شد، یا پراکسی جلوی پنل یک صفحه خطا فرستاد — باعث
  می‌شود از پنل پرسیده شود الان چه دارد. وقتی پنل هدیه را دارد، سرویس داده‌شده حساب می‌شود (و به کاربرش خبر داده
  می‌شود). وگرنه، یا وقتی نمی‌شود از پنل پرسید، ناموفق حساب می‌شود و دوباره امتحان نمی‌شود: ممکن است پنل باز هم آن را
  گرفته باشد، و هیچ سرویسی دو بار هدیه نمی‌گیرد.
- **سرویسی که پنل رد کرد** ناموفق حساب می‌شود.
- **«لغو»** آن را همان‌جا متوقف می‌کند («لغوشده») — آنچه داده شده، داده‌شده می‌ماند.

کارت ده مورد آخر را فهرست می‌کند.

### انتقال سرویس‌ها

«انتقال سرویس‌ها» › «انتقال سرویس‌ها» سرویس‌های این سرور را — مال همه فروشگاه‌ها، سرویس‌های کاربران نماینده‌ها هم —
یک‌جا به سرور دیگری منتقل می‌کند: برای خالی کردن سروری که کنارش می‌گذارید، یا نجات کاربرانتان وقتی پنلش از دست رفته.
هر بار یک سرویس، پس همان انتقال دسته‌ای [انتقال به سرور دیگر](Services.md#انتقال-به-سرور-دیگر) است، بدون نیاز به باز
نگه داشتن تب.

- «سرور مقصد» — هر سرور دیگری که الان می‌تواند بفروشد؛ سروری که نمی‌تواند، دلیلش را نشان می‌دهد (خاموش، پر، بدون لینک
  اشتراک، هرگز بررسی‌نشده).
- «روش»:
  - **«مهاجرت»** — پنل این سرور پاسخ می‌دهد. هر کلاینت آنجا خوانده می‌شود، با آنچه برایش مانده روی مقصد ساخته می‌شود،
    بعد اینجا حذف می‌شود.
  - **«نجات»** — پنل از دست رفته است. هر سرویس از روی آخرین چیزی که فروشگاه از آن خوانده (همگام‌سازی ۱۵ دقیقه‌ای) روی
    مقصد ساخته می‌شود، و هرگز از این پنل چیزی پرسیده نمی‌شود. کلاینت‌های قدیمی‌اش روی آن می‌مانند — اگر پنل برگردد،
    دوباره کار می‌کنند —، پس فروشگاه فهرستی از آن‌ها نگه می‌دارد و وقتی پنل پاسخ بدهد حذفشان می‌کند
    ([پایین‌تر](#کلاینت‌های-جامانده-روی-پنل)). وقتی آخرین تماس سرور ناموفق بوده، پنجره با همین روش شروع می‌شود.
- «سرویس‌های غیرفعال‌شده هم منتقل شوند» — خاموش: سرویس‌هایی که پشتیبانی خاموش کرده اینجا می‌مانند. روشن: آن‌ها هم منتقل
  می‌شوند: هر کدام روی مقصد خاموش ساخته می‌شود، و تا وقتی پشتیبانی روشنش نکند خاموش می‌ماند.
- «پیام به مشتری‌ها» — روشن: لینک تازه برای هر کاربر فرستاده می‌شود.
- «فقط سرویس‌های این پلن‌ها» — وقتی نشان داده می‌شود که سرویس‌های اینجا از بیش از یک پلن باشند؛ اگر هیچ‌کدام تیک نخورد،
  همه منتقل می‌شوند. سرویس بدون پلن (اکانت تست رایگان، سرویسی که با لینکش افزوده شده) فقط وقتی منتقل می‌شود که هیچ‌کدام
  تیک نخورده باشد.

پنجره از روی نسخه فروشگاه می‌شمارد که چند سرویس و از کدام فروشگاه‌ها منتقل می‌شوند، و وقتی «ظرفیت» مقصد برای تعداد
کمتری جا دارد هشدار می‌دهد.

**چه چیزی منتقل می‌شود**: سرویس‌هایی که وقتی «شروع انتقال» را زدید روی این سرور بودند — سرویس‌های فعال، در حال کار یا
در انتظار اولین اتصال، اکانت‌های تست هم —، و وقتی نوبتشان می‌رسد هنوز اینجا هستند. سرویس‌های تمام‌شده می‌مانند (چیزی
برای بردن نمانده؛ [حذف خودکار](Services.md#کارهای-خودکار) فروشگاه آن‌ها را برمی‌دارد). سرویسی که در نوبتش تمام‌شده پیدا
شود — پنلش می‌گوید زمان یا حجمش تمام شده — رد می‌شود («رد شد»). سرویسی که بعد از زدن دکمه اینجا خریده شود می‌ماند: برای
خالی کردن سرور، اول «فعال» را خاموش کنید تا چیز تازه‌ای روی آن فروخته نشود. سرویس‌های کاربران یک نماینده حتی وقتی آن
سرور را از فروشگاه آن نماینده بازداشته‌اید به مقصد می‌روند: آن فهرست، فروش‌ها، اکانت‌های تست و انتقال‌های تکی فروشگاه را
از آن سرور دور نگه می‌دارد، نه این را.

**آنچه هر سرویس نگه می‌دارد، و آنچه تغییر می‌کند**: کاربر، پلن، تاریخ پایان (یا مدتش که هنوز منتظر اولین اتصال است)،
محدودیت دستگاه، تمدیدی که پشت دوره‌اش در صف است، سفارش‌ها و «تمدید خودکار» را نگه می‌دارد. **لینکش تغییر می‌کند** —
کلاینت تازه‌ای روی پنل دیگری است —، و حجمش با سقفی برابر آنچه مانده بود، از صفر شروع می‌شود: ۳۰ گیگابایت با ۱۲
گیگابایت مصرف، ۱۸ گیگابایت بدون مصرف می‌شود. در نجات، آنچه مانده همان چیزی است که فروشگاه آخرین بار خوانده، پس حجمی که
از آخرین همگام‌سازی مصرف شده حساب نمی‌شود.

**آنچه کاربران می‌بینند**: «🔄 سرویس شما به سرور دیگری منتقل شد» با لینک تازه (و کارت QR آن، وقتی ربات کارت می‌فرستد)،
در ربات فروشگاه خودشان — کاربر یک نماینده از ربات آن نماینده —، همان‌طور که یک انتقال تکی می‌گوید
([مرجع متن‌های ربات (انگلیسی)](../Bot-Texts-Reference.md)). بدون «پیام به مشتری‌ها» به هیچ‌کس خبر داده نمی‌شود؛ صفحه
سرویس در هر حال لینک تازه را نشان می‌دهد. گروه گزارش‌های ربات اصلی در تاپیک «خطاها» از شروع و پایان انتقال، با
عددهایش، باخبر می‌شود.

**چطور اجرا می‌شود**: مثل [افزودن زمان و حجم](#افزودن-زمان-و-حجم) — توسط کارت تا وقتی صفحه باز است، وگرنه توسط زمان‌بند
به‌طور پیش‌فرض هر دقیقه. کارت نشان می‌دهد تا کجا پیش رفته: سرویس‌های بررسی‌شده، منتقل‌شده، ردشده و ناموفق، و کلاینت‌هایی که روی یک
پنل جا گذاشته و هنوز آنجا هستند («کلاینت روی پنل مانده است»؛ [پایین‌تر](#کلاینت‌های-جامانده-روی-پنل)).

- **پنلی که در دسترس نیست** — پنل مقصد، یا در مهاجرت پنل همین سرور — انتقال را روی همان سرویس نگه می‌دارد، با یادداشتی
  نارنجی که دلیلش را می‌گوید، و وقتی پنل پاسخ بدهد ادامه پیدا می‌کند. وقتی پنل همین سرور است که پاسخ نمی‌دهد، کارت
  «ادامه با حالت نجات» را پیشنهاد می‌کند: مهاجرت به شکل نجات ادامه پیدا می‌کند. مقصدی که در دسترس نیست نجات را هم نگه
  می‌دارد، پس آن‌وقت این دکمه پیشنهاد نمی‌شود.
- **پنلی که وسط کار یک سرویس از پاسخ دادن بازمی‌ماند**، پیش از اینکه چیزی برگردانده شود دوباره پرسیده می‌شود: کلاینت
  قدیمی‌ای که بی‌آنکه بگوید حذف کرده، سرویس را منتقل‌شده باقی می‌گذارد، و کلاینتی که مقصد بی‌آنکه بگوید ساخته نگه داشته
  می‌شود — کاربر هرگز بی‌سرویس نمی‌ماند، و دو سرویس هم نمی‌گیرد. وقتی از پنل هم نمی‌شود پرسید، کلاینتی که ممکن است
  هنوز داشته باشد همراه [کلاینت‌های جامانده](#کلاینت‌های-جامانده-روی-پنل) فهرست می‌شود و وقتی پاسخ بدهد حذف می‌شود.
- **سرویسی که مقصد رد کرد** ناموفق حساب می‌شود و انتقال ادامه پیدا می‌کند؛ «سرویس‌های ناموفق» هر کدام را با دلیلش
  فهرست می‌کند. وقتی علت برطرف شد، آن‌ها را یکی‌یکی از «اشتراک‌ها» منتقل کنید.
- **مقصدی که دیگر جا ندارد** — پر، خاموش، بدون لینک اشتراک — انتقال را با «ناتمام» و گفتن دلیلش تمام می‌کند؛ بقیه اینجا
  می‌مانند. ظرفیتش را بالا ببرید یا مقصد دیگری انتخاب کنید، و برای آن‌ها انتقال تازه‌ای شروع کنید.
- **سرویسی که تغییر دیگری روی آن در جریان است** (تمدید، کاری از پشتیبانی) کمی بعد دوباره امتحان می‌شود.
- «توقف موقت» و «ادامه» آن را متوقف می‌کنند و ادامه می‌دهند؛ «لغو» آن را تمام می‌کند — آنچه منتقل شده منتقل‌شده
  می‌ماند، بقیه اینجا می‌مانند. سرویسی که هنگام توقف موقت، یا رفتن به «ادامه با حالت نجات»، در جریان است، یا تمام
  می‌شود یا دوباره امتحان می‌شود: هیچ‌کدام رد نمی‌شود.

از هر سرور هر بار یک انتقال انجام می‌شود، و سروری که در حال دریافت یک انتقال است در این مدت نمی‌تواند انتقال خودش را
بفرستد. کارت ده مورد آخر را فهرست می‌کند.

#### کلاینت‌های جامانده روی پنل

کارت می‌گوید انتقال‌ها چند کلاینت روی پنل این سرور جا گذاشته‌اند — کلاینت‌های قدیمی یک نجات، کلاینت‌های سرویس‌هایی که
یکی‌یکی با «انتقال بدون حذف از سرور قبلی» منتقل شده‌اند ([سرویس‌ها](Services.md#انتقال-به-سرور-دیگر))، و هر کلاینتی که
پنلی حذف یا ساختنش را اعلام نکرد، یا حاضر به پس گرفتنش نشد. زمان‌بند وقتی پنل دوباره پاسخ بدهد خودش آن‌ها را حذف
می‌کند — هر بار که [ده دقیقه](#سلامت) کنار گذاشتن پنل تمام شود امتحان می‌شود —، تا کاربر هرگز دو سرویس فعال نداشته
باشد. «حذف همین حالا» همان لحظه امتحان می‌کند، حتی وقتی پنل کنار گذاشته شده است؛ «فراموش کردن» فهرست را کنار می‌گذارد،
برای پنلی که برای همیشه از دست رفته — اگر روزی برگردد، آن کلاینت‌ها کار می‌کنند. کلاینتی با نامی که دوباره سرویسی از هر
فروشگاهی روی این سرور دارد (مثلا دوباره به اینجا منتقل شده) دست نمی‌خورد، و کلاینتی که سرویسش در همان لحظه در حال
تغییر است منتظر امتحان بعدی می‌ماند.

### حذف سرور

«حذف سرور» تا وقتی **هر** سرویسی از هر فروشگاهی روی آن باشد، در هر وضعیتی — تمام‌شده، خاموش، حذف‌شده از پنل —، رد
می‌شود: اول آن‌ها را منتقل کنید یا از «اشتراک‌ها» حذفشان کنید ([سرویس‌ها](Services.md)) — سرویس‌های کاربران یک نماینده
را از فروشگاه همان نماینده —، یا به جای آن سرور را خاموش کنید (یا [همه را منتقل کنید](#انتقال-سرویس‌ها)). تا وقتی
انتقال سرویس‌ها از آن یا به آن در جریان یا متوقف باشد هم رد می‌شود («سرویس‌های این سرور در حال انتقال به سرور «…» است؛ …»):
بگذارید تمام شود، یا لغوش کنید. حذف، اینباندهایش، جایش در همه پلن‌ها، سابقه هدیه‌هایش و سابقه انتقال‌هایش را پاک
می‌کند — همراه فهرست کلاینت‌های جامانده روی پنلش؛ کلاینت‌هایی که انتقال‌هایش روی پنل سرور دیگری جا گذاشته‌اند همان‌جا
فهرست می‌مانند —؛ سفارش‌ها سابقه‌شان را نگه می‌دارند. به خود پنل دست زده نمی‌شود.

## سلامت

«آخرین بررسی» با هر بررسی جلو می‌رود، و با هر به‌روزرسانی اینباندها و هر همگام‌سازی ۱۵ دقیقه‌ای سرویس‌ها که موفق بوده
است. هر چیز دیگری که با پنل حرف می‌زند — فروش، تمدید، هدیه، صفحه سرویس کاربر — فقط وقتی وضعیت سرور را تغییر می‌دهد که
پنل از پاسخ دادن بازبماند (در دسترس نباشد، اطلاعات ورود را رد کند، یا API نباشد) و وقتی دوباره پاسخ بدهد.

پنلی که آخرین تماسش ناموفق بوده **۱۰ دقیقه** کنار گذاشته می‌شود: همگام‌سازی، هدیه‌ها، دوره‌های تمدید و تمدیدهای خودکار
منتظرش می‌مانند (در این مدت پولی کم نمی‌شود)، و صفحه سرویس خود کاربر آخرین عددها را نشان می‌دهد — ربات می‌گوید ممکن
است قدیمی باشند؛ به‌روزرسانی وب‌سایت می‌گوید پنل پاسخ نداد. بعد دوباره امتحان می‌شود. دکمه‌های خود شما، فروش‌ها و
تحویل‌ها منتظر نمی‌مانند.

داشبورد فروشگاه اصلی سرورهای روشنی را که آخرین تماسشان ناموفق بوده می‌شمارد («سرورهای دارای خطا»؛ سروری که خاموشش
کرده‌اید شمرده نمی‌شود)، و گروه گزارش‌های ربات
اصلی در تاپیک «خطاها» از آن باخبر می‌شود: «🔴 پنل سرور «…» جواب نمی‌دهد»، همراه دلیل، وقتی پنلی که پاسخ می‌داد از پاسخ دادن
بازبماند، و «🟢 پنل سرور «…» دوباره جواب می‌دهد» وقتی دوباره پاسخ بدهد ([گروه گزارش‌ها](Telegram-Group.md)).

## کانکتورها

**پنل 3X-UI** (v3 به بعد، نسخه MHSanaei):

- **سرویس اشتراک باید** در تنظیمات پنل **روشن باشد**: فروشگاه هر لینک را همان‌طور می‌سازد که پنل می‌سازد (دامنه، پورت و
  مسیر sub آن — مسیری که فقط `/` است هم)، یا از روی «آدرس اشتراک».
- مدت سرویس از اولین اتصال شروع می‌شود؛ تعداد دستگاه‌های پلن همان IP Limit آن است؛ کامنت، شناسه تلگرام کاربر را دارد.
- «تغییر لینک» به کلاینت اطلاعات ورود تازه و Sub ID تازه می‌دهد.
- با «نام کاربری و رمز»، وقتی Session پنل منقضی شده باشد، فروشگاه خودش دوباره وارد می‌شود — چه در حال خواندن چیزی بوده
  باشد چه در حال تغییر آن.

**پنل PasarGuard** (3.1 به بعد):

- **گروه‌هایش همان اینباندها هستند**: پلن گروه‌ها را می‌فروشد، و گروهی که روی پنل غیرفعال است فروخته نمی‌شود.
- هر پاسخ لینکی تازه امضاشده دارد، پس لینک نگه‌داشته‌شده سرویس با هر همگام‌سازی تغییر می‌کند — همه‌شان کار می‌کنند.
- محدودیت IP ندارد: **تعداد دستگاه‌های پلن** اینجا **اعمال نمی‌شود**.
- وضعیتش CPU، RAM، دیسک و آپتایم هاست پنل را نشان می‌دهد؛ هسته‌ها روی Nodeهایش اجرا می‌شوند، پس وضعیتشان «نامشخص»
  خوانده می‌شود.
- «تغییر لینک» لینک را باطل می‌کند: همه لینک‌های قبلی از کار می‌افتند.
- **کلید یا ادمینی بدهید که همه کاربرها را می‌بیند.** ادمینی که فقط به کاربرهای خودش محدود است — پیش از 5.0 ادمینی که sudo
  نیست؛ از 5.0 ادمینی که نقشش فقط کاربرهای خودش را می‌خواند، مثل نقش *operator* خود پنل — فقط کاربرهایی را می‌بیند که خودش
  ساخته: کاربر ادمینی دیگر رد می‌شود (پیش از 5.0، با راهنمای وصل شدن با ادمین sudo) یا پیدا نمی‌شود (5.0 به بعد)، سرویسی که
  روی پنل به ادمین دیگری داده شود در همگام‌سازی بعدی حذف‌شده حساب می‌شود، و [انتقال](Importing.md) از ربات دیگر هیچ سرویسی از
  ادمین‌های دیگر پیدا نمی‌کند. نامی که کاربر ادمینی دیگر دارد هم گرفته‌شده حساب می‌شود: فروش سراغ نام بعدی می‌رود — وقتی هم که
  PasarGuard 5 نامی را گرفته‌شده می‌داند ولی کاربرش را نشان نمی‌دهد. توضیحات کارتش همین را می‌گوید.
- **قاعده‌های نقش‌ها نام برده می‌شوند**: ردی که برای دسترسی‌ای باشد که نقش ادمین ندارد می‌گوید چه لازم است — دسترسی‌های کاربران
  (ایجاد، مشاهده، ویرایش، حذف، بازنشانی مصرف و لغو اشتراک)، مشاهده گروه‌ها و سیستم، همان‌طور که نقش *administrator* دارد —،
  و ردهای این‌ها هم همین‌طور: ادمینی که حجمش تمام شده، نقشی که کاربر را فقط از روی قالب می‌سازد (*Require template*)، حدهای
  یک نقش برای حجم، مدت یا تعداد کاربرها، نقشی که برای هر کاربر زمان انتظار (on-hold timeout) یا محدودیت HWID می‌خواهد
  (فروشگاه هیچ‌کدام را نمی‌فرستد)، و گروهی که پنل یا نقش آن را ندارد. چنین ردی فروش را همان لحظه ناموفق می‌کند — دسترسی‌ای
  که ادمین ندارد نام گرفته‌شده نیست. ادمینی که حجمش تمام شده و نقشش همه دسترسی‌اش را می‌بندد («Admin is limited — all access
  blocked») کل سرور را تا وقتی حجم بگیرد از کار می‌اندازد: روی سرور ثبت می‌شود، به‌عنوان پنلی که جواب نمی‌دهد گزارش می‌شود، و مثل
  پنلی که در دسترس نیست مدتی کنار گذاشته می‌شود ([سلامت](#سلامت))؛ ادمینی که نقشش فقط نوشتن‌هایش را می‌بندد، درخواست به
  درخواست رد می‌شود.
- **ادمینی که نقشش فقط فهرست ساده گروه‌ها را می‌خواند** — نقش *operator* خود پنل از 5.0 — گروه‌ها را فقط با شناسه و نام
  می‌گیرد: خاموش بودن یک گروه روی پنل آنجا دیده نمی‌شود و روشن نشان داده می‌شود. گروهی را که روی پنل خاموش می‌کنید از پلن‌های
  این سرور هم بردارید، وگرنه سرویس روی آن بدون کانفیگ ساخته می‌شود. توضیحات کارتش همین را می‌گوید.
- **کلید API** (5.1 به بعد) جای ادمین خودش کار می‌کند. کلیدی که رد شود — ناشناخته، منقضی، لغوشده، رسیده به سقف *Max Requests*
  خود، یا مال ادمینی که غیرفعال شده — همین را می‌گوید، همراه کاری که باید کرد: کلیدی بدون تاریخ انقضا و سقف درخواست بدهید.
  کلیدی که دسترسی کار را ندارد می‌گوید آن را با *Inherit admin permissions* بسازید، یا با دسترسی‌های بالا (فهرست ساده گروه‌ها
  کافی است). اگر به‌جایش با نام کاربری و رمز وصل شوید، پنل هر ورود فروشگاه را به ادمین‌های تلگرام یا دیسکوردش گزارش می‌دهد
  (وقتی اعلان ورود ادمین آن روشن باشد)، و ورود ناموفق را همراه رمزی که فرستاده شده؛ درخواست‌های کلید گزارش نمی‌شوند.
- **پاک‌سازی خود پنل برای کاربرهای تمام‌شده** — در 5.6 *Cleanup → Automatic retention → Expired accounts* در تنظیماتش، و پیش از
  آن `USERS_AUTODELETE_DAYS` — سرویس‌های تمام‌شده فروشگاه را پیش از مهلت تمدید فروشگاه و حذف خودکار خودش پاک می‌کرد.
  کاربرهایی که فروشگاه می‌سازد از آن معاف‌اند. آن‌هایی که AmoBot قبلی ساخته را نمی‌شود این‌طور عوض کرد — PasarGuard روزهای
  خود کاربر را فقط هنگام ساختنش می‌گذارد —: روی پنلی که این پاک‌سازی روشن است، برای نگه داشتن آن‌ها، قاعده‌اش را برای
  اکانت‌های منقضی خاموش کنید (*Keep forever*)، یا پیش از 5.6 `USERS_AUTODELETE_DAYS` را بردارید یا منفی کنید.
- **حجم یک بار در هر دوره است**: هر ویرایش ریست حجم کاربر را روی «بدون ریست» می‌گذارد، پس کاربری که از پنل پذیرفته شده و ریست
  خودش را داشت (هر روز، هفته یا ماه)، دیگر هر دوره حجمش را از نو نمی‌گیرد.
- **مدتی که از اولین اتصال شمرده می‌شود** از راه API آن از سرویس پاک نمی‌شود، و PasarGuard 5.1 به بعد هر سرویس خاموشی را که هنوز
  چنین مدتی دارد با روشن شدن on hold می‌کند. وقتی فروشگاه سرویسی را که می‌داند منتظر نیست — پایان ثابت دارد، یا پایانی
  ندارد — روشن یا ویرایش می‌کند، آن را دوباره فعال می‌کند، تا هرگز مدت قدیمی‌اش را در اتصال بعدی روی پایانش شروع نکند؛ سرویس
  خاموش بی‌پایانی که هنوز مدتی دارد منتظر خوانده می‌شود، همان‌طور که پنل می‌خواند.
- پیش از 5.1، ریست حجم خود پنل سرویس منتظر اولین اتصال را فعال می‌کند؛ ویرایشی که فروشگاه درست بعد از ریست می‌فرستد مدت
  منتظرش را برمی‌گرداند. next plan تنظیم‌شده روی پنل از PasarGuard 5.5 با ویرایش می‌ماند؛ نسخه‌های قبلی آن را برمی‌دارند.
- کامنت، که شناسه تلگرام کاربر را دارد، یادداشت کاربر است، کوتاه‌شده تا ۵۰۰ کاراکتر PasarGuard. لینکی که کاربر ادعا می‌کند، با
  پرسیدن از مسیر اشتراک خود پنل بررسی می‌شود که مال کیست — مسیری با چند پوشه هم ([افزودن سرویس با لینک](Service-Claims.md)).

**پنل HMPanel** («HMPanel (HMray)» در «افزودن سرور»، 2.5 به بعد) — پنلی که چند پنل 3X-UI را زیر دست خود اداره می‌کند:

- **کلیدش تنها راه ورود است**: در «تنظیمات ← API» آن ساخته می‌شود (یا <code dir="ltr">/api-keys</code>)، فقط یک بار
  نشان داده می‌شود، با دسترسی `*` — یا `clients.read`، `clients.write`، `clients.renew` و `inbounds.read`. کلید جای
  همان ادمین HMPanel کار می‌کند که برایش ساخته شده: کلید یک نماینده فقط به کلاینت‌های همان نماینده می‌رسد، و ادمینی که
  غیرفعال یا منقضی شود کلیدهایش را هم از کار می‌اندازد. «تست اتصال» کلید را می‌خواند و دسترسی کم را نام می‌برد.
- **فقط اینباندهای پنل‌های 3X-UI آن عرضه می‌شوند**، هر کدام با نام پنلش؛ پنل PasarGuard یا Eylan زیرمجموعه‌اش راه
  دیگری در خود HMPanel دارد. هر کلاینت روی **یک** پنل است: پلنی روی این سرور — یا اینباندهای «فروش»، برای پلنی که روی
  کل سرور فروخته می‌شود — باید فقط اینباندهای یک پنل را داشته باشد، وگرنه فروش‌هایش رد می‌شوند. برای فروش دو پنل آن
  به‌عنوان دو لوکیشن، HMPanel را دو بار اضافه کنید و هر سرور اینباندهای یک پنل را بفروشد.
- مدت سرویس از اولین اتصال شروع می‌شود و تعداد دستگاه‌های پلن IP Limit آن است — همان 3X-UI، که HMPanel منتقل
  می‌کند —؛ کامنت، شناسه تلگرام کاربر را دارد. اعداد، رونوشت HMPanel از اعداد 3X-UI هستند، به همان تازگی همگام‌سازی خودش.
- لینک، لینک خود HMPanel است (<code dir="ltr">https://panel.example.com/s/…</code>)، یا «آدرس اشتراک» پیش از توکن کلاینت
  (`https://sub.example.com/s`).
- «تغییر لینک» ندارد (API کلیدش اطلاعات ورود تازه نمی‌دهد)، و کارت وضعیت CPU، RAM و دیسک هم ندارد: API کلیدش چنین چیزی
  گزارش نمی‌کند.
- **هر کلید در دقیقه 60 درخواست جواب می‌گیرد**، مگر با سقف بالاتری ساخته شده باشد؛ بیشتر از آن، HMPanel تا پایان آن دقیقه
  همه درخواست‌ها را رد می‌کند و فروشگاه چند دقیقه سراغ سرور نمی‌رود («خطا در اتصال»، همراه کاری که باید کرد). فروشگاه
  درخواست‌هایش را کم نگه می‌دارد — همگام‌سازی هر بار 200 کلاینت را می‌خواند —، اما فروشگاه پرکار کلیدی با سقف بالاتر
  می‌خواهد.
- **خطای خود HMPanel** (پاسخ 500 یا بالاتر) به یک تغییر، پاسخ روشنی حساب نمی‌شود: HMPanel ممکن است پیش از خطا تغییر را
  انجام داده باشد، پس فروشگاه پیش از انجام دوباره از پنل می‌پرسد؛ هیچ سرویسی دو بار، با نامی دیگر، ساخته نمی‌شود.

**پنل Marzban** (0.8 به بعد، از Gozargah):

- **نام کاربری و رمز یک ادمین، تنها راه ورود**: API آن کلید ندارد. فروشگاه آن‌ها را با یک توکن عوض می‌کند — به‌طور
  پیش‌فرض یک‌روزه — و آن را میان درخواست‌ها نگه می‌دارد، رمزنگاری‌شده، برای همین سرور، آدرسش، راه رسیدن به آن و همان
  ورود، تا کمی پیش از پایانش (۱۰ دقیقه، یا یک‌دهم عمرش وقتی کوتاه‌تر باشد): فقط آن وقت دوباره وارد می‌شود، یا وقتی پنل توکن
  را رد کند (مثلا رمز عوض شده باشد). پنل Marzban هر ورود را به ادمین‌های تلگرامش خبر می‌دهد: برای اینکه از ورودهای فروشگاه
  خبری نگیرید، IP هاست فروشگاه را در `LOGIN_NOTIFY_WHITE_LIST` تنظیمات Marzban بگذارید، همان‌طور که توضیح کارتش می‌گوید.
  ورود ناموفق در هر حال گزارش می‌شود، همراه رمزی که فرستاده شده؛ <code dir="ltr">NOTIFY_LOGIN=false</code> همه گزارش‌ها را
  خاموش می‌کند.
- **ادمین sudo بدهید**، ادمینی که در دیتابیس پنل ساخته شده، نه `SUDO_USERNAME` فایل <code dir="ltr">.env</code> آن: کاربرهایی که آن یکی می‌سازد مال
  هیچ ادمینی نیستند، که Marzban 0.8.2 تا 0.8.4 حذفشان را درست انجام نمی‌دهد (پایین‌تر). ادمین دیگر فقط کاربرهایی را می‌بیند که
  خودش ساخته: سرورش هرگز یک‌جا خوانده نمی‌شود — همگام‌سازی، و [انتقال](Importing.md)، سرویس‌هایش را یکی‌یکی می‌پرسند —، و
  کاربر ادمینی دیگر رد می‌شود، با راهنمای وصل شدن با ادمین sudo. نامی که کاربر ادمینی دیگر دارد هم گرفته‌شده حساب می‌شود:
  فروش سراغ نام بعدی می‌رود.
- **اینباندهایش** همان اینباندهای تنظیمات Xray پنل‌اند («Core Settings» در داشبوردش)، هر کدام با تگش، همراه پروتکل، پورت،
  transport و security آن؛ هیچ‌کدام روی پنل خاموش نیست. سرویس روی اینباندهای پلنش ساخته می‌شود، با یک proxy از هر پروتکلی
  که آن اینباندها دارند (شناسه و رمزشان را پنل می‌سازد). Marzban اینباندهای کاربر را به شکل اینباندهایی از پروتکل‌هایش نگه
  می‌دارد که کاربر از آن‌ها کنار گذاشته شده: اینباندی که بعدا به پنل اضافه شود، از پروتکلی که سرویس دارد، به همان سرویس هم
  می‌رسد. اینباندی که پنل دیگر ندارد، پیش از فرستادن هر چیزی رد می‌شود، با این توضیح که اینباندها را دوباره بخوانید؛ اینباندی
  که پنل رد کند — اینباندی که دیگر نیست، پروتکلی که رویش خاموش است — می‌گوید «Core Settings» را ببینید.
- مدت سرویس از اولین اتصال شروع می‌شود (on hold در Marzban) یا در روز خودش تمام می‌شود؛ سرویسی که باید خاموش ساخته شود،
  ساخته و بعد خاموش می‌شود — و اگر پنل خاموش کردن را نپذیرد، پس گرفته می‌شود. کامنت، که شناسه تلگرام کاربر را دارد،
  یادداشت کاربر Marzban است (حداکثر ۵۰۰ کاراکتر). هر تغییر اول کاربر را می‌خواند و next plan تنظیم‌شده روی پنل را نگه
  می‌دارد. سرویسی که دوباره روشن می‌شود همان لحظه از طرف پنل سنجیده می‌شود — اگر حجم یا زمانش تمام شده، limited یا expired —،
  و هرگز اول چند ثانیه دسترسی نمی‌گیرد.
- **مدتی که عوض شود، انتظاری پشت سرش نمی‌گذارد**: API آن نمی‌تواند مدت on hold سرویس را پاک کند (۰ یعنی «بدون تغییر»)، و پنل
  سرویس خاموش بی‌پایانی را که هنوز چنین مدتی دارد منتظر می‌خواند. پس ویرایشی که مدت منتظری را عوض می‌کند، آن مدت را با مقداری
  می‌پوشاند که Marzban آن را هیچ می‌خواند — سرویسی که منتظر بوده، بعدا زمان نامحدود گرفته، و بعد خاموش و روشن شده، دیگر با مدت
  قدیمی‌اش on hold برنمی‌گردد.
- **حجم یک بار در هر دوره است**: هر ویرایش ریست حجم کاربر را روی «بدون ریست» می‌گذارد، پس کاربری که از پنل پذیرفته شده و
  ریست خودش را داشت (هر روز، هفته یا ماه)، دیگر هر دوره حجمش را از نو نمی‌گیرد.
- **پاک‌سازی خود پنل برای کاربرهای تمام‌شده** (`USERS_AUTODELETE_DAYS`) سرویس‌های تمام‌شده فروشگاه را پیش از مهلت تمدید فروشگاه
  و حذف خودکار خودش پاک می‌کرد. کاربرهایی که فروشگاه می‌سازد از آن معاف‌اند. آن‌هایی که AmoBot قبلی ساخته را نمی‌شود این‌طور
  عوض کرد — API پنل Marzban این را فقط هنگام ساختن کاربر می‌گذارد —: روی پنلی که `USERS_AUTODELETE_DAYS` دارد، برای نگه داشتن
  آن‌ها، آن را بردارید یا منفی کنید.
- **حذف سرویسی که کاربرش مال هیچ ادمینی نیست** — ساخته‌شده با `SUDO_USERNAME` فایل <code dir="ltr">.env</code>، یا ادمینش حذف شده — روی Marzban
  0.8.2 تا 0.8.4: پنل آن را از دیتابیسش حذف می‌کند، بعد پیش از برداشتنش از Xray ناموفق می‌شود (خطای 500، issue شماره 1634
  آن)، و کانفیگ کاربر تا راه‌اندازی دوباره هسته کار می‌کرد. فروشگاه چنین کاربری را اول خاموش می‌کند، که آن را از Xray برمی‌دارد،
  و خطایی که بعدش کاربر دیگر نباشد را حذف انجام‌شده حساب می‌کند — بازپرداخت، انتقال یا حذف انجام می‌شود.
- ریست حجم سرویس خاموش را خاموش و سرویس منتظر اولین اتصال را on hold نگه می‌دارد — ریست خود Marzban هر دو را روشن می‌کرد: در
  0.8.x وضعیت را اشتباه می‌خواند و کاربر خاموش را فعال می‌کند (در شاخه توسعه منتشرنشده آن درست شده)، و در همه نسخه‌ها کاربر on
  hold را فعال و بی‌پایان می‌کند.
- **محدودیت IP ندارد**: تعداد دستگاه‌های پلن اعمال نمی‌شود، و «کاربر اضافه» روی آن فروخته نمی‌شود.
- نام کلاینت ۳ تا ۳۲ حرف انگلیسی، رقم و `_` است ([تنظیمات ربات](Bot-Settings.md#نام-کاربری-سرویس)).
- «تغییر لینک» لینک را باطل می‌کند (revoke_sub در Marzban): اطلاعات proxy تازه، و همه لینک‌های قبلی از کار می‌افتند.
- لینک، لینک اشتراک کاربر است — روی آدرس خود پنل، وقتی Marzban فقط مسیرش را می‌دهد —، یا «آدرس اشتراک» پیش از توکن آن. هر
  پاسخ لینکی تازه امضاشده دارد، پس لینک نگه‌داشته‌شده سرویس با هر همگام‌سازی تغییر می‌کند — همه‌شان تا باطل شدن لینک کار
  می‌کنند. لینکی که کاربر ادعا می‌کند، با پرسیدن از مسیر اشتراک خود پنل بررسی می‌شود که مال کیست — مسیری با چند پوشه هم
  ([افزودن سرویس با لینک](Service-Claims.md)).
- وضعیتش CPU و RAM هاست پنل و وضعیت و نسخه Xray را نشان می‌دهد — دیسک و آپتایم نه. کاربری آنلاین حساب می‌شود که Marzban
  در یک دقیقه گذشته دیده باشد.
- همگام‌سازی کاربرهای یک ادمین sudo را ۵۰۰ تا ۵۰۰ تا می‌خواند؛ پنلی با بیش از ۵۰٬۰۰۰ کاربر، به‌جایش سرویس به سرویس پرسیده
  می‌شود.

  اشتراک خود پنل نشان داده می‌شود، مسیری با چند پوشه هم —، یا یک کانفیگ **VLESS یا VMess**، که شناسه‌اش همان کلید کاربر است.
  کانفیگ Trojan یا Shadowsocks مال هیچ‌کس پیدا نمی‌شود: رمزش هشی از کلید است که هیچ چیزی روی پنل آن را جست‌وجو نمی‌کند —
  چنین کاربری لینک اشتراک را بفرستد. (کاربری که پیش از آنکه Rebecca، در نسخه‌های اولش، شناسه کانفیگ‌ها را عوض کند ساخته شده،
  شاید فقط با لینک اشتراکش پیدا شود.)
- **مصرف پنهان**: ادمینی که حالت ترافیکش «حجم ساخته‌شده» است و «نمایش ترافیک کاربران» برایش خاموش است، مصرف همه کاربرها را
  صفر می‌بیند — فروشگاه هم، که آن‌وقت هرگز سرویسی را با تمام شدن حجمش تمام نمی‌کند. کلید ادمینی را بدهید که مصرف کاربرهایش
  را می‌بیند.
- وضعیتش CPU، RAM، دیسک و آپتایم هاست پنل، و وضعیت، نسخه و آخرین خطای Xray را نشان می‌دهد. کاربری آنلاین حساب می‌شود که
  Rebecca در ۲۰ ثانیه گذشته دیده باشد.
- همگام‌سازی کاربرهای یک ادمین full access یا sudo را ۵۰۰ تا ۵۰۰ تا می‌خواند؛ پنلی با بیش از ۵۰٬۰۰۰ کاربر، به‌جایش سرویس به
  سرویس پرسیده می‌شود.

**پنل Remnawave** (2.1 به بعد، نسخه‌های 3 هم — پنلی با نودهای Xray، که کاربرهایش با اسکوادها به آن‌ها می‌رسند):

- **توکن API آن تنها راه ورود است**: ساخته‌شده در *Remnawave Settings → API Tokens* آن، کل توکن — <code dir="ltr">eyJ…</code>،
  سه بخش که با نقطه از هم جدا شده‌اند —، که پنل فقط یک بار نشان می‌دهد، با دسترسی‌های <code dir="ltr">users:*</code>،
  <code dir="ltr">internal-squads:read</code> و <code dir="ltr">system:read</code> (دسترسی `*` هم کار می‌کند، ولی همه پنل را باز
  می‌کند). پنل Remnawave برای درخواست‌های API نه رمز
  ادمین را می‌پذیرد و نه توکن ورود خود ادمین را: اگر چنین توکنی جای آن داده شود، رد می‌شود و می‌گوید یک توکن API بسازید. هر
  توکن مدت اعتبار دارد: پیش از پایانش توکن تازه‌ای بسازید و اینجا بگذارید. توکنی که رد شود می‌گوید اشتباه است، مال پنل دیگری
  است یا تاریخش گذشته؛ توکنی که دسترسی لازم یک کار را ندارد، یا روی پنل حذف شده، می‌گوید چه دسترسی‌هایی بدهید.
- **فقط از راه ریورس‌پراکسی HTTPS**: پنل Remnawave هر درخواستی را که از چنین پراکسی‌ای نگذشته باشد بی‌جواب رها می‌کند.
  آدرس https دامنه پنل را بدهید، همان که داشبوردش با آن باز می‌شود. پورت خود پنل با http ساده فقط وقتی کار می‌کند که پنل روی هاست
  خود فروشگاه یا شبکه خصوصی آن باشد — `localhost`، یک IP لوپ‌بک، خصوصی یا از نوع Tailscale (`100.64.0.0/10`)، نام هاستی
  تک‌کلمه‌ای مثل نام یک سرویس Docker، یا نامی که به <code dir="ltr">.lan</code>، <code dir="ltr">.local</code>، <code dir="ltr">.internal</code> یا <code dir="ltr">.home.arpa</code> ختم می‌شود —:
  آن‌وقت فروشگاه آنچه را چنین پراکسی‌ای اضافه می‌کرد خودش می‌فرستد. از راه اینترنت چیزی اضافه نمی‌کند، پس Remnawave درخواست را
  بی‌جواب می‌گذارد: توکن و اطلاعات مشتری‌ها بی‌رمز فرستاده می‌شد. اتصالی که بی‌جواب قطع شود — یا دست‌دادن TLS ناموفق روی
  آدرس https که پورتی جز 443 دارد، یعنی پورت ساده خود پنل (گواهی ردشده مال خود گواهی است) — این‌طور گفته می‌شود که هیچ چیزی پاسخ نداد، همراه همین قاعده و آدرسی که باید داد؛ پراکسی جلوی پنل که از آن جوابی نگرفته می‌گوید پنل خاموش است، یا پراکسی `X-Forwarded-For` و
  `X-Forwarded-Proto` را نمی‌فرستد.
- **پنل پشت دروازه ورود** — Caddy یا TinyAuth، همان‌طور که راهنماهای امنیتی خود Remnawave راه می‌اندازند — درخواست‌های فروشگاه را
  فقط با کلید همان دروازه راه می‌دهد: آن را در «کلید دروازه» زیر «تنظیمات پیشرفته» بدهید (کلید API دروازه، یا در TinyAuth کل
  مقدار <code dir="ltr">Basic …</code>)؛ فروشگاه آن را با هر درخواست می‌فرستد. «آدرس پنل» همان آدرس خود پنل می‌ماند، بدون مسیر
  مخفی صفحه ورود دروازه. دروازه‌ای که فروشگاه را برگرداند — صفحه خودش، یا یک ریدایرکت، به‌جای API — می‌گوید کلید دروازه را بدهید.
- **اسکوادهای داخلی‌اش همان اینباندها هستند**: «اینباندها» آن‌ها را با نامشان فهرست می‌کند، هر کدام با تگ اینباندهایش و
  اعضایش. اسکوادی که اینباند ندارد چیزی به کاربر نمی‌دهد: خاموش نشان داده می‌شود و فروخته نمی‌شود. هر کاربر می‌تواند در چند
  اسکواد باشد، پس پلنی روی این سرور می‌تواند چند تا را با هم بفروشد. ویرایش اسکوادهای کاربر را همان‌طور که هستند می‌گذارد.
- **زمان از اولین اتصال ندارد**: پنل Remnawave چنین چیزی ندارد، پس زمان سرویس از لحظه فروش شروع می‌شود — مدتی که از اولین
  اتصال شمرده می‌شود، مال یک پلن یا یک اکانت تست، همان لحظه ساخت سرویس شروع می‌شود، و فروشگاه پایانی را نگه می‌دارد که آن‌وقت
  روی پنل است.
- سرویس در یک قدم روشن یا خاموش ساخته می‌شود. سرویس خاموش، زمان و حجمش هر چه باشد، خاموش می‌ماند. سرویسی که تمدید شود، یا در
  حالت روشن ویرایش شود، وقتی دوباره کار می‌کند که دوره تازه‌اش زمان و حجم داشته باشد؛ وگرنه پنل آن را تمام‌شده نگه می‌دارد.
  سرویسی که دوباره روشن شود تا بررسی بعدی پنل کار می‌کند — هر ۳۰ ثانیه برای زمان، هر ۴۵ ثانیه برای حجم — که اگر زمان یا حجمش
  تمام شده باشد دوباره تمامش می‌کند. مدتی که کوتاه شود تا همین حالا تمام شود، حدود یک دقیقه بعد تمام می‌شود: پنل Remnawave پایانی
  را که در آینده نباشد نمی‌پذیرد. تمدیدی که پاسخش هرگز نرسید (تایم‌اوت) از پنل پرسیده می‌شود، که مدت از اولین اتصال را به شکل
  مهلتی که شروع کرده نشان می‌دهد — یا مهلت گذشته را به شکل زودترین زمانی که می‌پذیرد —: فروشگاه آن را همان‌جا می‌شناسد، و یک بار
  تحویلش می‌دهد، نه دو بار.
- **حجم یک بار در هر دوره است**: کاربر بدون ریست حجم ساخته و ویرایش می‌شود.
- کامنت، که شناسه تلگرام کاربر را دارد، توضیح (description) کاربر است، و شناسه تلگرام در فیلد خود Remnawave برای آن هم
  می‌رود (Remnawave از راه آن چیزی به کاربر نمی‌فرستد)؛ سرویسی که به کاربر دیگری داده شود شناسه صاحب قبلی را آنجا پاک
  می‌کند.
- **تعداد دستگاه‌های پلن همان محدودیت دستگاه HWID آن است** (صفر یعنی بدون محدودیت)، و «کاربر اضافه» روی آن فروخته می‌شود.
  Remnawave آن را فقط وقتی اعمال می‌کند که «HWID Device Limit» در تنظیمات اشتراکش روشن باشد (به‌طور پیش‌فرض خاموش است)، و فقط
  برنامه‌هایی را می‌شمارد که هنگام گرفتن لینک شناسه دستگاه می‌فرستند (Happ، v2RayTun و چند برنامه دیگر)؛ وقتی روشن است، برنامه‌ای
  که شناسه نمی‌فرستد اشتراک را نمی‌گیرد. اگر خاموش باشد، تعداد دستگاه فقط حرف فروشگاه است.
- نام کلاینت ۳ تا ۳۶ حرف انگلیسی، رقم، `_` و `-` است، همان‌طور که نوشته شده سنجیده می‌شود
  ([تنظیمات ربات](Bot-Settings.md#نام-کاربری-سرویس)).
- «تغییر لینک» اشتراک را باطل می‌کند: شناسه کوتاه تازه — پس لینک تازه — و اطلاعات ورود تازه؛ همه لینک‌ها و کانفیگ‌هایی که پیش‌تر
  داده شده از کار می‌افتند. ریست حجم کاربری را که Remnawave به خاطر حجمش محدود کرده بود دوباره روشن می‌کند، و بقیه را همان‌طور
  که هستند می‌گذارد. سرویس حذف‌شده برای همیشه حذف می‌شود: نامش روی پنل دوباره آزاد است.
- لینک، لینک اشتراک کاربر است — دامنه اشتراک Remnawave و شناسه کوتاه کاربر —، یا «آدرس اشتراک» پیش از شناسه کوتاه.
- **لینکی که کاربر ادعا می‌کند** ([افزودن سرویس با لینک](Service-Claims.md)) یک لینک اشتراک است — حداکثر چهار بخش آن به‌عنوان
  شناسه کوتاه از پنل پرسیده می‌شود —، یا یک کانفیگ VLESS، Trojan یا Shadowsocks، که با اطلاعات ورود همه کاربرها تطبیق داده
  می‌شود (شناسه VLESS حتی وقتی مسیر یک هاست گروه سومش را عوض کرده باشد). شناسه کوتاهی که پرسیده می‌شود در لاگ و در هر خطایی
  که بخواهد آن را نقل کند پوشانده می‌شود.
- وضعیتش RAM و آپتایم هاست پنل را نشان می‌دهد: Remnawave بار CPU و دیسک را گزارش نمی‌کند («—»)، و هسته‌های Xray آن روی
  Nodeهایش اجرا می‌شوند، پس وضعیتشان «نامشخص» خوانده می‌شود. کاربری آنلاین حساب می‌شود که Remnawave ترافیکش را در ۳۰ ثانیه
  گذشته دیده باشد.
- همگام‌سازی کاربرها را ۱۰۰۰ تا ۱۰۰۰ تا می‌خواند؛ پنلی با بیش از ۵۰٬۰۰۰ کاربر، به‌جایش سرویس به سرویس پرسیده می‌شود.
- **خطای خود Remnawave** (پاسخ 500 یا بالاتر) به یک تغییر، پاسخ روشنی حساب نمی‌شود: پنل ممکن است پیش از خطا تغییر را انجام داده
  باشد، پس فروشگاه پیش از انجام دوباره از پنل می‌پرسد. پایانی که پنل آن را گذشته بداند و رد کند، می‌گوید بررسی کنید ساعت هاست
  فروشگاه و سرور پنل با هم یکی باشند.

افزودن پنلی دیگر، نوشتن یک درایور است ([درایورها](Drivers.md#کانکتور-پنل-vpn)). برای توسعه‌دهندگان، `panel:probe` یک پنل
را از کنسول امتحان می‌کند، همان‌طور که «تست اتصال» می‌کند ([دستورهای کنسول](Console-Commands.md))؛ فروشگاه هیچ‌وقت به
آن نیازی ندارد.

## مراقب باشید

- **سروری که پنلش از کار افتاده باز هم می‌فروشد**: خریدهایش پرداخت می‌شوند، بعد زیر «سفارش‌ها» › «نیازمند رسیدگی»
  منتظر تلاش دوباره می‌مانند. برای قطعی طولانی، سرور را خاموش کنید («تنظیمات اتصال» › «تنظیمات پیشرفته» › «فعال»).
- **بعد از تغییر پنل، «بررسی اتصال» را بزنید**: خاموش شدن سرویس اشتراک در 3X-UI فقط با بررسی فهمیده می‌شود — تا آن
  موقع فروش‌ها پیشنهاد می‌شوند و ناموفق می‌شوند («… لینک اشتراک نساخت …») —، و اینباندهایی که آنجا اضافه یا حذف شده‌اند
  تا یک بررسی یا «به‌روزرسانی از پنل» ناشناخته می‌مانند.
- **دو دکمه**: «تست اتصال» آنچه را فرم دارد امتحان می‌کند و چیزی نگه نمی‌دارد؛ «بررسی اتصال» سرور ذخیره‌شده را بررسی
  می‌کند و آنچه را فهمیده نگه می‌دارد.
- **فاصله‌های دو سر اطلاعات محرمانه حذف می‌شوند**: رمز پنلی که با فاصله شروع یا تمام شود وارد نمی‌شود.
