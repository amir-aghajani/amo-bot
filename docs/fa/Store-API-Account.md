# رابط Store API: حساب کاربری

حساب خود کاربری که وارد شده: اینکه کیست، چطور وارد می‌شود، همین Session و دستگاه‌هایش — و یکی کردن دو حساب او. مسیرها زیر
[آدرس پایه](Store-API.md#آدرس-پایه) هستند؛ همه با توکن Bearer کاربر
([توکن‌ها و Sessionها](Store-API-Sign-In.md#توکن‌ها-و-sessionها)).

## حساب کاربری

پاسخ `200` به `GET /me`:
```json
{
  "customer": {
    "id": 57,
    "first_name": "سارا",
    "last_name": "احمدی",
    "telegram": { "id": 987654321, "username": null },
    "email": "sara@example.com",
    "google": false,
    "has_password": true,
    "two_factor": true,
    "phone": null,
    "balance": "150000.00",
    "created_at": "2026-10-01T14:05:09+00:00"
  },
  "unread_notifications": 3,
  "staff": null,
  "loyalty": {
    "tier": { "id": 2, "name": "نقره‌ای", "discount_percent": 3, "cashback_percent": 1 },
    "spent": "750000.00",
    "next": { "name": "طلایی", "min_spent": "2000000.00", "missing": "1250000.00" }
  },
  "session": { "method": "password_2fa", "biometric": false, "recent_until": null }
}
```

| فیلد | معنا |
|---|---|
| `id` | شماره کاربر — وقتی حساب در حساب قدیمی‌تری ادغام شود عوض می‌شود ([پیشنهاد ادغام](#پیشنهاد-ادغام)) |
| `first_name`، `last_name` | نام و نام خانوادگی؛ اگر نباشد `null` |
| `telegram` | حساب تلگرامش (`id`، و `username` بدون @ یا `null`)؛ برای کسی که هیچ‌وقت تلگرام را وصل نکرده `null` |
| `email` | ایمیلش، که همیشه تاییدشده است — با کدی که به آن فرستاده و وارد شده، یا با تایید گوگل؛ اگر نباشد `null` |
| `google` | با یک حساب گوگل وارد می‌شود |
| `has_password` | با ایمیل و رمز عبور وارد می‌شود |
| `two_factor` | ورود با رمز عبور یک مرحله دوم می‌خواهد ([ورود دومرحله‌ای](#ورود-دومرحله‌ای)) |
| `phone` | شماره موبایل تاییدشده با قالب E.164 — همان‌طور که در ربات فرستاده، یا با کد پیامکی در وب‌سایت ثابت کرده؛ تا وقتی وب‌سایت ورود با پیامک دارد یک روش ورود است ([روش‌های ورود](#روش‌های-ورود-افزودن-و-حذف))؛ اگر نباشد `null` |
| `balance` | موجودی کیف پول به تومان؛ کمتر از صفر یعنی بدهی نماینده |
| `created_at` | از کی کاربر فروشگاه است |
| `unread_notifications` | عدد زنگوله اعلان‌های سایت ([اعلان‌ها](Store-API-Notifications.md)) |
| `staff` | کارهایی که API مدیران فروشگاه برایش باز می‌کند — مجوزهایش، اینکه این Session با ورود قوی است یا نه، تا کی با API مدیران کار می‌کند و تا کی تازه حساب می‌شود —؛ برای کاربری که مدیر فروشگاه نیست، تا وقتی وب‌سایت هیچ مدیری را راه نمی‌دهد، از طریق مینی‌اپ، که API مدیران ندارد، و برای Sessionی که مینی‌اپ وارد کرده، که API مدیران در وب‌سایت هم ردش می‌کند، `null` ([مدیران سایت](Store-API-Admins.md#ورود)) |
| `loyalty` | سطح وفاداری‌اش — `tier` (نام سطح، تخفیفی که در خریدهایش می‌دهد و کش‌بک اضافه‌ای که اضافه می‌کند) یا `null` پایین‌تر از اولین سطح —، مبلغی که خرج کرده (`spent`: خریدها، تمدیدها و خریدهای اضافه‌ای که پرداخت شده و برنگشته، به تومان)، و سطح بعدی (`next`) با مبلغی که هنوز تا آن مانده (`missing`)، که در بالاترین سطح `null` است؛ فروشگاهی که سطحی ندارد هر دو را `null` دارد ([سطوح وفاداری](Loyalty-Cashback-And-Draws.md#سطوح-وفاداری)) |
| `session` | همین Session: `method`، اینکه چطور وارد شده یا روش قوی‌تری که بعد روی آن ثابت شده (`telegram`، `mini_app`، `google`، `phone`، `password`، `password_2fa` — یا `preview`، نگاه پنل به مینی‌اپ به جای این کاربر: فقط برای خواندن، فقط از کلید مینی‌اپ، برای ۳۰ دقیقه، [پیش‌نمایش پنل](Store-API-Sign-In.md#پیش‌نمایش-پنل))؛ `biometric`، اینکه مینی‌اپ برای آن رمز اثر انگشت نگه می‌دارد یا نه ([اثر انگشت یا چهره](#اثر-انگشت-یا-چهره))؛ و `recent_until`، اینکه تا کی تازه حساب می‌شود — وقتی گذشت `null`: پیش از کاری که ورود تازه می‌خواهد، یک روش ورود را دوباره ثابت کنید ([ورود تازه](#ورود-تازه)) |

پاسخ `PATCH /me` همان پاسخ `GET /me` است. `PUT /me/password`، `POST /me/2fa/disable`، افزودن یا حذف روش ورود (پاسخ‌های
`200` در <code dir="ltr">/me/identities/\*</code>) و `POST /me/merge` فقط <code dir="ltr">{ "customer": … }</code> را
برمی‌گردانند — همان شیء `customer`، بدون عدد اعلان‌ها، `staff`، `loyalty` یا `session`. بقیه همان چیزی را برمی‌گردانند که
می‌سازند: کلید راه‌اندازی، کدهای بازیابی، مدت اعتبار یک کد یا یک تایید، پیشنهاد ادغام.

## ورود تازه

کارهایی که روش‌های ورود به حساب را عوض می‌کنند، و کارهایی که سرویس یا پولی را به کاربر دیگری می‌دهند، چیزی بیشتر از توکن
Session لازم دارند، تا توکنی که لو رفته نتواند حسابی را بگیرد یا چیزی را به کسی بدهد:

| ورود تازه لازم دارد | ببینید |
|---|---|
| `PUT /me/password` | [رمز عبور](#رمز-عبور) |
| `POST /me/2fa/setup`، `POST /me/2fa/enable`، `POST /me/2fa/disable` | [ورود دومرحله‌ای](#ورود-دومرحله‌ای) |
| `POST /me/identities/telegram`، <code dir="ltr">…/google</code>، <code dir="ltr">…/email</code>، <code dir="ltr">…/email/verify</code>، <code dir="ltr">…/phone</code>، <code dir="ltr">…/phone/verify</code>، و <code dir="ltr">DELETE /me/identities/{kind}</code> | [روش‌های ورود](#روش‌های-ورود-افزودن-و-حذف) |
| `POST /me/merge` | [پیشنهاد ادغام](#پیشنهاد-ادغام) |
| `PUT /me/biometric`، که رمزی می‌سازد که یک روش ورود را ثابت می‌کند (فقط در مینی‌اپ) | [اثر انگشت یا چهره](#اثر-انگشت-یا-چهره) |
| `POST /subscriptions/{id}/transfer`، که سرویسی را به دیگری می‌دهد | [انتقال سرویس به کاربر دیگر](Store-API-After-Buying.md#انتقال-سرویس-به-کاربر-دیگر) |
| `POST /wallet/transfer`، که پول را برای دیگری می‌فرستد | [انتقال موجودی به کاربر دیگر](Store-API-After-Buying.md#انتقال-موجودی-به-کاربر-دیگر) |

ورود این Session باید حداکثر ۱۵ دقیقه پیش بوده باشد، یا بعد از آن یک روش ورود به حساب دوباره روی آن ثابت شده باشد.
وگرنه پاسخ `403` با `WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age=900` (RFC 9470) است، که
پیش از انجام هر کاری برمی‌گردد؛ چیزی را هم تمام نمی‌کند — توکن سر جایش است:

پاسخ `403` به `PUT /me/password`:
```json
{ "message": "برای این کار دوباره وارد شوید.", "request_id": "5d1e0c3b9a4f7e21" }
```

درخواست `POST /me/reauthenticate` یکی از روش‌های ورود به همین حساب را دوباره ثابت می‌کند و این تغییرها را برای ۱۵ دقیقه
دیگر باز می‌کند. روش‌هایی را پیشنهاد کنید که حساب دارد:

| `method` | بدنه | کی پیشنهادش کنید |
|---|---|---|
| `password` | <code dir="ltr">{ method, password, code? }</code> — `code` همان کد برنامه یا یک کد بازیابی است، همان‌طور که مرحله دوم می‌گیرد ([رمز عبور و مرحله دوم](Store-API-Sign-In.md#رمز-عبور-و-مرحله-دوم))، و تا وقتی `two_factor` روشن است لازم است؛ کد بازیابی‌ای که اینجا به کار رود، مثل هنگام ورود، مصرف می‌شود | `has_password` |
| `telegram` | `{ method, id_token, nonce }` از پاپ‌آپ ([پاپ‌آپ](Store-API-Sign-In.md#تلگرام-پنجره-پاپ‌آپ))، یا — تا وقتی `sign_in.telegram.redirect` در <code dir="ltr">GET /</code> برابر true است — `{ method, code, state, code_verifier }` از ریدایرکت، با stateی که همین Session از `POST /me/telegram/authorize` گرفته ([ریدایرکت](Store-API-Sign-In.md#تلگرام-ریدایرکت)) | `customer.telegram` برابر `null` نیست و <code dir="ltr">GET /</code> تلگرام را ارائه می‌کند |
| `google` | `{ method, id_token, nonce }` ([گوگل](Store-API-Sign-In.md#گوگل)) | `google` درست است و <code dir="ltr">GET /</code> گوگل را ارائه می‌کند |
| `phone` | `{ method, code }` — کد شش رقمی‌ای که `POST /me/reauthenticate/phone` برای همین Session به موبایل حساب پیامک کرده (پایین‌تر) | `phone` یک شماره موبایل ایران است، `two_factor` خاموش است و <code dir="ltr">GET /</code> فیلد `sign_in.phone` را ارائه می‌کند |
| `mini_app` | `{ method, init_data }` — داده راه‌اندازی‌ای که تلگرام به مینی‌اپ داده ([مینی‌اپ](Store-API-Sign-In.md#مینی‌اپ))، حداکثر ۱۵ دقیقه پیش ساخته شده: Session از `auth_date` آن تازه حساب می‌شود، و هرگز کمتر از آنچه بود تازه نمی‌شود | در مینی‌اپ، تا وقتی داده راه‌اندازی‌اش تازه است — هرگز در وب‌سایت |
| `biometric` | `{ method, token }` — رمز اثر انگشت همین Session، همان‌طور که تلگرام بعد از تطبیق اثر انگشت یا چهره برمی‌گرداند ([اثر انگشت یا چهره](#اثر-انگشت-یا-چهره)) | در مینی‌اپ، تا وقتی `session.biometric` درست است — هرگز در وب‌سایت |

این دو روش آخر فقط مال مینی‌اپ‌اند: با کلید یک وب‌سایت روی `method` رد می‌شوند، هر قدر هم که تایید معتبر باشد.

روش `phone` دو قدم دارد. `POST /me/reauthenticate/phone` (بدون بدنه) کدی به موبایل خود حساب پیامک می‌کند و مثل
`POST /auth/phone` پاسخ `202` با <code dir="ltr">{ "sent": true, "expires_in": 300, "resend_in": 60 }</code> می‌دهد
([کد پیامکی](Store-API-Sign-In.md#کد-پیامکی))؛ بعد `POST /me/reauthenticate` با <code dir="ltr">{ "method": "phone", "code": … }</code>
آن را ثابت می‌کند. کد فقط مال همین Session است — دستگاه دیگر کاربر با آن چیزی ثابت نمی‌کند —، پنج دقیقه اعتبار دارد و پنج
بار امتحان می‌شود. مال وب‌سایت است: زیر کلید مینی‌اپ قدم اول مسیری نیست و `phone` مثل روش خاموش وب‌سایت رد می‌شود. برای
حسابی که شماره موبایل ایران ندارد `422` روی `method` می‌گیرد
(`این حساب شماره موبایلی ندارد که پیامک به آن برسد؛ با روش ورود دیگری تایید کنید.`)، و همین‌طور حسابی که ورود دومرحله‌ای
دارد، که رمز عبور و کدش آن را ثابت می‌کنند (`این حساب ورود دو مرحله‌ای دارد؛ با رمز عبور و کد برنامه احراز هویت تایید کنید.`:
سیم‌کارتی که تعویض شده، یا شماره‌ای که به کس دیگری داده شده، کد پیامکی را می‌خواند)، تا وقتی وب‌سایت ورود با پیامک ندارد
`422` بدون فیلد، و ارسال‌هایش از سهمیه‌های پیامک کم می‌شود — هر کاربر روزی ده کد، افزودن شماره و ثابت کردن دوباره با هم.

درخواست `POST /me/reauthenticate`:
```json
{ "method": "password", "password": "kooh-e damavand 1404", "code": "482913" }
```

پاسخ `200` به `POST /me/reauthenticate`:
```json
{ "expires_in": 900 }
```

خطاها:

- کد `422` زیر یک فیلد:
  - رمز عبور خالی (`رمز عبور حساب را وارد کنید.`) یا اشتباه (`رمز عبور درست نیست.`)، کد اشتباه، یا نبودن کد در حالی که
    ورود دومرحله‌ای روشن است (`کد برنامه احراز هویت یا یکی از کدهای بازیابی را وارد کنید.`)؛
  - حساب بدون رمز عبور، روی `password` (`این حساب با رمز عبور وارد نمی‌شود؛ با روش ورود دیگری تایید کنید.`)؛
  - تایید تلگرام یا گوگلی که معتبر نیست (روی `id_token`، یا `code` ریدایرکت)، یا حساب دیگری را ثابت می‌کند
    (`این ورود مال حساب دیگری است؛ با یکی از روش‌های ورود همین حساب تایید کنید.`)؛
  - داده راه‌اندازی‌ای که معتبر نیست یا بیش از ۱۵ دقیقه از آن گذشته، روی `init_data` (`ورود از مینی‌اپ تایید نشد؛ مینی‌اپ را
    ببندید و دوباره از ربات باز کنید.`)، یا مال حساب تلگرام دیگری است — از جمله برای حسابی که تلگرام ندارد —
    (`این ورود مال حساب دیگری است؛ …`)؛
  - رمز اثر انگشتی که مال این Session نیست، روی `token` (`تایید با اثر انگشت یا چهره درست نبود؛ مینی‌اپ را ببندید و
    دوباره از ربات باز کنید.`): مال Session دیگری است، عوض یا فراموش شده، یا اصلا رمزی نگه داشته نشده؛
  - کد پیامکی‌ای که اشتباه، منقضی، استفاده‌شده یا مال Session دیگری است، روی `code` (`کد درست نیست یا منقضی شده است.`)؛
  - مقدار `method` که هیچ‌کدام از این شش نیست، روی `method`؛ و `mini_app` یا `biometric` با کلید یک وب‌سایت، باز روی
    `method` (`این روش تایید فقط در مینی‌اپ فروشگاه کار می‌کند؛ با روش ورود دیگری تایید کنید.`).
- کد `422` بدون فیلد: روشی که وب‌سایت بعد از خواندن <code dir="ltr">GET /</code> خاموش کرده
  (`ورود با تلگرام برای این وب‌سایت فعال نیست.`، `ورود با Google برای این وب‌سایت فعال نیست.`،
  `ورود با شماره موبایل برای این وب‌سایت فعال نیست.`).
- کد `429`: هر تایید ناموفق یک ورود ناموفق حساب می‌شود — و هر کد، در سهمیه مرحله دوم هم — طبق
  [محدودیت‌ها و مدت اعتبار](Store-API-Sign-In.md#محدودیت‌ها-و-مدت-اعتبار).
- کد `502`: سرویس ورود (تلگرام یا گوگل) در دسترس نیست.

افزودن روش ورود ([روش‌های ورود](#روش‌های-ورود-افزودن-و-حذف)) فقط همان روشی را ثابت می‌کند که اضافه می‌شود: آن ۱۵ دقیقه را
تازه نمی‌کند.

هر Session این را هم به یاد دارد که چطور وارد شده. Sessionی که فقط با رمز عبور یا کد پیامکی وارد شده، وقتی یک روش قوی
اینجا روی آن ثابت شود، Session قوی می‌شود — همان چیزی که API مدیران فروشگاه از مدیرانش می‌خواهد
([مدیران سایت](Store-API-Admins.md#ورود)) —: تلگرام، گوگل، داده راه‌اندازی مینی‌اپ، یا رمز عبور همراه کدش. ثابت کردن
دوباره رمز عبور یا کد پیامکی به‌تنهایی ورود را تازه می‌کند — آن ۱۵ دقیقه، و ۱۲ ساعتی که Session مدیر با API مدیران کار
می‌کند — ولی آن را قوی نمی‌کند؛ رمز اثر انگشت هم همین‌طور، که فقط صاحب همین Session را دوباره ثابت می‌کند و `method` آن را دست
نمی‌زند. `method` قوی تا آخر عمر Session همان می‌ماند، از جمله `mini_app` — و Sessionی که `method` آن `mini_app` است با
API مدیران کار نمی‌کند، چون مینی‌اپ فقط برای مشتری‌هاست.

کار سایت: تغییر را بفرستید؛ اگر آن `403` آمد، از کاربر بخواهید یک روش ورود را ثابت کند، بعد تغییر را دوباره بفرستید —
چون پیش از اجرا رد شده بود، حالا برای اولین بار اجرا می‌شود.

```ts
/** A change of how the account is signed in to: on the 403 that asks a recent sign-in, proven again and sent again. */
export async function withRecentSignIn<T>(change: () => Promise<T>, reprove: () => Promise<void>): Promise<T> {
  try {
    return await change()
  } catch (e) {
    if (!(e instanceof StoreError) || !e.needsRecentSignIn) throw e
    await reprove() // your dialog: the password (and code), or Telegram's or Google's button → POST /me/reauthenticate
    return change()
  }
}

// await withRecentSignIn(() => store('/me/identities/google', { method: 'DELETE' }), askToProve)
```

تغییری که از تلگرام یا گوگل می‌گذرد — افزودن یکی از آن‌ها، یا ریدایرکت — اگر پیش از شروع ثابت شود روان‌تر پیش می‌رود:
`session.recent_until` در پاسخ `GET /me` می‌گوید Session تا کی تازه حساب می‌شود (`expires_in` یک تایید دوباره هم همین را
می‌گوید)؛ وقتی `null` شد، اول تایید را بخواهید، تا کاربر فقط یک بار تایید بدهد، نه اول پنجره سرویس ورود و بعد یک پنجره
دیگر.

**هر تغییری از این دست به کاربر خبر داده می‌شود** — روش ورودی که اضافه یا برداشته شده، رمز عبوری که گذاشته یا عوض شده،
ورود دومرحله‌ای که روشن یا خاموش شده، دو حسابی که ادغام شده‌اند، مرحله دومی که آن‌قدر اشتباه زده شده که تا مدتی بسته
است، کدهایی که به ایمیلش فرستاده شده و آن‌قدر اشتباه زده شده که تا مدتی کدی فرستاده نمی‌شود: با یک اعلان
([انواع اعلان](Store-API-Notifications.md#انواع-اعلان))، و از همه راه‌هایی که حساب دارد — چت تلگرامش *و* ایمیلش، چون کسی
که تغییر را داده ممکن است یکی از این دو را در دست داشته باشد.

## نام‌ها

درخواست `PATCH /me` با <code dir="ltr">{ first_name?, last_name? }</code>: فقط فیلدهایی که فرستاده شوند عوض می‌شوند
(بدنه خالی چیزی را عوض نمی‌کند)، و پاسخ همان پاسخ `GET /me` است. نام ۱ تا ۶۴ کاراکتر است و نام خانوادگی حداکثر ۶۴
(`""` آن را پاک می‌کند). حسابی که تلگرام دارد رد می‌شود (`422` زیر هر فیلدی که فرستاده شده،
`نام حساب‌های تلگرامی از تلگرام خوانده می‌شود.`): نام‌هایش از تلگرام است و ربات هر بار از نو آن‌ها را می‌خواند. تا وقتی
`customer.telegram` برابر `null` نیست، فرم را پنهان کنید.

## رمز عبور

درخواست `PUT /me/password` با `{ current_password?, password }`، با ورود تازه ([ورود تازه](#ورود-تازه)). حساب باید ایمیل
داشته باشد (وگرنه `422` با `اول یک ایمیل به حساب اضافه کنید.`)؛ تا وقتی حساب رمز عبور دارد (`has_password`)، فیلد
`current_password` لازم است و مقدار اشتباه آن `422` روی `current_password` می‌گیرد (`رمز عبور درست نیست.`) و یک ورود
ناموفق حساب می‌شود. اگر هنوز رمز عبوری ندارد — مثلا با گوگل ثبت‌نام کرده — این درخواست رمز عبور می‌گذارد. رمز عبور تازه
تابع قاعده ثبت‌نام است ([ثبت‌نام با ایمیل](Store-API-Sign-In.md#ثبت‌نام-با-ایمیل)). همه Sessionهای دیگر کاربر تمام
می‌شوند؛ این یکی می‌ماند و به کاربر خبر داده می‌شود (`password_changed`).

## ورود دومرحله‌ای

کد یک برنامه احراز هویت (TOTP: شش رقم، گام‌های ۳۰ ثانیه‌ای، RFC 6238) که بعد از رمز عبور خواسته می‌شود. فقط برای حسابی که
ایمیل و رمز عبور دارد — وگرنه `422`
(`ورود دو مرحله‌ای برای ورود با ایمیل و رمز است؛ اول ایمیل و رمز عبور را به حساب اضافه کنید.`). ورود با تلگرام و گوگل
هیچ‌وقت آن را نمی‌خواهد: خود تلگرام یا گوگل کاربر را وارد کرده. هر قدم زیر ورود تازه لازم دارد
([ورود تازه](#ورود-تازه))؛ روشن یا خاموش شدنش به کاربر خبر داده می‌شود (`two_factor_enabled`، `two_factor_disabled`).

1. درخواست `POST /me/2fa/setup` (بدون بدنه) یک کلید تازه برمی‌گرداند که ۱۵ دقیقه منتظر اولین کد می‌ماند؛ راه‌اندازی بعدی
   جایش را می‌گیرد — تا وقتی ورود دومرحله‌ای خاموش است (اگر روشن باشد:
   `422` با `ورود دو مرحله‌ای این حساب از قبل روشن است؛ برای کلید تازه، اول آن را خاموش کنید.`). مقدار `uri` را به شکل
   کد QR نشان دهید — سایت خودش آن را می‌سازد، مثلا با <code dir="ltr">QRCode.toDataURL(uri)</code> از پکیج `qrcode` — و
   `secret` را برای وارد کردن دستی نشان دهید. issuer این URI نام فروشگاه است و account آن ایمیل کاربر. پاسخ `200` به
   `POST /me/2fa/setup`:
   ```json
   {
     "secret": "NA7NDMGJE74CMTA6EYKQXVVMQH5TV45Y",
     "uri": "otpauth://totp/Amo%20Shop:sara%40example.com?secret=NA7NDMGJE74CMTA6EYKQXVVMQH5TV45Y&issuer=Amo%20Shop&algorithm=SHA1&digits=6&period=30"
   }
   ```
2. درخواست `POST /me/2fa/enable` با `{ code }` و کد برنامه آن را روشن می‌کند و ده کد بازیابی برمی‌گرداند — که فقط همین
   یک بار نشان داده می‌شوند: از کاربر بخواهید آن‌ها را نگه دارد. هر کد ده حرف بزرگ و رقم است، بدون کاراکترهای شبیه به
   هم، و یک بار به جای کد برنامه کاربر را وارد می‌کند. پاسخ `200` به `POST /me/2fa/enable`:
   ```json
   { "recovery_codes": ["EVWJRCJMJX", "WWFJGJDFD4", "PUJNQZJSVR", "NTYX8TXUQJ", "PK8XHXEND9", "2YXYP83VP6", "C4GU7BH8CH", "F85HJMXH35", "MKMYTZEDDY", "ED3GBCHUJD"] }
   ```
   کد اشتباه `422` روی `code` می‌گیرد
   (`کد درست نیست؛ کدی را که برنامه احراز هویت همین حالا نشان می‌دهد وارد کنید.`)؛ بعد از پنج کد اشتباه، یا بعد از ۱۵
   دقیقه، `422` روی `code` می‌گوید از اول راه‌اندازی کنید
   (`زمان راه‌اندازی ورود دو مرحله‌ای گذشته است؛ آن را از اول راه‌اندازی کنید.`).
3. درخواست `POST /me/2fa/disable` با `{ password }` آن را خاموش می‌کند (رمز اشتباه: `422` روی `password` که یک ورود ناموفق
   حساب می‌شود؛ اگر از قبل خاموش باشد، `422` با `ورود دو مرحله‌ای این حساب روشن نیست.`).

کاربری که گوشی‌اش را گم کرده از یک کد بازیابی استفاده می‌کند، یا از پشتیبانی کمک می‌خواهد، که می‌تواند ورود دومرحله‌ای را
از پنل خاموش کند — یا یکی از مدیران سایت از وب‌سایت، اگر فروشگاه این اجازه را به آن‌ها داده باشد — و آن موقع هم به کاربر
خبر داده می‌شود (`two_factor_disabled`)، در تلگرام و با ایمیل. ورود دومرحله‌ای خود مدیران فقط از پنل خاموش می‌شود.

## دستگاه‌ها

پاسخ `200` به `GET /me/sessions`:
```json
{
  "sessions": [
    { "id": 77, "device": "Chrome در Windows", "ip": "203.0.113.7", "created_at": "2026-10-07T12:00:00+00:00", "last_used_at": "2026-10-08T09:41:00+00:00", "current": true },
    { "id": 61, "device": "Safari در iOS", "ip": "198.51.100.23", "created_at": "2026-09-30T18:12:44+00:00", "last_used_at": "2026-10-06T21:05:10+00:00", "current": false }
  ]
}
```

جدیدترین اول، حداکثر ۲۰ تا ([توکن‌ها و Sessionها](Store-API-Sign-In.md#توکن‌ها-و-sessionها))؛ `device` همان چیزی است که
مرورگر درباره خودش گفته، به زبان ساده؛ `ip` آدرسی که از آن وارد شده؛ `current` دستگاهی است که همین درخواست را
فرستاده؛ `last_used_at` هر چند دقیقه یک بار نوشته می‌شود، نه با هر درخواست. درخواست
<code dir="ltr">DELETE /me/sessions/{id}</code> یک Session را تمام می‌کند (`204`) — تمام کردن `current` همین دستگاه را
خارج می‌کند، مثل `POST /auth/logout`. Session کاربر دیگر `404` می‌گیرد. پیش‌نمایش پنل از مینی‌اپ
([پیش‌نمایش پنل](Store-API-Sign-In.md#پیش‌نمایش-پنل)) جزو دستگاه‌های او نیست: اینجا فهرست نمی‌شود، و شناسه‌اش اینجا هم `404`
می‌گیرد.

## اثر انگشت یا چهره

مینی‌اپ می‌تواند یک روش ورود را با اثر انگشت یا چهره دستگاه، از طریق `BiometricManager` تلگرام، دوباره ثابت کند، بی‌آنکه
فروشگاه هیچ‌کدام را ببیند: فروشگاه به Session یک رمز می‌دهد، تلگرام آن را در فضای امن دستگاه نگه می‌دارد و فقط بعد از تطبیق
اثر انگشت یا چهره پس می‌دهد، و مینی‌اپ آن را به‌شکل <code dir="ltr">{ "method": "biometric", "token": … }</code> به
`POST /me/reauthenticate` می‌فرستد ([ورود تازه](#ورود-تازه)).

پاسخ `200` به `PUT /me/biometric` (بدون بدنه، با ورود تازه):
```json
{ "token": "4f9c2d7e1a8b3f6c0e5d9a2b7c4f1e8d3a6b0c9f2e5d8a1b4c7f0e3d6a9b2c5f" }
```

- مقدار `token` — ۶۴ کاراکتر هگز، که فقط همین یک بار نشان داده می‌شود — به `BiometricManager.updateBiometricToken` داده می‌شود. فقط sha256 آن، و فقط روی همین Session، نگه داشته می‌شود: روی Sessionهای دیگر کاربر چیزی را ثابت نمی‌کند، و یک `PUT` تازه جایش را می‌گیرد.
- ساختنش ورود تازه می‌خواهد، چون ثابت کردن دوباره‌اش یک روش ورود را ثابت می‌کند: وگرنه `403` با همان challenge. فقط روی Sessionی ساخته می‌شود که خود مینی‌اپ وارد کرده (`session.method` برابر `mini_app`): توکن Session دیگری که با کلید مینی‌اپ بیاید `422` می‌گیرد — وگرنه خودش را تا آخر عمرش تازه نگه می‌داشت.
- درخواست `DELETE /me/biometric` (`204`) آن را فراموش می‌کند؛ تمام شدن Session هم همین‌طور. `session.biometric` در پاسخ `GET /me` می‌گوید رمزی نگه داشته شده یا نه.
- هر دو فقط مال مینی‌اپ‌اند: با کلید یک وب‌سایت `404` می‌گیرند، انگار که نیستند، و `POST /me/reauthenticate` آنجا `biometric` را روی `method` رد می‌کند. وب‌سایت اثر انگشتی ندارد که رمز را پشتش نگه دارد — اگر کنار توکن Bearer نگه داشته شود، این دو با هم Session را تا آخر عمرش تازه نگه می‌دارند.
- ثابت کردنش آن ۱۵ دقیقه Session را از همین حالا تازه می‌کند؛ اگر ناموفق باشد، یک ورود ناموفق از آن آدرس شمرده می‌شود ([محدودیت‌ها و مدت اعتبار](Store-API-Sign-In.md#محدودیت‌ها-و-مدت-اعتبار)).

## روش‌های ورود: افزودن و حذف

هر حساب از هر نوع حداکثر یکی دارد: یک حساب تلگرام، یک حساب گوگل، یک ایمیل (با رمز عبورش)، یک شماره موبایل. هر کدام همان‌طور ثابت می‌شود
که با آن وارد می‌شوند؛ افزودن و حذف هر کدام ورود تازه لازم دارد ([ورود تازه](#ورود-تازه)):

| افزودن | درخواست | پاسخ‌ها |
|---|---|---|
| تلگرام | `POST /me/identities/telegram` — `{ id_token, nonce }` از پاپ‌آپ، یا `{ code, state, code_verifier }` از ریدایرکت با stateی که همین Session از `POST /me/telegram/authorize` گرفته ([پاپ‌آپ](Store-API-Sign-In.md#تلگرام-پنجره-پاپ‌آپ)، [ریدایرکت](Store-API-Sign-In.md#تلگرام-ریدایرکت)) | `200` با `{ customer }`، یا `202` با پیشنهاد ادغام |
| گوگل | `POST /me/identities/google` — `{ id_token, nonce }` ([گوگل](Store-API-Sign-In.md#گوگل)) | `200` با `{ customer }`، یا `202` با پیشنهاد ادغام |
| ایمیل | `POST /me/identities/email` — `{ email, password }`: کدی به آدرس فرستاده می‌شود؛ بعد `POST /me/identities/email/verify` — `{ email, code }` | `202` با `{ expires_in }`؛ بعد `200` با `{ customer }`، یا `202` با پیشنهاد ادغام |
| موبایل | `POST /me/identities/phone` — `{ phone }`: کدی به شماره پیامک می‌شود؛ بعد `POST /me/identities/phone/verify` — `{ phone, code }` (مال وب‌سایت، تا وقتی `sign_in.phone` درست است) | `202` با `{ sent, expires_in, resend_in }`؛ بعد `200` با `{ customer }`، یا `202` با پیشنهاد ادغام |

- پاسخ `200` — اضافه شد (به کاربر خبر داده می‌شود: `way_in_added`)، یا از قبل مال همین حساب بود. تلگرام یوزرنیم و نام‌هایش
  را می‌آورد، به جای نام‌هایی که حساب داشت (حساب تلگرامی که نام خانوادگی ندارد نام خانوادگی را خالی می‌گذارد)، و از آن به
  بعد `PATCH /me` تغییر نام را رد می‌کند؛ گوگل آدرس ایمیلی را که تایید می‌کند می‌آورد ([گوگل](Store-API-Sign-In.md#گوگل))،
  اگر حساب آدرسی ندارد و کس دیگری هم آن را ندارد؛ ایمیل با رمز عبوری می‌آید که همراهش انتخاب شده (و به‌عنوان افزودن روش
  ورود خبر داده می‌شود، نه تغییر رمز عبور)؛ شماره از آن به بعد با پیامک وارد می‌شود.
- پاسخ `202` — مال حساب دیگری از همین فروشگاه است: یک پیشنهاد ادغام ([پیشنهاد ادغام](#پیشنهاد-ادغام)). برای گوگل، این
  همچنین وقتی پیش می‌آید که حساب گوگل برای فروشگاه تازه است ولی آدرسی که تایید می‌کند مال حساب دیگری است.
- پاسخ `422` — حساب یکی دیگر از همین نوع دارد
  (`این حساب به حساب تلگرام دیگری وصل است؛ اول آن را جدا کنید.`، `این حساب به حساب گوگل دیگری وصل است؛ اول آن را جدا کنید.`،
  `این حساب ایمیل دارد.`، `این حساب شماره موبایل دارد؛ برای شماره تازه، اول آن را جدا کنید.`)، ادغامی که قاعده‌ها اجازه
  نمی‌دهند ([پیشنهاد ادغام](#پیشنهاد-ادغام))، ورود با تلگرام، گوگل یا پیامک وب‌سایت خاموش است، یا ریدایرکت تلگرام راه‌اندازی نشده
  (`ورود با redirect برای این وب‌سایت آماده نیست؛ Client Secret تلگرام در پنل وارد نشده است.`) — این سه بدون فیلد —، یا
  تاییدی که معتبر نبود: تایید تلگرام یا گوگل روی `id_token` (یا `code` ریدایرکت، از جمله stateی که Session دیگری گرفته)
  — هرگز `401`، چون Session سالم است —، کد ایمیل یا پیامک روی `code` (`کد درست نیست یا منقضی شده است.`)، و شماره‌ای که
  موبایل ایران نیست روی `phone`.
- قدم اول ایمیل همچنین `503` می‌گیرد وقتی ایمیل فروشگاه فرستاده نمی‌شود یا سهمیه ایمیل‌های ورود آن تمام شده
  (`فعلا ایمیلی از این فروشگاه فرستاده نمی‌شود؛ کمی بعد دوباره امتحان کنید یا از راه دیگری وارد شوید.`)، و `502` وقتی سرور
  ایمیل، ایمیل را نپذیرفته (`ایمیل فرستاده نشد؛ کمی بعد دوباره امتحان کنید.`). `sign_in.email` در
  <code dir="ltr">GET /</code> وقتی ثبت‌نام با ایمیل خاموش است چیزی درباره این نمی‌گوید: افزودن ایمیل را پیشنهاد کنید و
  این خطاها را مدیریت کنید.

کد ایمیل فرستاده می‌شود، چه حساب دیگری آن آدرس را داشته باشد چه نه — اول آدرس ثابت می‌شود —؛ فقط مال همین حساب است (کد
کاربر دیگری برای همان آدرس دست نمی‌خورد)؛ و از سهمیه‌های ایمیل ثبت‌نام کم می‌شود
([محدودیت‌ها و مدت اعتبار](Store-API-Sign-In.md#محدودیت‌ها-و-مدت-اعتبار)) به‌علاوه یک سهمیه جداگانه: هر کاربر روزی
حداکثر پنج کد از این نوع می‌تواند بخواهد. کدهای اشتباه در سهمیه آدرس و سهمیه همین حساب شمرده می‌شوند.

کد شماره هم همین‌طور می‌رود: چه حساب دیگری آن شماره را داشته باشد چه نه، فقط مال همین حساب، با سهمیه‌های پیامکی
`POST /auth/phone` ([کد پیامکی](Store-API-Sign-In.md#کد-پیامکی)) به‌علاوه روزی ده کد برای هر کاربر. قدم اولش همچنین وقتی
سرویس پیامک آن را نپذیرد `502` و وقتی سهمیه پیامک تمام شده `503` می‌گیرد.

درخواست <code dir="ltr">DELETE /me/identities/{telegram|google|email|phone}</code> یک روش را حذف می‌کند و `{ customer }`
را برمی‌گرداند (به کاربر خبر داده می‌شود: `way_in_removed`) — ولی هیچ‌وقت آخرین روش را حذف نمی‌کند
(`422` با `حداقل یک روش ورود باید بماند.`؛ شماره موبایل فقط جایی روشی حساب می‌شود که می‌ماند که ورود با پیامک همین حساب را
با آن باز کند: زیر کلید وب‌سایتی که ورود با پیامک دارد، شماره موبایل ایران، و از حساب‌هایی که این شماره را دارند همانی که
چنین ورودی بازش می‌کند؛ برای روشی که حساب ندارد، `422` با `این روش ورود به حساب وصل نیست.`). ایمیل،
چه رمز عبور داشته باشد چه نه، یک روش ورود حساب می‌شود، پس حسابی که با گوگل ثبت‌نام کرده وقتی گوگل را حذف کند آدرسش را
نگه می‌دارد: بدون رمز عبور (`has_password` برابر false) از آن به بعد فقط با گذاشتن رمز از راه کد فراموشی رمز عبور، یا
دوباره با گوگل، وارد می‌شود — پیش از اینکه کاربر گوگل را حذف کند این را به او بگویید. ایمیل همراه رمز عبور و ورود
دومرحله‌ای‌اش حذف می‌شود، و ایمیلی به همان آدرس می‌رود که دیگر روش ورود نیست. حذف تلگرام سرویس‌ها را در همین حساب نگه
می‌دارد، و ربات از پیام بعدی آن حساب تلگرام را کاربر تازه‌ای می‌شناسد — پیش از تایید کاربر این را بگویید. از راه کلید مینی‌اپ این کار رد می‌شود، با `422` روی `kind`
(`حساب تلگرام از داخل مینی‌اپ جدا نمی‌شود؛ …`): مینی‌اپ و ربات کاربر را با همین حساب می‌شناسند — وب‌سایت آن را حذف
می‌کند. حذف شماره در فروشگاهی که ربات شماره همه کاربران را می‌خواهد (`shop.phone_required`) باعث می‌شود ربات دوباره آن را
بخواهد. «تغییر ایمیل» و «تغییر شماره» نداریم: آن را حذف کنید (روش ورود دیگری باید بماند) و تازه را اضافه کنید.

## پیشنهاد ادغام

افزودن روش ورودی که مال حساب دیگری از همان فروشگاه است، پاسخ `202` می‌گیرد:

پاسخ `202` به `POST /me/identities/telegram`:
```json
{
  "merge": {
    "token": "6a4ae800353b0c5c9a84b8a84d6caabce080931b4a069c6140425447d532f462",
    "expires_in": 900,
    "account": {
      "name": "علی رضایی",
      "created_at": "2025-11-02T17:20:00+00:00",
      "services": 1,
      "orders": 4,
      "balance": "15000.00",
      "telegram": true,
      "email": false,
      "google": false,
      "phone": true
    },
    "keeps": "other"
  }
}
```

حساب دیگر را به کاربر نشان دهید تا بتواند ببیند مال خودش است — نامش (اگر نباشد `null`)، از کی ساخته شده، سرویس‌های فعالش
(`services`)، سفارش‌هایش (`orders`)، موجودی‌اش (`balance`)، روش‌های ورودش (`phone`: شماره موبایل تاییدشده دارد) — و
اینکه ادغام چه معنایی دارد:

- **حساب قدیمی‌تر همیشه می‌ماند.** <code dir="ltr">keeps: "this"</code> — حسابی که با آن وارد شده می‌ماند و حساب دیگر در
  آن ادغام می‌شود. <code dir="ltr">keeps: "other"</code> — حسابی که با آن وارد شده در حساب دیگر ادغام می‌شود؛ کاربر وارد
  می‌ماند، این بار در همان حساب دیگر، که از آن به بعد `id` آن شناسه اوست.
- **همه چیز به حسابی که می‌ماند منتقل می‌شود:** سفارش‌ها و پرداخت‌هایشان، سرویس‌ها، کیف پول (یک دفتر تراکنش، با جمع
  موجودی‌ها)، همه دستگاه‌هایی که وارد شده‌اند، اعلان‌ها، تیکت‌های پشتیبانی، نظرات، کاربرانی که دعوت کرده، و درخواست
  نمایندگی. روش‌های ورود، نام‌ها، تلفن و کد دعوت حساب دیگر جاهای خالی حسابی را که می‌ماند پر می‌کنند، و همین‌طور روشی که
  در حال افزودن بود: حساب تلگرام یا گوگل، ایمیل، یا شماره. رمز عبوری که همراه یک ایمیل انتخاب شده، اگر آن ایمیل آدرس حسابی باشد
  که می‌ماند، رمز عبور آن حساب می‌شود — به جای رمز قبلی — و همه Sessionهای دیگر آن حساب را تمام می‌کند. حساب دیگر از بین
  می‌رود.

برای پذیرفتن، `POST /me/merge` را با توکن پیشنهاد و با ورود تازه بفرستید ([ورود تازه](#ورود-تازه))؛ پاسخ حسابی است که
می‌ماند، و به کاربر خبر داده می‌شود (`account_merged` — و `password_changed` اگر ادغام رمز عبوری را که همراه ایمیل انتخاب
شده بود گذاشته) — کاربری را که در سایت نگه داشته‌اید با آن عوض کنید و همه چیز را دوباره بخوانید. نپذیرفتن یعنی هیچ کاری
نکنید: توکن ۱۵ دقیقه بعد منقضی می‌شود و چیزی عوض نمی‌شود.

درخواست `POST /me/merge`:
```json
{ "token": "6a4ae800353b0c5c9a84b8a84d6caabce080931b4a069c6140425447d532f462" }
```

پیشنهاد از همان اول، بدون توکن، رد می‌شود (`422`) وقتی: یکی از دو حساب مسدود باشد؛ هر دو یک حساب *متفاوت* از یک نوع
داشته باشند (`هر دو حساب به یک نوع روش ورود متفاوت وصل هستند (تلگرام)؛ اول یکی را جدا کنید.` — اول باید یکی حذف شود)؛
هر دو نماینده باشند؛ یا حساب دیگر فقط از راه ایمیلش پیدا شده باشد — با کد ایمیل، یا آدرسی که گوگل تایید می‌کند — و ورود
دومرحله‌ای‌اش روشن باشد
(`این ایمیل به حسابی با ورود دو مرحله‌ای وصل است؛ برای یکی کردن دو حساب، با همان ایمیل وارد شوید و روش ورود این حساب را از آنجا وصل کنید.`)،
یا فقط از راه شماره موبایلش، با کد پیامکی
(`این شماره به حسابی با ورود دو مرحله‌ای وصل است؛ برای یکی کردن دو حساب، به همان حساب وارد شوید و روش ورود این حساب را از آنجا وصل کنید.`):
کاربر وارد آن حساب می‌شود و روش ورود این حساب را از آنجا اضافه می‌کند. در `POST /me/merge`، پاسخ `422` با
`این پیشنهاد ادغام دیگر معتبر نیست؛ دوباره تلاش کنید.` یعنی توکن مصرف یا منقضی شده یا مال این حساب نیست، یا حساب دیگر دیگر
آن روش ورود را ندارد: از اول شروع کنید. ادغام آنجا دوباره هم سنجیده می‌شود، پس ردهای مرحله پیشنهاد ممکن است دوباره بیایند
— حساب دیگر مسدود شده، یا روش ورودی از نوعی که این حساب دارد گرفته، یا از راه آدرسش پیدا شده و بعد از آن ورود
دومرحله‌ای‌اش روشن شده —، هر کدام `422` با همان پیام.

ورود با پیامک هم، وقتی حساب دیگری از فروشگاه این شماره را دارد، کنار توکنش ادغامی پیشنهاد می‌دهد
([کد پیامکی](Store-API-Sign-In.md#کد-پیامکی)): همان `merge`، که به همان شکل با توکن تازه پذیرفته می‌شود.

فروشگاه از هر ادغام سابقه‌ای نگه می‌دارد — حسابی که ماند، شماره قبلی و روش‌های ورود حساب ادغام‌شده، و آنچه منتقل شد — که
پشتیبانی در صفحه کاربر در پنل می‌بیند.
