# معماری

نقشه‌ای از سیستم برای کسی که تازه با کد آشنا می‌شود: بخش‌های آن، مسیری که یک درخواست، یک آپدیت تلگرام و یک دقیقه
کار پس‌زمینه در میان آن‌ها طی می‌کند، و چند ایده‌ای که باقی سیستم بر آن‌ها تکیه دارد. صفحه هر بخش جزئیات بیشتری
دارد: [دیتابیس](Database.md)، [قراردادهای کد](Conventions.md)، [قرارداد API](API-Contract.md)،
[درایورها](Drivers.md)، و صفحه‌های ساختار داخلی — [فروش](Internals-Commerce.md)، [سرویس‌ها](Internals-Services.md)،
[ربات تلگرام](Internals-Telegram-Bot.md)، [API وب‌سایت](Internals-Website-API.md)، [پنل‌ها](Internals-Panels.md).

## شکل کلی

پروژه AmoBot یک برنامه PHP 8.2 است (Slim 4، PHP-DI، Eloquent، Symfony Console) که هیچ HTMLی رندر نمی‌کند جز یک صفحه
کوچک — صفحه‌ای که مرورگر کاربر از یک درگاه پرداخت آنلاین به آن برمی‌گردد (`Payments\Controllers\ReturnPage`). این
برنامه چهار چهره دارد:

- **دو پنل** — پنل مالک فروشگاه در `/admin/` و پنل نماینده در `/agent/` — یک پروژه React (`resources/panel`) که به
  فایل‌های استاتیک بیلد می‌شود و وب‌سرور همان فایل‌ها را بی‌تغییر سرو می‌کند. پنل‌ها فقط از راه JSON API با PHP حرف
  می‌زنند.
- **ربات‌های تلگرام** — ربات اصلی و ربات هر نماینده — که آپدیت‌هایشان از راه Webhook یا long polling می‌رسد.
- **رابط Store API** (<code dir="ltr">/api/store/v1/{store}</code>)، که وب‌سایت خود فروشگاه آن را از مرورگر
  بازدیدکنندگانش صدا می‌زند.
- **کار پس‌زمینه**، که هر دقیقه یک بار با یک Cron، یک سرویس پینگ بیرونی یا پولینگ راه می‌افتد.

همه چیز باید روی هاست اشتراکی (cPanel و مانند آن) اجرا شود: مالک فروشگاه شل ندارد، و daemon، سرور کش و مرحله بیلد هم
در کار نیست. همین یک محدودیت دلیل بسیاری از تصمیم‌های زیر است — `config.php` به‌جای متغیرهای محیطی، فایل به‌جای
Redis، نصب‌کننده وب و به‌روزرسان، و یک زمان‌بند که کارها را تکه‌تکه انجام می‌دهد.

## راه‌اندازی برنامه

هر دو، `public/index.php` (برای HTTP) و `bin/console` (برای CLI)، فایل `bootstrap/app.php` را صدا می‌زنند که
<code dir="ltr">Core\Application::boot()</code> را اجرا می‌کند:

1. وقتی PHP با همان حسابی اجرا می‌شود که مالک برنامه است، فایل‌هایی که برنامه می‌نویسد فقط برای همان حساب قابل
   دسترسی می‌شوند (`Core\Support\Files`). هشدارهای PHP به پاسخ‌ها راه پیدا نمی‌کنند و به
   `storage/logs/php-errors.log` می‌روند؛ exceptionها آرگومان‌های فراخوانی را نگه نمی‌دارند.
2. فایل `config.php` (تنظیمات مالک فروشگاه — [پیکربندی](Configuration.md) را ببینید) خوانده می‌شود و به بخش‌هایی
   تبدیل می‌شود که `config/*.php` از آن می‌سازند (`Core\Config`). هیچ چیز از متغیرهای محیطی خوانده نمی‌شود.
3. ساعت PHP روی UTC تنظیم می‌شود؛ منطقه زمانی فروشگاه (`APP_TIMEZONE`) فقط برای نمایش نگه داشته می‌شود.
4. کانتینر PHP-DI از روی `bootstrap/container.php` ساخته می‌شود — factoryها، رجیستری‌های درایورها و مسیر هر فایلی که
   برنامه می‌نویسد. هر چه آنجا نیامده باشد autowire می‌شود.
5. دیتابیس از راه درایورش راه‌اندازی می‌شود، فید تغییرات شروع به گوش دادن می‌کند، و castهای رمزنگاری‌شده کلیدشان را
   می‌گیرند.

بعد <code dir="ltr">Application::http()</code> برنامه Slim را می‌سازد (`Core\Http\HttpKernel`) و
<code dir="ltr">Application::console()</code> برنامه CLI را (`App\Console\Kernel`، که هر دستورش فقط هنگام اجرا ساخته
می‌شود).

## مسیر یک درخواست

لایه‌های middleware سراسری، از بیرونی‌ترین: شناسه درخواست، هدرهای امنیتی، CORS (فقط برای API وب‌سایت‌ها)، محافظ
خروجی (خروجی سرگردان هرگز به پاسخ نمی‌رسد)، مدیریت خطا، مسیریابی، و خواننده بدنه JSON (حداکثر ۱ MiB، که پیش از decode
شدن خوانده می‌شود).

هر چیز دیگری که یک درخواست لازم دارد را **middlewareهای گروه مسیر** آن فراهم می‌کنند، در `routes/api.php`،
`routes/web.php` و `routes/webhooks.php`. هیچ middlewareی خودش آدرس را بررسی نمی‌کند، پس این مسیریاب است که تعیین
می‌کند درخواست چیست، و آدرسی که جور دیگری نوشته شده باشد (encodeشده، زیر یک زیرپوشه) به همان مسیر و پشت همان
بررسی‌های امنیتی می‌رسد — `tests/Feature/RouteGuardsTest` برای اثبات این، همه مسیرها را یکی‌یکی امتحان می‌کند.

| گروه | بررسی‌های امنیتی، به ترتیب |
|---|---|
| <code dir="ltr">/api/admin</code> (پنل مدیریت) | نصب‌شده › هدر CSRF برای هر تغییر › Session › ورود مالک فروشگاه › فروشگاهی که درخواست نام می‌برد |
| <code dir="ltr">/api/agent</code> (پنل نمایندگی) | نصب‌شده › هدر CSRF برای هر تغییر › Session › ورود یک نماینده، در فروشگاه ربات خودش |
| <code dir="ltr">/api/install</code> | هنوز نصب‌نشده › هدر CSRF برای هر تغییر › کلید نصب |
| <code dir="ltr">/api/store/v1/{store}</code> | نصب‌شده › وب‌سایتی که کلید باز می‌کند › بدنه‌های JSON › (توکن Bearer یک کاربر) |
| <code dir="ltr">…/admin</code> زیر store | › توکن یک کاربر › یکی از مدیران سایت، که راهش داده‌اند و ورودش به اندازه کافی تازه است |
| <code dir="ltr">/webhooks/…</code>، <code dir="ltr">/cron/{token}</code>، <code dir="ltr">/payments/callback/{payment}/{secret}</code> (Callback یک درگاه آنلاین) | نصب‌شده (رمزی که در آدرس است هویت را ثابت می‌کند) |
| <code dir="ltr">/payments/webhooks/{driver}</code> (Webhookی که درگاه امضا می‌کند: Webhook درگاه Variza) | نصب‌شده (امضا هویت را ثابت می‌کند) |
| `/`، <code dir="ltr">/health</code>، <code dir="ltr">/api/app</code> | هیچ: این‌ها پیش از نصب هم پاسخ می‌دهند |

هر کنترلر یعنی *بارگذاری، سرویس، نمایش* (load → service → present). کنترلر جلوی ردهای فروشگاه را نمی‌گیرد: یک
`Core\Exceptions\DomainRuleException` (یک `ValidationException`، یک 409، یک 429…) را `Core\Http\ErrorHandler` با
وضعیت، پیام و خطاهای فیلدهای خودش پاسخ می‌دهد؛ ردیفی که وجود ندارد (یا مال فروشگاه دیگری است) 404 است؛ و هر چیز
دیگری یک 500 عمومی است که یک بار همراه trace خودش لاگ می‌شود.

## خطاها و مقاوم‌سازی

هر درخواست شناسه‌ای از خود برنامه می‌گیرد (`Core\Http\RequestId`): این شناسه در هدر `X-Request-Id`، در بدنه هر خطا
(`{message, errors?, request_id}`) و روی هر خط لاگی که درخواست می‌نویسد، کنار اینکه برای چه کسی کار کرده، می‌آید.
پنل‌ها آن را در خطای سرور به‌صورت «کد پیگیری» نشان می‌دهند، و مالک فروشگاه خط‌های لاگ را با آن پیدا می‌کند. جزئیات
یک خطا (کلاس، trace) فقط با `APP_DEBUG`، فقط برای یک 500، و فقط برای درخواستی که مستقیم از خود سرور آمده باشد نشان
داده می‌شود. آنچه برنامه از پسش برنمی‌آید — یک `config.php` خراب، یک خطای fatal — به آخرین چاره `public/index.php`
می‌رسد: همان 500 از نوع JSON با شناسه‌اش.

در کنار این‌ها:

- هر پاسخ یک سیاست sandboxing دارد و کش نمی‌شود (صفحه بازگشت سیاست خودش را دارد، که آن هم هیچ اسکریپتی اجرا
  نمی‌کند)؛
- برنامه اطلاعات محرمانه را از هر خطی که در لاگش می‌نویسد و از جزئیات هر خطا حذف می‌کند (`Core\Logging\Redact`):
  توکن ربات‌ها، بخش محرمانه آدرس‌های ماشینی (Webhookها، Cron، Callbackهای پرداخت)، نام کاربری و رمزی که در یک آدرس
  نوشته شده باشد (مثل آدرس پراکسی) و کلیدی که در query یک آدرس باشد. هشدارها و خطاهای fatal خود PHP، که خود PHP در
  `storage/logs/php-errors.log` می‌نویسد، پاک‌سازی نمی‌شوند؛
- به Callback یک درگاه آنلاین هرگز اعتماد نمی‌شود — فقط باعث می‌شود فروشگاه از خود درگاه بپرسد
  (`Payments\Services\OnlinePayments`) —، و Webhook یک درگاه فقط وقتی پذیرفته می‌شود که رمز یکی از روش‌های پرداخت آن
  را امضا کرده باشد؛
- هر ورودی محدودیت تعداد تلاش دارد، و اگر خود این محدودیت خطا بدهد راه بسته می‌ماند (fail closed)؛
- نصب‌کننده یک آپلود تازه کلیدی از فایل‌های هاست می‌خواهد؛
- تصویرهای آپلودشده از روی بایت‌هایشان سنجیده و دوباره نوشته می‌شوند؛
- هر فایلی که برنامه می‌نویسد، جایی که PHP با حساب مالک برنامه اجرا می‌شود، فقط برای همان حساب قابل دسترسی است
  (`Core\Support\Files`).

سیاست گزارش آسیب‌پذیری در [امنیت](Security.md) آمده و آنچه به اداره‌کننده هاست مربوط است در
[اجرا روی هاست](Running-In-Production.md).

## ماژول‌ها

کد دامنه در <code dir="ltr">app/Modules/&lt;Module&gt;/</code> است (مدل‌ها، سرویس‌ها، کنترلرها، enumها، taskها).
`app/Core` (HTTP، دیتابیس، درایورها و فرم‌ها، ایمیل، کپچا، زمان‌بندی، امنیت، Sessionها، لاگ، پیکربندی، فایل‌ها) و
`app/Support` (ورودی، پول، زمان، فارسی، حجم) نام هیچ ماژولی را نمی‌برند. آنچه Core از یک ماژول لازم دارد interfaceی
است که آن ماژول پیاده‌سازی می‌کند: `Core\Scheduling\Shops` همان `BotShops` ماژول Bots است.

| ماژول | چیست |
|---|---|
| Providers | پنل‌های VPN: کانکتورها (3X-UI، PasarGuard)، سرورها و سلامتشان |
| Catalog | پلن‌ها، دسته‌بندی‌ها، و اینکه امروز کدام سرورها می‌توانند یک پلن را بفروشند |
| Subscriptions | سرویس یک کاربر روی یک پنل: ساخت روی پنل، همگام‌سازی، تمدید، انتقال‌ها، هدیه‌های زمان و حجم، خریدهای اضافه، یادآوری‌ها |
| Orders, Payments | چرخه عمر سفارش؛ روش‌های پرداخت، پیش‌فاکتور مشترک ربات و وب‌سایت، تسویه |
| Discounts, Rewards | کدها، فروش‌های ویژه، سطوح وفاداری؛ کش‌بک، کدهای هدیه، گردونه شانس، قرعه‌کشی شبانه |
| Users, Referrals | کاربران، کیف پول‌ها، گروه‌ها و تصویرها؛ لینک‌های دعوت و پورسانت‌ها |
| Agency, Bots | نماینده‌ها، سطح‌ها و حجمشان؛ ربات‌ها، و اینکه کد در فروشگاه چه کسی کار می‌کند |
| Telegram | ربات‌ها: توزیع آپدیت‌ها، handlerها، گیت‌ها، متن‌ها، کیبوردها، ارسال‌های همگانی، گروه گزارش‌ها |
| Accounts, Store | ورود و حساب کاربری کاربران وب‌سایت؛ API وب‌سایت‌ها |
| Notifications, Support, Reviews | آنچه فروشگاه به کاربر می‌گوید؛ تیکت‌های پشتیبانی؛ نظرات کاربران |
| Auth | ورود به پنل‌ها، محدودیت تعداد تلاش (throttle)، principalها و actorها، مجوزهایی که فروشگاه به مدیران سایتش می‌دهد (`StaffGrant`) |
| Admin | کنترلرهای پنل‌ها، داشبورد و صف‌ها |
| Settings, Installer, Updates | صفحه‌های تنظیمات؛ نصب‌کننده وب؛ به‌روزرسانی با یک دکمه |

اینکه هر ماژول می‌تواند نام کدام ماژول‌ها را ببرد در یک نگاشت آمده است، `MODULES` در
`tests/Unit/Core/LayersTest.php`، و این نگاشت دقیقا با کد مقایسه می‌شود: یک وابستگی تازه میان ماژول‌ها تست را رد
می‌کند تا وقتی در نگاشت بیاید — و هر جا این وابستگی چیزی بیشتر از استفاده ساده از سرویس‌های ماژول دیگر باشد، با
کامنتی که دلیلش را بگوید. ماژولی که ماژول دیگری به آن وابسته است، خودش به آن ماژول وابسته نمی‌شود: Store ماژول
Accounts را صدا می‌زند، و Accounts آنچه را از یک وب‌سایت لازم دارد از راه interface خودش می‌پرسد
(`Accounts\Contracts\SignInSite`). درهای ورود به کل فروشگاه — Admin، Store، Telegram — نام بیشتر ماژول‌ها را می‌برند.

## چند ربات، یک دیتابیس

یک نصب، ربات اصلی و ربات هر نماینده را اجرا می‌کند، **هر کدام با فروشگاهی از آن خودش** — کاربران، پلن‌ها، دسته‌بندی‌ها،
روش‌های پرداخت، سفارش‌ها، پرداخت‌ها، سرویس‌ها، تنظیمات، متن‌ها، کیبوردها، گروه گزارش‌ها، ارسال‌های همگانی، وب‌سایت،
تیکت‌ها — در همان دیتابیس. سرورها، هدیه‌های زمان و حجم، نمایندگی و خود ربات‌ها مال کل نصب‌اند.

- ردیف یک فروشگاه `bot_id` دارد، و مدلش از `Bots\Models\Concerns\BelongsToBot` استفاده می‌کند: یک global scope هر
  کوئری را به فروشگاه فعلی محدود می‌کند و ردیف تازه با آن پر می‌شود. ردیف فروشگاه دیگر به‌سادگی پیدا نمی‌شود — یک 404.
- کلاس `Bots\CurrentBot` می‌گوید کد در فروشگاه چه کسی کار می‌کند: رباتی که آپدیت به آن رسیده، فروشگاهی که یک درخواست
  پنل نام می‌برد، وب‌سایتی که یک کلید فروشگاه باز می‌کند، و برای یک کار زمان‌بندی‌شده هر فروشگاه به نوبت.
  <code dir="ltr">CurrentBot::run($bot, $work)</code> در یک فروشگاه کار می‌کند و برمی‌گردد؛
  <code dir="ltr">CurrentBot::everywhere($work)</code> این محدوده را برای کار روی سرورها برمی‌دارد.
- هر چه مال هر فروشگاه است از همین پیروی می‌کند: `BotApi` از زبان ربات فعلی حرف می‌زند، `Settings` ردیف‌های همان
  فروشگاه را می‌خواند، یک اعلان در فروشگاه گیرنده‌اش اجرا می‌شود، و یک گزارش به گروه رباتی می‌رود که درباره آن است.
- پنل مدیریت فروشگاهی را که نشان می‌دهد در آدرسش نگه می‌دارد (<code dir="ltr">/admin/s/&lt;id&gt;/…</code>) و در هر
  درخواست آن را در هدر `X-Shop` نام می‌برد (`Auth\NamedShop`) — هرگز در Session، که همه تب‌های یک مرورگر در آن
  شریک‌اند.

## مفهوم Principal و Actor

هر کسی که از راه یک API روی فروشگاه کار می‌کند یک **principal** است (`Auth\Principal`): مالک فروشگاه در پنل خودش، یک
نماینده در پنل خودش، یا یکی از مدیران سایت (کاربری که نقشش ادمین است) در API مدیران وب‌سایت آن فروشگاه. بررسی امنیتی
گروه مسیر آن را روی درخواست می‌گذارد (<code dir="ltr">Principal::of()</code>)، درخواست را در فروشگاه آن اجرا می‌کند،
و آن را خواننده درخواست می‌کند (`Auth\CurrentPrincipal`) — یک پاسخ می‌تواند به اینکه چه کسی آن را می‌خواند بستگی داشته
باشد؛ برای نمونه، نام کاربری ورود مالک فروشگاه به هیچ‌کس دیگری نشان داده نمی‌شود.

هر عملیاتی که تصمیمی را ثبت می‌کند یک **actor** می‌گیرد (`Auth\Actor`): یک principal، یکی از مدیران ربات که دکمه‌ای
را در گروه گزارش‌ها می‌زند، یا خود فروشگاه (یک زمان‌سنج). نام actor به‌عنوان `reviewer` تصمیم نگه داشته می‌شود و روی
خط‌های لاگ درخواست می‌آید، و مدیری که به‌عنوان خودش کار می‌کند نمی‌تواند درباره حساب خودش تصمیم بگیرد
(`ActorRefusedException`). هر جای دیگر این نام از راه `Auth\Services\Reviewers` خوانده می‌شود: پنل مدیریت آن را
همان‌طور که نگه داشته شده نشان می‌دهد، و همه دیگران — یک نماینده، مدیران سایت، یک گروه گزارش‌ها
(<code dir="ltr">ShopReports::bySupport()</code>، «🎧 توسط پشتیبانی») — نام کاربری ورود مالک فروشگاه را «پشتیبانی»
می‌بینند. جایی که صفحه‌ای نشان می‌دهد چه کسی چیزی را نوشته (پاسخ یک تیکت)،
<code dir="ltr">Reviewers::names()</code> نام و نام خانوادگی مدیر سایت را کنار آن می‌خواند — همه نام‌هایی که صفحه
لازم دارد با یک کوئری.

## ربات‌ها در حال کار

هر آپدیت از راه Webhook تلگرام (<code dir="ltr">/webhooks/telegram/{secret}</code>، یا
<code dir="ltr">/webhooks/telegram/bot/{id}/{secret}</code> برای ربات یک نماینده) یا `bin/console bot:poll` می‌رسد،
که برای هر ربات یک long poll باز نگه می‌دارد و به هر کدام که پاسخ داد رسیدگی می‌کند. در فروشگاه همان ربات،
`Telegram\Update\Dispatcher` شناسه آپدیت را به نام خودش ثبت می‌کند (به هر آپدیت فقط یک بار رسیدگی می‌شود)، کاربر را
پیدا می‌کند، گیت‌ها را اجرا می‌کند (ربات خاموش، شماره تلفن، کانال‌ها) و آپدیت را به handlerی می‌دهد که
`routes/bot.php` دستور، دکمه، Callback یا مرحله گفتگوی آن را به آن نگاشت کرده است؛ بعد صف گروه گزارش‌ها فرستاده
می‌شود. جزئیات در [ساختار داخلی: ربات تلگرام](Internals-Telegram-Bot.md) آمده است.

## کار پس‌زمینه

کلاس `Core\Scheduling\Scheduler` کارهایی را که `bootstrap/schedule.php` فهرست می‌کند، هر کدام در فاصله زمانی خودش،
اجرا می‌کند. این زمان‌بند هر دقیقه یک بار راه می‌افتد: با `bin/console schedule:run` از یک Cron، با آدرس
<code dir="ltr">/cron/{token}</code> برای هاستی که Cron آن فقط می‌تواند یک URL را صدا بزند، یا با `bot:poll` (در
پروسه‌ای جدا، تا pollها ادامه پیدا کنند). در هر لحظه فقط یک اجرا (با یک قفل فایل)؛ زمان یک کار پیش از اجرایش نوشته
می‌شود، تا کاری که پروسه را از کار می‌اندازد هر دقیقه دوباره اجرا نشود. کار یک فروشگاه یک بار در هر فروشگاه اجرا
می‌شود؛ کارهای سرورها یک بار برای همه فروشگاه‌ها. ۴۵ ثانیه یک اجرا میان نوبت‌هایش تقسیم می‌شود
(`Core\Scheduling\Budget`)، و کاری که یک صف را پیش می‌برد در سهم خودش متوقف می‌شود، تا یک اجرا با تعداد نماینده‌ها
طولانی‌تر نشود. فهرست کارها در [اجرا روی هاست](Running-In-Production.md#زمان‌بند) آمده است.

## فید تغییرات

پنل‌ها بدون بارگذاری دوباره، فروشگاه را دنبال می‌کنند. `Core\Database\ChangeFeed` هر نوشتن commitشده را از رویدادهای
خود اتصال دیتابیس می‌خواند — هر کسی آن را انجام داده باشد: یک درخواست پنل، ربات، یک کار زمان‌بندی‌شده — و برای هر حوزه
یک شماره نسخه را بالا می‌برد (`change_versions`؛ `ChangeFeed::AREAS` هر جدول را به حوزه‌اش نگاشت می‌کند). هر پنل هر
چند ثانیه `GET /api/{panel}/changes` را می‌پرسد (مدیران سایت <code dir="ltr">…/admin/changes</code> را) و آنچه را
حوزه‌های تغییرکرده نشان می‌دهند دوباره می‌گیرد. هیچ سرویسی لازم نیست نوشتن‌هایش را گزارش کند؛ نوشتنی که لازم نیست
صفحه‌ای دنبالش کند (آخرین زمان دیده شدن یک کاربر) داخل <code dir="ltr">ChangeFeed::quietly()</code> انجام می‌شود.

هر نوشتن دو بار شمرده می‌شود: برای کل نصب، و برای فروشگاهی که در آن انجام شده است
(<code dir="ltr">Core\Scheduling\Shops::current()</code>).

- **پنل مدیریت** شماره‌های کل نصب را می‌خواند: نوشتن‌های همه فروشگاه‌ها.
- **پنل یک نماینده و مدیران سایت** شماره‌های فروشگاه خودشان را می‌خوانند، و نوشتن‌هایی را که برای همه
  فروشگاه‌ها انجام شده‌اند (نوشتنی که در همه فروشگاه‌ها با هم انجام شده، یا داخل
  <code dir="ltr">ChangeFeed::forEveryShop()</code>) — فعالیت فروشگاه دیگر هرگز صفحه‌هایشان را دوباره بارگذاری
  نمی‌کند. حوزه نمایندگی نوشتن‌های فروشگاه اصلی را هم دنبال می‌کند (حجمی که یک نماینده از ربات اصلی خریده، یک
  درخواست)، و آنچه صفحه‌های نمایندگی پنل مدیریت درباره فروشگاه یک نماینده می‌نویسند برای همه فروشگاه‌ها شمرده می‌شود
  (`Bots\ShopScopeMiddleware`).
- **حوزه‌های سرورها** (سرورها، هدیه‌های زمان و حجم، انتقال‌های یک سرور) فقط مال کل نصب‌اند: یک شماره برای همه.

## داده‌ها

فایل `database/schema.php` همه جدول‌هاست؛ یک فروشگاه نصب‌شده از راه <code dir="ltr">database/upgrades/</code> با هر
نسخه همراه می‌شود. موجودی‌ها دفتر تراکنش (ledger) هستند، وضعیت‌ها ستون‌هایی با compare-and-swap هستند، و هر لیست آنچه
را ردیف‌هایش نشان می‌دهند با تعداد ثابتی کوئری بارگذاری می‌کند. [دیتابیس](Database.md) را ببینید.

## فایل‌هایی که برنامه می‌نویسد

هاست اشتراکی سرور کش یا سرویس قفل ندارد، پس برنامه وضعیتش را در فایل‌هایی زیر <code dir="ltr">storage/</code> نگه
می‌دارد، که هر کدام یک ورودی در کانتینر است تا مجموعه تست‌ها آن را به پوشه‌ای مخصوص خودش ببرد:

| چه چیزی | کجا (ورودی کانتینر) |
|---|---|
| پیکربندی، و قفل نویسندگانش | `config.php` کنار برنامه (`config.file`)، `storage/cache/config.lock` |
| قفل نصب و نسخه دیتابیس | `storage/installed.lock` (`installation.lock`) |
| کلیدهای یک‌بارمصرف نصب‌کننده و بازیابی | `storage/install-key.txt`، `storage/recovery-key.txt` |
| وضعیت و قفل زمان‌بند؛ قفل پولینگ | `storage/cache/schedule.json` و `schedule.json.lock`، `storage/cache/bot-poll.lock` |
| شمارش‌های محدودیت تعداد تلاش | <code dir="ltr">storage/cache/throttle/</code> (`throttle.path`) |
| قفل‌هایی که باعث می‌شوند در هر لحظه فقط یک پروسه درباره یک پرداخت آنلاین از درگاه بپرسد: ۳۲ فایل قفل، که فایل هر پرداخت از روی شناسه‌اش انتخاب می‌شود | <code dir="ltr">storage/cache/payment-turns/</code> (`payments.turns`) |
| کپی‌های کوتاه‌مدت از تصویرهایی که تلگرام نگه می‌دارد | <code dir="ltr">storage/cache/files/</code> (`files.cache`) |
| کلیدهای سرویس‌دهنده‌های OpenID؛ جدول مسیریاب | <code dir="ltr">storage/cache/jwks/</code>، <code dir="ltr">storage/cache/routes/</code> |
| رسیدهای آپلودشده، تصویرهای تیکت‌ها، پس‌زمینه‌های QR | <code dir="ltr">storage/uploads/{receipts,tickets,qr}</code> |
| Sessionها، لاگ‌ها | <code dir="ltr">storage/sessions/</code>، <code dir="ltr">storage/logs/</code> |
| کار به‌روزرسان و پرچم حالت تعمیر | <code dir="ltr">storage/updates/</code>، `storage/updating.flag` |

نوشتن‌ها اتمیک‌اند (یک فایل موقت که روی فایل اصلی تغییر نام داده می‌شود) یا زیر یک قفل فایل انجام می‌شوند
(`Core\Support\Files`، `FileLock`)، تا خواننده هرگز نیمی از یک فایل را نبیند. فایل <code dir="ltr">.htaccess</code>
پوشه <code dir="ltr">storage/</code> دسترسی وب به آن را می‌بندد.

## درایورها

آنچه فروشگاه از راه دیگران انجام می‌دهد — یک پنل VPN، یک درگاه پرداخت، دیتابیس، ایمیل، یک کپچا — درایوری از یک خانواده
است که روی یک هسته کوچک بنا شده (`Core\Drivers`، `Core\Forms`). هر درایور فرم خودش را توصیف می‌کند، و پنل‌ها آن را فقط
از روی همین توصیف رسم می‌کنند. [درایورها](Drivers.md) را ببینید.
