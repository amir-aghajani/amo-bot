# رابط Store API: بعد از خرید

سرویس‌ها، سفارش‌ها و پرداخت‌ها، کیف پول و برنامه زیرمجموعه‌گیری کاربری که وارد شده — فقط مال خود او: سرویس یا سفارش کاربر
دیگر `404` می‌گیرد، انگار هیچ‌وقت نبوده. مسیرها زیر [آدرس پایه](Store-API.md#آدرس-پایه) هستند؛ همه با توکن Bearer کاربر.

## سرویس‌ها

درخواست <code dir="ltr">GET /subscriptions?status=&amp;page=</code> سرویس‌های کاربر را می‌آورد، جدیدترین اول (`status`:
`active`، `expired`، `disabled`، `deleted`؛ هر مقدار دیگری یعنی همه)؛ پاسخ <code dir="ltr">GET /subscriptions/{id}</code>
هم <code dir="ltr">{ "subscription": … }</code> است. هر دو سرویس را همان‌طور نشان می‌دهند که فروشگاه آخرین بار از سرورش
خوانده (`synced_at`؛ فروشگاه هر سرویس فعال را تقریبا هر ۱۵ دقیقه یک بار می‌خواند).

پاسخ `200` به <code dir="ltr">GET /subscriptions/{id}</code>:
```json
{
  "subscription": {
    "id": 9,
    "name": "ali_1",
    "status": "active",
    "is_test": false,
    "claimed_at": null,
    "plan": { "id": 3, "name": "یک ماهه ۵۰ گیگ" },
    "server": { "id": 2, "name": "هلند" },
    "link": "https://sub.example.net/sub/3d9e6b1f0a72",
    "traffic": { "limit_bytes": 107374182400, "used_bytes": 42949672960, "remaining_bytes": 64424509440 },
    "term": { "duration_days": 60, "duration_hours": 1440, "starts_at": "2026-09-20T10:00:00+00:00", "expires_at": "2026-11-19T10:00:00+00:00", "awaits_first_use": false },
    "ended_at": null,
    "removes_at": null,
    "auto_renew": { "on": true, "offered": true, "days_before": 2 },
    "renewable": true,
    "picks_plan": false,
    "renewal_window": { "open": true, "opens_at": null, "days_before": null, "traffic_percent": null },
    "devices": 2,
    "extras": { "traffic": true, "time": true, "devices": true },
    "link_rotation": true,
    "next_period": { "ends_at": "2026-10-20T10:00:00+00:00", "bytes": 53687091200 },
    "next_devices": null,
    "presence": null,
    "synced_at": "2026-10-08T09:30:12+00:00",
    "created_at": "2026-09-20T09:58:40+00:00"
  }
}
```

| فیلد | معنا |
|---|---|
| `name` | نامش روی سرور (`ali_1`، `USER_7`) — همان چیزی که کاربر به پشتیبانی می‌گوید |
| `status` | `active` فعال (یا منتظر اولین اتصال)؛ `expired` زمان یا حجمش تمام شده؛ `disabled` پشتیبانی خاموشش کرده؛ `deleted` از سرورش حذف شده |
| `is_test` | اکانت تست رایگانی که کاربر در ربات گرفته ([اکانت‌های تست](Test-Accounts.md)): بدون پلن، `renewable` و `picks_plan` برابر false، همه `extras` برابر false، `auto_renew.offered` برابر false (فیلد هست) — و وقتی تمام شد، یا اگر هیچ‌وقت وصل نشود، فروشگاه ممکن است بی‌صدا حذفش کند (`removes_at`) |
| `claimed_at` | زمانی که کاربر آن را با لینکش به حسابش اضافه کرد ([افزودن سرویس با لینک](#افزودن-سرویس-با-لینک)): سرویسی که پشتیبانی دستی روی سرور ساخته. برای بقیه سرویس‌ها `null` |
| `plan` | پلنی که سرویس با آن فروخته شده یا آخرین بار با آن تمدید شده؛ برای تست رایگان، و برای سرویسی که با لینک اضافه شده یا کاربر خودش ساخته تا وقتی روی یک پلن تمدید نشود، `null` |
| `server` | جایی که سرویس روی آن است («لوکیشن») |
| `link` | تنها لینک اشتراکی که کاربر به برنامه‌اش اضافه می‌کند — آن را با دکمه کپی و کد QR که سایت می‌سازد نشان دهید؛ بعد از `deleted` شدن `null` |
| `traffic` | `limit_bytes` (`0` نامحدود)، `used_bytes`، `remaining_bytes` (برای نامحدود `null`) |
| `term` | `duration_hours` مدت دقیق به ساعت (`0` هیچ‌وقت تمام نمی‌شود — تست یک‌ساعته `1` است و یک ماه `720`)، `duration_days` همان مدت به روز کامل، رو به بالا گرد شده (برای سایت‌هایی که پیش از `duration_hours` ساخته شده‌اند نگه داشته شده)، `starts_at` (اولین اتصال)، `expires_at`، `awaits_first_use` |
| `ended_at` | زمان تمام شدن — مهلتی که از آن گذشت، وگرنه وقتی سرورش گفت حجمش تمام شده یا سرویس حذف شده؛ تا وقتی فعال است `null` (تمدید یا خرید اضافه‌ای که آن را برگرداند این فیلد را پاک می‌کند) |
| `removes_at` | زمانی که فروشگاه خودش آن را از سرورش و از فروشگاه حذف می‌کند: سرویس تمام‌شده تا وقتی حذف خودکار فروشگاه روشن است، و تست رایگان طبق قاعده‌های فروشگاه برای تست؛ اگر حذف نمی‌کند `null`. آن را روی سرویس تمام‌شده نشان دهید — «پیش از … تمدید کنید تا بماند» — و وقتی سرویس حذف شد (`404`) آن را از صفحه‌هایتان بردارید. زمانی که گذشته یعنی در بررسی بعدی فروشگاه (هر ۱۵ دقیقه) حذف می‌شود؛ سفارش بازی که درباره این سرویس باشد حذف را عقب می‌اندازد |
| `auto_renew` | `on` کلید کاربر، `offered` اینکه اصلا می‌شود روشنش کرد، `days_before` چند روز پیش از پایان، کیف پول آن را تمدید می‌کند — قاعده فروشگاه، یکسان برای همه سرویس‌ها ([تمدید خودکار](#تمدید-خودکار)) |
| `renewable` | الان می‌شود آن را روی پلن خودش تمدید کرد ([تمدید سرویس](Store-API-Buying.md#تمدید-سرویس)): فعال یا تمام‌شده است، پلنش هنوز هست و چیزی تمدید می‌کند — و در فروشگاه نماینده، حجم نماینده برایش کافی است. برای سرویس بدون پلن false |
| `picks_plan` | الان می‌شود آن را روی چیزی که کاربر انتخاب می‌کند تمدید کرد: پلن ندارد (با لینک اضافه شده یا ساخته شده؛ هرگز تست رایگان)، فعال یا تمام‌شده است، و پلنی در حال فروش روی سرورش فروخته می‌شود یا ساخت سرویس دلخواه فروشگاه فعال است — گزینه‌ها را با `GET …/renewal-plans` بگیرید و پلن انتخاب‌شده را با `plan_id` بفرستید ([تمدید سرویس](Store-API-Buying.md#تمدید-سرویس))، یا بسته دلخواه را با `gb` و `days` ([تمدید با بسته دلخواه](Store-API-Buying.md#تمدید-با-بسته-دلخواه)). اگر روی پلن تمدید شود همان پلن را می‌گیرد و از آن به بعد `renewable` ملاک است؛ اگر با بسته دلخواه تمدید شود همچنان `picks_plan` دارد |
| `renewal_window` | اینکه فروشگاه الان اجازه تمدید آن را می‌دهد یا نه («آستانه مجاز تمدید»): `open`، و تا وقتی باز نیست، چیزی که بازش می‌کند — `opens_at`، `days_before` (برای سرویسی که زمانش منتظر اولین اتصال است)، `traffic_percent` — هر کدام زودتر برسد؛ اگر هیچ‌کدام نباشد، پایان سرویس. دکمه تمدید را نگه دارید و بگویید از کی ممکن است ([تمدید سرویس](Store-API-Buying.md#تمدید-سرویس)) |
| `devices` | چند دستگاه می‌توانند هم‌زمان از آن استفاده کنند (محدودیت IP)؛ `0` بدون محدودیت. کاربر اضافه این عدد را تا پایان دوره فعلی بالا می‌برد؛ تمدید محدودیت پلن خودش را می‌آورد — برای سرویس فعالی که با `extend` یا `reset_traffic` تمدید شده بعد از پایان دوره فعلی، وگرنه همان لحظه ([`devices` تمدید](Store-API-Buying.md#تمدید-سرویس)) |
| `extras` | `traffic`، `time` و `devices`: اینکه الان می‌شود برایش حجم اضافه، زمان اضافه و کاربر اضافه خرید یا نه ([حجم، زمان و کاربر اضافه](Store-API-Buying.md#حجم-زمان-و-کاربر-اضافه)) — یعنی فروشگاه آن را می‌فروشد و سرویس می‌تواند آن را بگیرد: حجم تا وقتی سرویس سقف حجم دارد و زمانش تمام نشده، زمان تا وقتی مدت دارد و حجمش تمام نشده، کاربر تا وقتی محدودیت دستگاه دارد، نه زمانش تمام شده نه حجمش، و سرورش این محدودیت را اعمال می‌کند (روی PasarGuard نه) |
| `link_rotation` | الان می‌شود لینکش را عوض کرد ([لینک جدید](#لینک-جدید)): فعال است و سرورش می‌تواند لینک تازه بدهد |
| `next_period` | حجم تمدیدی که پشت دوره فعلی در صف است: زمان پایان آن دوره، و بیشترین حجمی که آن موقع باقی می‌ماند ([تمدید سرویس](Store-API-Buying.md#تمدید-سرویس))؛ اگر نباشد `null` — تمدیدی که حجمش همان لحظه اضافه شده (فروشگاه حجم مصرف‌نشده را منتقل می‌کند، `reset_traffic`) چیزی در صف نمی‌گذارد |
| `next_devices` | محدودیت دستگاه تمدیدی که پشت دوره فعلی در صف است: `from` از کی (پایان آن دوره) و `devices` آن موقع چند دستگاه (`0` بدون محدودیت) — کنار `devices` بنویسید «از … N دستگاه»؛ تا وقتی محدودیت عوض نمی‌شود `null` |
| `presence` | اینکه الان وصل است یا نه — فقط در پاسخ `POST …/refresh`، وگرنه `null` |

**مدت از اولین اتصال شروع می‌شود.** سرویس تازه `awaits_first_use: true` دارد و `starts_at` و `expires_at` آن `null`
است: بنویسید «با اولین اتصال شروع می‌شود — ۳۰ روز» (یا «— ۱ ساعت» برای سرویس پلن ساعتی: مدت را از `duration_hours`
بنویسید). بعد از اولین اتصال، `expires_at` زمان پایان آن است.

## خواندن لحظه‌ای سرویس

درخواست `POST /subscriptions/{id}/refresh` (بدون بدنه) همین حالا سرویس را از سرورش می‌خواند و آن را با `presence`
برمی‌گرداند، مثلا <code dir="ltr">"presence": { "online": true, "last_online_at": "2026-10-08T09:41:02+00:00" }</code>
(اگر سرور نتواند بگوید، `online` برابر `null` است). سرویسی که سرور دیگر ندارد با وضعیت `deleted` و `link` برابر `null`
برمی‌گردد. پاسخ `502` با `اطلاعات این سرویس الان از سرور خوانده نشد؛ کمی بعد دوباره تلاش کنید.` یعنی سرور همین حالا
خوانده نمی‌شود — در دسترس نیست، یا بعد از یک خطا چند دقیقه کنار گذاشته شده: همان نسخه‌ای را که دارید با `synced_at` آن
نشان دهید. آن را وقتی صفحه سرویس باز می‌شود یا با یک دکمه صدا بزنید — نه در یک حلقه: هر کاربر حداکثر ۱۰ درخواست از این
نوع در دقیقه دارد، که درخواست ردشده یا ناموفق هم شمرده می‌شود، و بعد `429`
(`اطلاعات سرویس را زیاد به‌روز کرده‌اید؛ …`).

## تمدید خودکار

پاسخ <code dir="ltr">PATCH /subscriptions/{id}</code> با <code dir="ltr">{ "auto_renew": true }</code> یا `false` (یک
boolean در JSON) همان <code dir="ltr">{ "subscription": … }</code> است. این کلید فقط وقتی ارائه می‌شود
(`auto_renew.offered`) که سرویس فعال باشد، روزی تمام شود، هنوز پلنش را داشته باشد — پلنی که مدتش دست‌کم همان
`days_before` باشد که تمدید در آن انجام می‌شود: پلن چندساعته نه —، و فروشگاه پرداخت با کیف پول را با قیمت تمدید کاربر
بپذیرد: یعنی مبلغ بین کمترین و بیشترین مبلغ کیف پول باشد (سرویسی که کیف پول تمدیدش را نمی‌پذیرد دستی تمدید می‌شود و
پایانش یادآوری می‌شود) — و تا وقتی آن تمدید سرویس را تا ۲۸ دی ۱۴۱۶ (۱۷ ژانویه ۲۰۳۸) تمام کند، آخرین روزی که تاریخ‌های
فروشگاه جا می‌دهند (به سرویسی که دیرتر تمام می‌شود این کلید داده نمی‌شود و پایانش به کاربر یادآوری می‌شود). سرویس بدون
پلن — که با لینک اضافه شده، یا ساخته شده و با بسته‌های دلخواه تمدید شده — تا وقتی تمدید روی یک پلن، پلنی به آن ندهد
هیچ‌وقت خودکار تمدید نمی‌شود. تا وقتی ارائه نمی‌شود، کلید به هیچ طرف عوض نمی‌شود — خاموش کردنش هم رد می‌شود: `422` روی
`auto_renew` (`تمدید خودکار برای این سرویس در دسترس نیست.`). هر چیزی جز boolean هم روی همین فیلد `422` می‌گیرد. وقتی
روشن است، فروشگاه سرویس را `auto_renew.days_before` روز پیش از پایانش با کیف پول تمدید می‌کند، روی پلن خودش و با قیمت
همان پلن. کاربر خبردار می‌شود: `auto_renewed`، `auto_renew_short` (موجودی کیف پول کافی نیست — یک بار گفته می‌شود و تا
وقتی کافی شود دوباره امتحان می‌شود)، یا `renewal_failed`.

## لینک جدید

درخواست `POST /subscriptions/{id}/rotate-link` (بدون بدنه) به سرویس لینک تازه‌ای می‌دهد و آن را برمی‌گرداند؛ همه
دستگاه‌هایی که با لینک قبلی وصل‌اند قطع می‌شوند — اول از کاربر تایید بگیرید. تا وقتی `link_rotation` برابر true است این
گزینه را نشان دهید. خطاها: `422` روی `status` (`لینک فقط برای سرویس فعال عوض می‌شود.`،
`سرور این سرویس تغییر لینک را پشتیبانی نمی‌کند.`)؛ `409` با
`این سرویس همین حالا در حال تغییر است؛ چند لحظه بعد دوباره تلاش کنید.` — کمی بعد دوباره امتحان کنید؛ `502`
(`لینک این سرویس عوض نشد: …`، زیر `errors.panel` هم) وقتی سرورش نتوانست — پیش از نشان دادن لینک، سرویس را دوباره
بخوانید؛ `429` بعد از ۵ درخواست در ساعت، که درخواست‌های ردشده و ناموفق هم شمرده می‌شوند
(`لینک سرویس را زیاد عوض کرده‌اید؛ …`). ربات لینک تازه را اعلام نمی‌کند.

## انتقال سرویس به کاربر دیگر

«انتقال سرویس»: کاربر یکی از سرویس‌هایش را رایگان به کاربر دیگری از فروشگاه می‌دهد که با شناسه عددی تلگرامش پیدا می‌شود —
مثل ربات. تا وقتی `shop.service_transfers` در <code dir="ltr">GET /</code> برابر true است این گزینه را نشان دهید
([آنچه سایت اول می‌پرسد](Store-API-Shop.md#آنچه-سایت-اول-می‌پرسد)): در هر فروشگاهی خاموش است تا مدیر فروشگاه روشنش کند.
گیرنده باید دست‌کم یک بار ربات را استارت کرده باشد.

1. **به چه کسی می‌رسد** — `GET /subscriptions/{id}/transfer?telegram_id=7070` با `200` و
   <code dir="ltr">{ "recipient": { "name": "Sara", "username": "sara" } }</code> جواب می‌دهد (هر کدام ممکن است `null`
   باشد): آن را نشان دهید و از کاربر تایید بگیرید. چیزی عوض نمی‌شود.
2. **انتقال** — `POST /subscriptions/{id}/transfer` با `{ "telegram_id": "7070" }` (یک عدد، یا رقم‌هایش همان‌طور که تایپ
   شده؛ رقم فارسی هم خوانده می‌شود)، با ورود تازه ([ورود تازه](Store-API-Account.md#ورود-تازه): توکنی که لو رفته نمی‌تواند
   سرویسی را بدهد؛ پاسخ `403` یعنی اول `POST /me/reauthenticate` لازم است)، با `200` و همان `recipient` جواب می‌دهد. سرویس
   از این لحظه مال گیرنده است: <code dir="ltr">GET /subscriptions/{id}</code> برای کاربر بعد از آن `404` می‌دهد، پس آن را
   از صفحه بردارید. لینک، پایان و حجمش را نگه می‌دارد، و `name` آن روی سرور هم عوض نمی‌شود — با الگوی پیش‌فرض فروشگاه،
   یوزرنیم تلگرام دهنده و یک عدد (`ali_1`)، و با `{tg_id}` شناسه دهنده
   ([نام کاربری سرویس](Bot-Settings.md#نام-کاربری-سرویس)): نام کلاینت روی سرورش عوض نمی‌شود. «تمدید خودکار» آن خاموش
   می‌شود. گیرنده در ربات و در اعلان‌هایش خبردار می‌شود (`service_received`)؛ خود کاربر نه — پاسخ همین درخواست خبر اوست.
   گروه گزارش‌ها از هر انتقال خبردار می‌شود.

لینک همراه سرویس می‌رود، پس دستگاه‌های دهنده تا وقتی گیرنده لینک را عوض نکند وصل می‌مانند ([لینک جدید](#لینک-جدید)): پیش
از تایید این را به دهنده بگویید. جایی که سرور می‌تواند لینک را عوض کند (`link_rotation`)، اعلان گیرنده این را می‌گوید.

همه ردها `422` هستند، با پیام‌هایی که باید همان‌طور نشان داده شوند:

| زیر | کی |
|---|---|
| `errors.status` | فروشگاه الان این امکان را ندارد (`انتقال سرویس در این فروشگاه فعال نیست.`)؛ تست رایگان؛ سرویسی که از سرورش حذف شده؛ سرویسی با سفارش باز از طرف کاربر — تمدید یا خرید اضافه‌ای که منتظر پرداخت یا رسید است، یا در حال تحویل است (`سفارشی از این سرویس هنوز باز است …`؛ سفارش پرداخت‌نشده بعد از ۴۸ ساعت خودش کنار می‌رود)؛ سرویسی که تحویل یکی از سفارش‌هایش ناموفق بوده و پشتیبانی باید به آن رسیدگی کند — با تلاش دوباره یا برگرداندن پول (`تحویل سفارشی از این سرویس ناموفق بوده و منتظر پشتیبانی است؛ …`) |
| `errors.telegram_id` | عدد نیست (`شناسه عددی تلگرام را وارد کنید: …`)؛ هیچ کاربری از این فروشگاه این شناسه را ندارد (`مشتری‌ای با این شناسه تلگرام در این فروشگاه نیست؛ …`)؛ خود کاربر است؛ حساب مسدود است |

هر `GET` — و هر `POST`، که گیرنده را دوباره پیدا می‌کند — شمرده می‌شود: حداکثر ۱۰ بار در ۱۰ دقیقه برای هر کاربر، همراه با
درخواست‌های [انتقال موجودی](#انتقال-موجودی-به-کاربر-دیگر)؛ و حداکثر ۵ انتقال سرویس در ساعت. بیشتر از هر کدام، `429` با
`Retry-After`. سرویس کاربر دیگر مثل همه جا `404` می‌گیرد.

## افزودن سرویس با لینک

«افزودن سرویس با لینک» ([افزودن سرویس با لینک](Service-Claims.md)): کاربر سرویسی را که پشتیبانی دستی روی یک سرور ساخته با
فرستادن لینکش به حسابش اضافه می‌کند — مثل ربات. تا وقتی `shop.service_claims` در <code dir="ltr">GET /</code> برابر true
است این گزینه را نشان دهید ([آنچه سایت اول می‌پرسد](Store-API-Shop.md#آنچه-سایت-اول-می‌پرسد)): فقط در فروشگاه اصلی، و
خاموش تا مدیرش روشنش کند.

درخواست `POST /subscriptions/claim`:
```json
{ "link": "سرویسم این است: https://sub.example.net/sub/5b7d2c9e1f04" }
```

فیلد `link` همان متنی است که کاربر چسبانده، تا ۲۰۰۰ کاراکتر: یک لینک اشتراک (<code dir="ltr">https://…/sub/…</code>، با هر
دامنه‌ای) یا یکی از کانفیگ‌های سرویس (<code dir="ltr">vless://</code>، <code dir="ltr">vmess://</code>،
<code dir="ltr">trojan://</code>، <code dir="ltr">ss://</code>، <code dir="ltr">hysteria2://</code> یا
<code dir="ltr">hy2://</code>، <code dir="ltr">tuic://</code>)، تنها یا لابه‌لای متن دیگر. لینک‌های متن با هم خوانده
می‌شوند، حداکثر پنج تا.

پاسخ `201` با <code dir="ltr">{ "subscription": … }</code> است، سرویس به همان شکلی که در [سرویس‌ها](#سرویس‌ها) آمده: با
`claimed_at` پرشده و `plan` برابر `null`. اولین کاربری که لینک را بفرستد سرویس را می‌گیرد؛ گروه گزارش‌ها از هر افزودن
خبردار می‌شود. `Idempotency-Key` نمی‌گیرد: اگر دوباره فرستاده شود، با این دلیل که از قبل مال خود کاربر است رد می‌شود.

همه ردها زیر `errors.link` هستند، با پیام‌هایی که باید همان‌طور نشان داده شوند:

| وضعیت | کی |
|---|---|
| `422` | فروشگاه الان سرویسی نمی‌پذیرد (`افزودن سرویس با لینک فعلا فعال نیست.`)؛ لینکی در متن نیست، یا متن بیش از حد بلند است؛ هیچ‌کدام از سرورها آن را ندارند؛ از قبل مال خود کاربر است؛ سرورش برای آن لینک اشتراک نمی‌دهد |
| `409` | در حساب کاربر دیگری است (`… اگر سرویس شماست با پشتیبانی تماس بگیرید.`) |
| `502` | سروری که ممکن است آن را داشته باشد پاسخ نداد — کمی بعد دوباره امتحان کنید |
| `429` | بیش از ۱۰ لینک در ۱۰ دقیقه، با `Retry-After`: هر لینک از همه سرورها پرسیده می‌شود |

سرویسی که این‌طور اضافه شده پلن ندارد: اولین تمدیدش روی پلنی است که کاربر انتخاب می‌کند (`picks_plan`،
[تمدید سرویس](Store-API-Buying.md#تمدید-سرویس)) و بعد همان پلن، پلن سرویس می‌شود. تا آن موقع، حجم، زمان و کاربر اضافه با
قیمت‌های خود فروشگاه برایش فروخته می‌شوند، اگر فروشگاه آن‌ها را بفروشد.

## سفارش‌ها و پرداخت‌ها

درخواست <code dir="ltr">GET /orders?status=&amp;type=&amp;page=</code> سفارش‌های کاربر را می‌آورد، جدیدترین اول، هر کدام
با پرداخت‌هایش (جدیدترین اول) — با همان شکل سفارش در [پاسخ درخواست سفارش](Store-API-Buying.md#پاسخ-درخواست-سفارش).
`status` و `type` فهرست را به یکی از مقدارهای زیر محدود می‌کنند؛ هر مقدار دیگری یعنی همه. پاسخ
<code dir="ltr">GET /orders/{id}</code> هم <code dir="ltr">{ "order": … }</code> است. `subscription` سفارش سرویسی است که
سفارش تحویل داده، تمدید می‌کند یا خرید اضافه را به آن می‌دهد، به شکل `{ id, name }` — با نامش روی سرور، همان‌طور که تیکت
سرویسش را نام می‌برد ([فهرست تیکت‌ها](Store-API-Support-Tickets.md#فهرست-تیکت‌ها)): برای خرید بعد از تحویل، برای تمدید و
خرید اضافه از همان اول؛ اگر نباشد، یا بعد از حذف آن سرویس، `null`. آن را به <code dir="ltr">GET /subscriptions/{id}</code>
لینک کنید. `package_name` چیزی است که خرید یا تمدید می‌خرد، به زبان ساده — نام پلن، یا برای سرویسی که کاربر ساخته
«سرویس دلخواه · ۵۰ گیگ · ۳۰ روز» —، و برای بقیه `null`. `traffic_bytes`، `days` و `devices` چیزی هستند که سفارش خرید
اضافه به سرویسش می‌دهد — حجم اضافه به بایت، زمان اضافه به روز، کاربر اضافه — یا مشخصات خود سرویس ساخته‌شده، و برای بقیه
`null` (سفارش `traffic` نماینده هم حجمش را در `traffic_bytes` می‌گوید).

| `type` | |
|---|---|
| `purchase` | سرویس تازه |
| `renewal` | تمدید یک سرویس (`subscription` همان سرویس است و `server` جایی که روی آن است) |
| `extra_traffic` | حجم اضافه برای یک سرویس (`traffic_bytes`؛ `subscription` همان سرویس است، `plan` پلن آن و `server` جایی که روی آن است) |
| `extra_time` | زمان اضافه برای یک سرویس (`days`؛ `subscription`، `plan` و `server` مثل حجم اضافه) |
| `extra_devices` | کاربر اضافه برای یک سرویس (`devices`؛ `subscription`، `plan` و `server` مثل حجم اضافه) |
| `wallet_topup` | شارژ کیف پول (`plan`، `server` و `subscription` برابر `null`) |
| `traffic` | حجمی که نماینده برای ربات خودش در ربات خریده |

| `status` سفارش | |
|---|---|
| `pending` | منتظر پرداخت — رسید کارت به کارت هنوز نیامده، رد شده یا نزد پشتیبانی است؛ یا صفحه پرداخت درگاه آنلاین باز است (پرداخت سفارش می‌گوید کدام) |
| `paid` | پرداخت شده؛ تحویل شروع نشده |
| `processing` | پرداخت شده؛ در حال تحویل |
| `fulfilled` | تحویل شده (`fulfilled_at`؛ `subscription` سرویسی که تحویل یا تمدید شده یا خرید اضافه گرفته) |
| `failed` | پرداخت شده ولی تحویل نشده — `failure` دلیلش را می‌گوید: `delivery` (پشتیبانی تحویلش می‌دهد)، `first_purchase_used` یا `service_changed_hands` (هیچ‌وقت تحویل نمی‌شود: پشتیبانی پرداخت را با کاربر تسویه می‌کند) — [چرا سفارش ناموفق شد](Store-API-Buying.md#چرا-سفارش-ناموفق-شد) |
| `cancelled` | پشتیبانی لغوش کرده، یا ۴۸ ساعت پرداخت‌نشده مانده |
| `refunded` | پول برگشته — پول خرید، تمدید یا خرید اضافه به کیف پول، و پول شارژی که تحویل شده بود دوباره از کیف پول بیرون |

| `status` پرداخت | |
|---|---|
| `pending` | کارت به کارتی که منتظر رسید است، یا پرداخت آنلاینی که منتظر جواب درگاه است (`link`: صفحه پرداخت، تا وقتی پول می‌گیرد — [پرداخت آنلاین](Store-API-Buying.md#پرداخت-آنلاین)) |
| `awaiting_review` | رسیدش نزد پشتیبانی است (`receipt.sent_at`) |
| `paid` | پذیرفته شده (`paid_at`) |
| `failed` | رسیدش رد شده، پرداخت پذیرفته نشده، یا صفحه پرداخت آنلاین بدون پرداخت بسته شده |
| `cancelled` | پشتیبانی لغوش کرده، سفارش منقضی شده، سفارش با روش دیگری پرداخت شده، یا سرویسش به کاربر دیگری منتقل شده |
| `refunded` | برگردانده شده |

فیلد `note` پرداخت توضیح آخرین تصمیم درباره آن است، برای کاربر: دلیل رد از طرف پشتیبانی، یادداشت پشتیبانی برای لغو یا
بازپرداخت، یا توضیح خود فروشگاه (`سفارش با روش دیگری پرداخت شد`، `پرداخت در مهلت کامل نشد`،
`سرویس این سفارش به حساب دیگری منتقل شد`، `مهلت پرداخت در درگاه تمام شد`،
`سفارش پیش از رسیدن این پرداخت بسته شده بود؛ مبلغ به کیف پول مشتری رفت`، و برای پرداخت آنلاینی که
[برای پشتیبانی نگه داشته شده](Store-API-Buying.md#پرداخت-نگه-داشته-شده-برای-پشتیبانی)، در هر وضعیتی،
`پرداخت سفارش #53 برای بررسی به پشتیبانی رسیده است؛ …` به جای توضیحی که فروشگاه برای پشتیبانی درباره دلیلش می‌نویسد). آن را
زیر پرداخت نشان دهید. یادداشت‌های داخلی پشتیبانی روی سفارش هیچ‌وقت در API نمی‌آیند: `failure` سفارش `failed` دلیلش را در
یک کلمه می‌گوید.

## کیف پول

پاسخ `200` به `GET /wallet`:
```json
{
  "balance": "380000.00",
  "credit": "0.00",
  "spendable": "380000.00",
  "top_up": { "min": "10000.00", "max": "500000000.00", "presets": ["50000.00", "100000.00", "200000.00", "500000.00"], "random": ["73000.00", "128000.00"] },
  "transfer": { "min": "10000.00", "max": "5000000.00", "daily_cap": "10000000.00", "left_today": "9950000.00", "most": "380000.00" }
}
```

فیلد `balance` آخرین خط دفتر تراکنش است؛ `credit` اینکه کیف پول نماینده تا چه حد می‌تواند زیر صفر برود (برای بقیه
`"0.00"`)؛ `spendable` مبلغی که کیف پول الان می‌تواند بپردازد. `top_up` همان چیزی است که «افزایش موجودی» ربات نشان می‌دهد:
کمترین و بیشترین مبلغ شارژ، مبلغ‌هایی که به شکل دکمه نشان داده می‌شوند به ترتیب صعودی، و — اگر فروشگاه بخواهد (به‌طور
پیش‌فرض نه) — مبلغ‌هایی که تصادفی در همان بازه انتخاب شده‌اند، که بعد از مبلغ‌های پیش‌فرض و به ترتیب صعودی می‌آیند و
هیچ‌کدام مبلغ پیش‌فرض نیست؛ هر پاسخ آن‌ها را از نو انتخاب می‌کند. هر کدام را همان‌طور که هست برگردانید
([شارژ کیف پول](Store-API-Buying.md#شارژ-کیف-پول)). `transfer` چیزی است که کاربر می‌تواند برای کاربر دیگری بفرستد
([انتقال موجودی به کاربر دیگر](#انتقال-موجودی-به-کاربر-دیگر))؛ تا وقتی فروشگاه این امکان را ندارد `null`.

پاسخ `200` به <code dir="ltr">GET /wallet/transactions?page=</code>:
```json
{
  "transactions": [
    { "id": 31, "type": "debit", "amount": "120000.00", "balance_after": "380000.00", "description": "پرداخت سفارش #51 (خرید)", "created_at": "2026-10-07T12:00:00+00:00" },
    { "id": 30, "type": "credit", "amount": "500000.00", "balance_after": "500000.00", "description": "شارژ کیف پول (سفارش #50)", "created_at": "2026-10-07T11:40:21+00:00" }
  ],
  "meta": { "page": 1, "per_page": 25, "total": 2, "last_page": 1 }
}
```

جدیدترین خط اول، همان خط‌هایی که «کیف پول» ربات نشان می‌دهد؛ `description` فارسی و آماده نمایش است.

## انتقال موجودی به کاربر دیگر

«انتقال موجودی»: کاربر بدون کارمزد از کیف پولش برای کاربر دیگری از فروشگاه پول می‌فرستد که با شناسه عددی تلگرامش پیدا
می‌شود — مثل ربات ([تنظیمات ربات](Bot-Settings.md#انتقال-موجودی)). تا وقتی `transfer` در `GET /wallet` برابر `null` نیست
این گزینه را نشان دهید: در هر فروشگاهی خاموش است تا مدیر فروشگاه روشنش کند. عددهای آن مبلغ را محدود می‌کنند: از `min` تا
`most` — کمترین مقدار میان `max` فروشگاه، موجودی خود کیف پول (هرگز اعتبار نماینده) و باقی‌مانده سقف روزانه امروز (`left_today`؛
همراه `daily_cap`، که اگر فروشگاه سقفی نگذاشته باشد `null` است، و از نیمه‌شب به وقت فروشگاه شمرده می‌شود). اگر `most`
کمتر از `min` باشد، کاربر الان نمی‌تواند چیزی بفرستد: به جای فرم همین را بگویید — در این حالت گیرنده هم پیدا نمی‌شود:
`GET /wallet/transfer` یک `422` زیر `errors.amount` برمی‌گرداند که دلیلش را می‌گوید.

1. **به چه کسی می‌رسد** — `GET /wallet/transfer?telegram_id=7070` با `200` و
   <code dir="ltr">{ "recipient": { "name": "Sara", "username": "sara" } }</code> جواب می‌دهد (هر کدام ممکن است `null`
   باشد): آن را نشان دهید، بعد مبلغ را بپرسید و برای هر دو تایید بگیرید. چیزی عوض نمی‌شود.
2. **فرستادن** — `POST /wallet/transfer`، با هدر `Idempotency-Key` (یک UUID تازه برای هر انتقالی که کاربر تایید می‌کند)
   و ورود تازه ([ورود تازه](Store-API-Account.md#ورود-تازه): توکنی که لو رفته نمی‌تواند پولی بدهد؛ پاسخ `403` یعنی اول
   `POST /me/reauthenticate` لازم است). پول همان لحظه منتقل می‌شود.

درخواست `POST /wallet/transfer`:
```json
{ "telegram_id": "7070", "amount": "50000" }
```

پاسخ `200` به `POST /wallet/transfer`:
```json
{
  "transfer": { "id": 9, "amount": "50000.00", "recipient": { "name": "Sara", "username": "sara" }, "created_at": "2026-10-14T12:00:00+00:00" },
  "wallet": {
    "balance": "330000.00",
    "credit": "0.00",
    "spendable": "330000.00",
    "top_up": { "min": "10000.00", "max": "500000000.00", "presets": ["50000.00", "100000.00", "200000.00", "500000.00"], "random": [] },
    "transfer": { "min": "10000.00", "max": "5000000.00", "daily_cap": "10000000.00", "left_today": "9950000.00", "most": "330000.00" }
  }
}
```

فیلدهای `telegram_id` و `amount` همان‌طور که کاربر تایپ می‌کند فرستاده می‌شوند (عدد، یا متن با رقم فارسی، جداکننده،
«هزار» و «تومان»: [قراردادها](Store-API.md#قراردادها))، یا `amount` با قالب خود API (`"50000.00"`). `wallet` کیف پول
کاربر است همان‌طور که الان هست. در تاریخچه هر دو کیف پول خطی با نام کاربر دیگر ثبت می‌شود
(<code>انتقال موجودی به Sara (@sara)</code>، <code>دریافت موجودی از Ali (@ali)</code>). گیرنده در ربات و در اعلان‌هایش
خبردار می‌شود (`wallet_received`)، و خود کاربر در اعلان‌هایش و در تلگرام (`wallet_sent`). گروه گزارش‌ها از هر انتقال
خبردار می‌شود.

اگر درخواست با همان `Idempotency-Key` دوباره فرستاده شود — مثلا تلاش دوباره به خاطر شبکه —، پاسخ همان انتقالی است که آن کلید
انجام داده، با کیف پول همان‌طور که الان هست: هیچ‌وقت انتقال دوم انجام نمی‌شود، حتی برای دو درخواست در یک لحظه. همان کلید با
`telegram_id` یا `amount` دیگر `422` زیر `errors.idempotency_key` می‌گیرد
(`این Idempotency-Key پیش‌تر برای انتقال دیگری به کار رفته است.`)، و همین‌طور نبودن کلید یا کلید نادرست.

همه ردها `422` هستند، با پیام‌هایی که باید همان‌طور نشان داده شوند:

| زیر | کی |
|---|---|
| `errors.status` | فروشگاه الان این امکان را ندارد (`انتقال موجودی در این فروشگاه فعال نیست.`) |
| `errors.telegram_id` | عدد نیست (`شناسه عددی تلگرام را وارد کنید: …`)؛ هیچ کاربری از این فروشگاه این شناسه را ندارد (`مشتری‌ای با این شناسه تلگرام در این فروشگاه نیست؛ …`)؛ خود کاربر است؛ حساب مسدود است |
| `errors.amount` | کاربر الان نمی‌تواند چیزی بفرستد، که `GET` هم همین را می‌گوید: موجودی کیف پول کمتر از حداقل است (`برای انتقال، دست‌کم ۱۰٬۰۰۰ تومان موجودی در کیف پول لازم است.`) یا سقف روزانه پر شده (`… امروز پر شده است؛ …`)؛ مبلغ عدد صحیح تومان نیست (`مبلغ را به تومان و بدون اعشار بنویسید.`)؛ کمتر از حداقل (`کمترین مبلغ انتقال ۱۰٬۰۰۰ تومان است.`) یا بیشتر از حداکثر (`بیشترین مبلغ هر انتقال … است.`)؛ بیشتر از موجودی (`موجودی کیف پول شما (…) برای این انتقال کافی نیست.`، و برای نماینده همراه با `اعتبار نمایندگی منتقل نمی‌شود.`)؛ بیشتر از سقف روزانه (`سقف انتقال روزانه … است و امروز تا … دیگر می‌توانید منتقل کنید.`، یا `… امروز پر شده است؛ …`) |

هر `GET` — و هر `POST`، که گیرنده را دوباره پیدا می‌کند — شمرده می‌شود: حداکثر ۱۰ بار در ۱۰ دقیقه برای هر کاربر، همراه با
درخواست‌های [انتقال سرویس](#انتقال-سرویس-به-کاربر-دیگر)؛ و حداکثر ۱۰ انتقال در ساعت. بیشتر از هر کدام، `429` با
`Retry-After`.

## برنامه زیرمجموعه‌گیری

پاسخ `200` به `GET /referral`:
```json
{
  "enabled": true,
  "rate": 10,
  "renewal_rate": 5,
  "first_only": false,
  "start_gift": { "referrer": "20000.00", "invitee": "10000.00", "trigger": "purchase" },
  "reward": { "every": 5, "plan": { "id": 4, "name": "یک‌ماهه" } },
  "code": "k7m2xq9p",
  "bot_link": "https://t.me/amo_shop_bot?start=ref_k7m2xq9p",
  "invited": 3,
  "earned": "36000.00",
  "rewards": 0
}
```

- فیلد `code` — کد دعوت کاربر، که اولین باری که خواسته شود ساخته می‌شود، چه برنامه روشن باشد چه نه.
- فیلد `bot_link` — لینک دعوت ربات با همین کد؛ تا وقتی @username ربات معلوم نیست `null`.
- لینک دعوت خود سایت را خودتان بسازید — `https://shop.example.com/?ref=k7m2xq9p` — و آن را اجرا کنید: کدی را که
  بازدیدکننده با آن می‌آید نگه دارید و هنگام ورودش با نام `referral_code` بفرستید
  ([کدهای دعوت در ثبت‌نام](Store-API-Sign-In.md#کدهای-دعوت-در-ثبت‌نام)).
- فیلد `invited` — کاربرانی که با کد او آمده‌اند؛ `earned` — درآمدی که از آن‌ها گرفته، به تومان.
- تا وقتی `enabled` است، هر پرداخت کاربر معرفی‌شده که پول تازه وارد می‌کند — کارت به کارت، برای هر چیزی؛ نه پرداخت با
  کیف پول — `rate` درصد (تومان کامل، رو به پایین گرد شده) به کیف پول معرف می‌ریزد — برای تمدید، به جای آن `renewal_rate`
  (۰: تمدید چیزی نمی‌آورد) —؛ با `first_only`، فقط از اولین پرداخت آن کاربر. فقط یک سطح: زیرمجموعه‌های یک زیرمجموعه چیزی
  برای معرف نمی‌آورند. برگرداندن شارژ کیف پول (که پولش از فروشگاه بیرون می‌رود) پورسانتش را از کیف پول معرف پس می‌گیرد
  (اعلان `referral_commission_back`)؛ بازپرداخت خرید، تمدید یا خرید اضافه، که پولش به شکل موجودی کیف پول در فروشگاه
  می‌ماند، به پورسانت دست نمی‌زند.
- فیلد `start_gift` («هدیه شروع»، تا وقتی نیست `null`) — مبلغی به تومان به کیف پول معرف (`referrer`) و به کیف پول خود
  تازه‌وارد (`invitee`)، برای هر تازه‌وارد یک بار: وقتی عضو می‌شود (`trigger` برابر `join`) یا وقتی اولین خریدش پرداخت
  می‌شود (`purchase` — با هر روش پرداختی؛ سرویسی که رایگان داده شده خرید حساب نمی‌شود). هر دو خبردار می‌شوند (اعلان‌های
  `referral_start_gift`).
- فیلد `reward` («جایزه دعوت»، تا وقتی نیست `null`) — هر بار که `every` نفر دیگر از تازه‌واردهایی که با کد او آمده‌اند
  خرید کنند (خرید با قیمت، که بعدا بازپرداخت نشده)، یک سرویس از `plan` رایگان به او داده می‌شود (اعلان `referral_reward`،
  و بعد خود سرویس مثل هر سفارشی)؛ `rewards` — چند بار جایزه گرفته.
- تا وقتی هشداری روی زیرمجموعه‌هایش هست — هشدار پشتیبانی، وقتی ساختگی به نظر می‌رسند —، هیچ هدیه شروع و جایزه‌ای داده
  نمی‌شود، و آنچه در این مدت داده نشده بعدا هم داده نمی‌شود؛ پورسانت‌ها مثل همیشه‌اند.

## کدهای هدیه

هر «کد هدیه» یا مبلغی به تومان در کیف پول است یا سرویس رایگانی از یک پلن، و فقط یک بار گرفته می‌شود — به دست یک کاربر از
فروشگاه، چه از «🎁 کد هدیه» ربات و چه از وب‌سایت ([کدهای هدیه](Gift-Codes-And-Lucky-Wheel.md#کدهای-هدیه)).

درخواست `POST /gift-codes/redeem` با `{ "code": "nowruz-7k3m 9qxapt" }` و پاسخ `200`:
```json
{
  "gift": {
    "kind": "wallet",
    "words": "۵۰٬۰۰۰ تومان شارژ کیف پول",
    "balance": "430000.00",
    "order": null,
    "subscription": null
  }
}
```

- کد را همان‌طور که کاربر تایپ کرده بفرستید: حروف بزرگ و کوچک فرقی ندارند، خط تیره و فاصله هر جا باشد اشکالی ندارد، رقم
  فارسی هم — فروشگاه آن را به شکلی که نگه می‌دارد می‌خواند (حروف بزرگ لاتین و رقم).
- فیلد `words` چیزی است که کد داده، آماده نمایش. کد کیف پول `balance` را برمی‌گرداند، یعنی موجودی کیف پول بعد از شارژ؛
  کد پلن `order` را برمی‌گرداند، سفارشی که سرویسش با آن داده شده — `fulfilled`، یا `failed` و منتظر تلاش دوباره پشتیبانی،
  مثل هر سفارشی — و بعد از تحویل، `subscription` آن را ([سرویس‌ها](#سرویس‌ها))؛ در این حالت `balance` برابر `null` است.
  چیزی در تلگرام فرستاده نمی‌شود: سایت شما نتیجه را نشان می‌دهد.
- در صورت رد، `422` با دلیل زیر `code`، به زبان کاربر: فروشگاه الان کدی نمی‌پذیرد (کلیدش خاموش است)، چنین کدی نیست، کد
  گرفته شده — به دست همین کاربر یا کاربر دیگر —، از آخرین روزش گذشته، یا سرویسش همین حالا تحویل‌دادنی نیست (هیچ سروری پلن
  را تحویل نمی‌دهد: کد برای امتحان دوباره بعدا مال کاربر می‌ماند).
- هر تلاشی که کد هیچ‌کدام از کدهای فروشگاه نباشد به حساب کاربر و شبکه‌ای که از آن آمده شمرده می‌شود: ۱۰ کد اشتباه در ساعت
  برای هر کاربر، ۳۰ برای هر شبکه، و بعد `429` که `Retry-After` آن مدت انتظار را می‌گوید — تا کدها حدس زده نشوند.
