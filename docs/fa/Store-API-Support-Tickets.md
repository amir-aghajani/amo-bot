# رابط Store API: تیکت‌های پشتیبانی

تیکت یک گفتگو با پشتیبانی است: یک موضوع، سرویسی که تیکت درباره آن است (یا هیچ)، و پیام‌ها — پیام‌های کاربر و
پشتیبانی، هر کدام یک متن و حداکثر یک تصویر، و حداکثر ۲۰۰ پیام در هر تیکت. کاربر در وب‌سایت یا در ربات تیکت باز می‌کند و
در آن می‌نویسد، و هر دو همان تیکت‌ها را نشان می‌دهند. پشتیبانی از هر کدام از دو پنل، گروه تلگرام فروشگاه یا بخش مدیریت
وب‌سایت ([مدیران سایت](Store-API-Admins.md)) پاسخ می‌دهد؛ طرف کاربر لازم نیست بداند از کدام. مسیرها زیر
[آدرس پایه](Store-API.md#آدرس-پایه) هستند؛ همه با توکن Bearer کاربر، و تیکت کاربر دیگر `404` می‌گیرد، انگار هیچ‌وقت
نبوده.

## فهرست تیکت‌ها

پاسخ `200` به <code dir="ltr">GET /tickets?status=&amp;page=</code>:
```json
{
  "tickets": [
    {
      "id": 12,
      "subject": "قطعی اتصال",
      "status": "answered",
      "subscription": { "id": 9, "name": "ali_1" },
      "last_message_at": "2026-10-08T10:40:00+00:00",
      "unread": true,
      "rating": null,
      "created_at": "2026-10-08T10:15:00+00:00",
      "closed_at": null
    },
    {
      "id": 7,
      "subject": "سوال درباره تمدید خودکار",
      "status": "closed",
      "subscription": null,
      "last_message_at": "2026-10-02T18:20:00+00:00",
      "unread": false,
      "rating": 5,
      "created_at": "2026-10-02T17:55:00+00:00",
      "closed_at": "2026-10-02T18:20:00+00:00"
    }
  ],
  "meta": { "page": 1, "per_page": 25, "total": 2, "last_page": 1, "unread": 1 }
}
```

تازه‌ترین فعالیت اول؛ `status` فهرست را به یک وضعیت محدود می‌کند و هر مقدار دیگری یعنی همه. `meta.unread` تعداد همه
تیکت‌های اوست که پیام پشتیبانی در آن‌ها خوانده نشده، هر صفحه یا `status`ی که نشان داده شود — عدد کنار لینک پشتیبانی.

| فیلد | معنا |
|---|---|
| `status` | `open` منتظر پشتیبانی؛ `answered` آخرین پیام را پشتیبانی نوشته و منتظر کاربر است؛ `closed` |
| `subscription` | سرویسی که تیکت درباره آن است، با نامش روی سرور ([سرویس‌ها](Store-API-After-Buying.md#سرویس‌ها))؛ `null` اگر نباشد یا بعدا حذف شده باشد |
| `last_message_at` | آخرین پیام آن — ترتیب فهرست با همین است |
| `unread` | پشتیبانی بعد از آخرین باری که کاربر تیکت را خوانده چیزی نوشته — سایت خواندن را خبر داده باشد (`POST /tickets/{id}/read`، [گفتگو](#گفتگو)) یا ربات تیکت را به او نشان داده باشد: ردیف را مشخص کنید |
| `rating` | امتیاز ۱ تا ۵ کاربر، بعد از بسته شدن؛ اگر نباشد `null` |
| `closed_at` | زمان بسته شدن؛ تا بسته نشده `null` |

چه چیزی وضعیت را عوض می‌کند: پیام کاربر آن را `open` می‌کند — تیکت بسته را هم؛ پاسخ پشتیبانی آن را `answered` می‌کند،
تیکت بسته را هم؛ هر دو طرف می‌توانند آن را ببندند. پشتیبانی می‌تواند تیکت بسته را دوباره باز کند (`open`)، بی‌آنکه به کاربر
خبر دهد. تیکتی که دوباره باز شود، از هر راهی، `closed_at`، `rating` و `rating_note` قبلی‌اش را از دست می‌دهد.

## باز کردن تیکت

درخواست `POST /tickets`:
```json
{ "subject": "قطعی اتصال", "body": "از دیشب سرویس ali_1 وصل نمی‌شود.\nروی دو گوشی امتحان کردم.", "subscription_id": 9 }
```

پاسخ `201` به `POST /tickets`:
```json
{
  "ticket": {
    "id": 12,
    "subject": "قطعی اتصال",
    "status": "open",
    "subscription": { "id": 9, "name": "ali_1" },
    "last_message_at": "2026-10-08T10:15:00+00:00",
    "unread": false,
    "rating": null,
    "created_at": "2026-10-08T10:15:00+00:00",
    "closed_at": null,
    "rating_note": null,
    "messages": [
      { "id": 31, "author": "customer", "body": "از دیشب سرویس ali_1 وصل نمی‌شود.\nروی دو گوشی امتحان کردم.", "attachment": null, "created_at": "2026-10-08T10:15:00+00:00" }
    ]
  }
}
```

پاسخ، تیکت با گفتگوی آن است، همان‌طور که <code dir="ltr">GET /tickets/{id}</code> برمی‌گرداند ([گفتگو](#گفتگو))؛ گروه
تلگرام فروشگاه حدودا ظرف یک دقیقه خبردار می‌شود. برای فرستادن تصویر، همان فیلدها را به شکل فرم بفرستید و تصویر را با نام
`file` — فرمی بدون `file` هم مثل JSON تیکتی بدون تصویر باز می‌کند:

```ts
const form = new FormData()
form.append('subject', subject)
form.append('body', body)
if (serviceId) form.append('subscription_id', String(serviceId))
if (file) form.append('file', file) // a JPEG, PNG or WebP picture, 10 MB at most
const { ticket } = await store<S['StoreTicketResponse']>('/tickets', { method: 'POST', form })
```

| فیلد | قاعده |
|---|---|
| `subject` | ۳ تا ۱۲۰ کاراکتر |
| `body` | ۱ تا ۴۰۰۰ کاراکتر، با همان شکستگی خط‌ها — با تصویر هم متن لازم است |
| `subscription_id` | یکی از سرویس‌های کاربر (`GET /subscriptions`، در هر وضعیتی)؛ برای هیچ، نفرستید یا `null` یا `""` بفرستید |
| `file` | فقط در فرم، اختیاری: یک تصویر JPEG، PNG یا WebP (با محتوای فایل سنجیده می‌شود)، حداکثر ۱۰ مگابایت (HEIC آیفون اول تبدیل می‌شود، و تصویر همان‌طور که فروشگاه دوباره می‌نویسدش نگه داشته می‌شود: [رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید)) |

همه خطاها با هم می‌آیند:

پاسخ `422` به `POST /tickets`:
```json
{
  "message": "اطلاعات واردشده معتبر نیست.",
  "errors": {
    "subject": ["موضوع حداقل 3 کاراکتر است."],
    "file": ["تصویر باید JPG، PNG یا WebP باشد."]
  },
  "request_id": "9b2d4e6f8a0c1e3f"
}
```

خطاهای دیگر: `موضوع تیکت را بنویسید.`، `موضوع حداکثر 120 کاراکتر است.`، `متن پیام را بنویسید.`،
`پیام حداکثر 4000 کاراکتر است.`، `این سرویس پیدا نشد.` (سرویس مال او نیست)،
`حجم تصویر حداکثر ۱۰ مگابایت می‌تواند باشد.` — و محدودیت‌های خود هاست، مثل رسید
([رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید)). بعد سقف‌های [محدودیت‌ها](#محدودیت‌ها) (`429`). فرم تصویردار `503`
می‌گیرد وقتی دیسک سرور بیش از حد پر است
(`فضای ذخیره سرور پر شده و فعلا تصویری پذیرفته نمی‌شود؛ کمی بعد دوباره امتحان کنید.`) یا وقتی فروشگاه در یک روز ۱
گیگابایت تصویر گرفته (`امروز بیش از این تصویری پذیرفته نمی‌شود؛ چند ساعت دیگر دوباره بفرستید.`) — و این پیش از بررسی
فیلدهای دیگر گفته می‌شود، پس بعدا دوباره امتحان کنید یا متن را بدون تصویر بفرستید.

## گفتگو

پاسخ <code dir="ltr">GET /tickets/{id}</code> تیکت با کل گفتگوی آن است، همان‌طور که هست — خواندنش چیزی را عوض نمی‌کند.
وقتی سایت تیکت را به کاربر نشان می‌دهد، این را خبر می‌دهد: `POST /tickets/{id}/read` (بدون بدنه) همان تیکت را
خوانده‌شده برمی‌گرداند — آخرین پیام پشتیبانی خوانده می‌شود و `unread` از آن به بعد `false` است — و اعلان‌های آن را هم در
فهرست اعلان‌های کاربر خوانده‌شده می‌کند ([اعلان‌ها](Store-API-Notifications.md)). پس صفحه تیکت را با همین `POST` باز کنید؛
برای خواندن دوباره تیکت `GET` بفرستید (پولینگ، پیش‌بارگذاری، تب پس‌زمینه)، و اگر `GET` تیکت را `unread` دید و صفحه جلوی
چشم کاربر است، `POST …/read` را دوباره بفرستید. نوشتن در تیکت، بستن یا امتیاز دادن آن را خوانده‌شده نمی‌کند؛ صفحه تیکت
ربات آن را مثل `POST …/read` خوانده‌شده می‌کند.

پاسخ `200` به `POST /tickets/{id}/read`:
```json
{
  "ticket": {
    "id": 12,
    "subject": "قطعی اتصال",
    "status": "answered",
    "subscription": { "id": 9, "name": "ali_1" },
    "last_message_at": "2026-10-08T10:40:00+00:00",
    "unread": false,
    "rating": null,
    "created_at": "2026-10-08T10:15:00+00:00",
    "closed_at": null,
    "rating_note": null,
    "messages": [
      { "id": 31, "author": "customer", "body": "از دیشب سرویس ali_1 وصل نمی‌شود.\nروی دو گوشی امتحان کردم.", "attachment": null, "created_at": "2026-10-08T10:15:00+00:00" },
      { "id": 33, "author": "customer", "body": "این خطا را می‌دهد:", "attachment": { "name": "screenshot.jpg", "kept": true }, "created_at": "2026-10-08T10:18:00+00:00" },
      { "id": 35, "author": "support", "body": "مشکل سرور برطرف شد؛ لطفا یک بار اتصال را قطع و دوباره وصل کنید.", "attachment": null, "created_at": "2026-10-08T10:40:00+00:00" }
    ]
  }
}
```

پیام‌ها از اول به آخر می‌آیند؛ `author` یا `customer` است یا `support` — پیام‌های پشتیبانی هیچ‌وقت نمی‌گویند کدام نفر از
پشتیبانی آن‌ها را نوشته. `body` متن ساده است: آن را به شکل متن نشان دهید، هرگز به شکل HTML، و با `white-space: pre-line`.

تصویر هر پیام در `GET /tickets/{id}/messages/{message}/attachment` است: خود فایل — JPEG، PNG، WebP یا GIF به همان شکل،
و هر چیز دیگری به شکل فایلی برای ذخیره — با کش خصوصی پنج‌دقیقه‌ای. توکن Bearer لازم دارد که `<img src>` نمی‌تواند
بفرستد: آن را fetch کنید و یک object URL نشان دهید، و نام فایل دانلودی را از `attachment.name` بگذارید (هدر
`Content-Disposition` از Origin دیگر خواندنی نیست). تصویری که از وب‌سایت یا یکی از پنل‌ها آپلود شده همان‌طور برمی‌گردد که
فروشگاه دوباره نوشته ([رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید))، نه همان‌طور که فرستاده شده.

فیلد `attachment.kept` می‌گوید تصویری برای گرفتن هست یا نه. تصویری که در تیکت آپلود شده ۳۰ روز بعد از بسته شدن تیکت پاک
می‌شود — تیکتی که پیش از آن دوباره باز شود تصویرهایش را نگه می‌دارد —: پیام هنوز می‌گوید تصویری داشته (`kept: false`) و
آدرسش `404` می‌دهد، پس نام فایل را نشان دهید و تصویر را درخواست نکنید. تصویری که در ربات فرستاده شده در تلگرام می‌ماند.

```ts
// lib/store.ts, beside store(): a picture the API serves, as an address an <img> can show —
// a message's (ask only while attachment.kept): picture(`/tickets/${ticket}/messages/${message}/attachment`)
export async function picture(path: string, tokens: Tokens = customerTokens): Promise<string> {
  const res = await fetch(BASE + path, { headers: { Authorization: `Bearer ${tokens.get()}` } })
  if (!res.ok) {
    const wait = res.headers.get('Retry-After')
    const error = new StoreError(res.status, await res.json(), wait === null ? null : Number(wait), res.headers.get('WWW-Authenticate'))
    if (error.signedOut) tokens.clear()
    throw error
  }
  return URL.createObjectURL(await res.blob()) // revoke it once the picture leaves the page
}
```

پاسخ `404` وقتی پیام تصویری ندارد یا تصویرش دیگر نیست (`این پیام تصویری ندارد.`، `این تصویر دیگر در تلگرام نیست.`،
`فایل این تصویر دیگر روی سرور نیست.` — آخری برای `kept: false` هم)؛ `502` تا وقتی تلگرام در دسترس نیست — تصویری که در
ربات فرستاده شده در تلگرام است (`تلگرام در دسترس نبود؛ چند لحظه بعد دوباره امتحان کنید.`)؛ `429` بعد از ۱۲۰ تصویر در یک
ساعت — هر درخواستی شمرده می‌شود، درخواست ردشده هم (`تصویر زیادی خواسته‌اید؛ …`): هر تصویر را وقتی به دید می‌آید fetch کنید
و تا وقتی صفحه باز است object URL آن را نگه دارید.

## نوشتن، بستن، امتیاز دادن

پاسخ هر کدام `{ ticket }` است — تیکت همان‌طور که الان هست، با گفتگوی آن ([گفتگو](#گفتگو))؛ هیچ‌کدام تیکت را خوانده‌شده
نمی‌کند.

- درخواست `POST /tickets/{id}/messages` — `{ body }`، یا فرمی با `body` و اگر تصویری هست `file` (با قاعده‌های
  [باز کردن تیکت](#باز-کردن-تیکت)): تیکت دوباره منتظر پشتیبانی می‌شود (`open`)، تیکت بسته هم. هر تیکت ۲۰۰ پیام جا دارد،
  پیام‌های کاربر و پشتیبانی با هم؛ بعد از آن `422` روی `status`
  (`این تیکت به سقف پیام‌ها رسیده؛ تیکت تازه‌ای باز کنید.`) — راه ادامه، تیکت تازه است. هر تیکت ۲۰ تصویر آپلودشده کاربر
  را نگه می‌دارد؛ بعد از آن پیام تصویردار `422` روی `file` می‌گیرد
  (`این تیکت بیشتر از ۲۰ تصویر از شما نمی‌گیرد؛ پیام را بدون تصویر بفرستید، یا تیکت تازه‌ای باز کنید.`) — فقط متن را
  بفرستید. درخواست `POST /tickets/{id}/messages`:
  ```json
  { "body": "درست شد، ممنون." }
  ```
- درخواست `POST /tickets/{id}/close` (بدون بدنه) — تیکت بسته می‌شود؛ اگر از قبل بسته باشد `422` روی `status`
  (`این تیکت بسته شده است.`). بستن تیکت به دست خود کاربر فقط به پشتیبانی خبر داده می‌شود.
- درخواست `POST /tickets/{id}/rating` — امتیاز ۱ تا ۵ و یادداشتی حداکثر ۵۰۰ کاراکتری؛ فقط وقتی تیکت بسته است (`422` روی
  `status`: `امتیاز را پس از بسته شدن تیکت می‌توانید ثبت کنید.`)، و امتیاز دوباره جای امتیاز قبلی را می‌گیرد. خارج از
  بازه: `امتیاز باید عددی بین 1 تا 5 باشد.` روی `rating`. هر امتیاز در سقف [محدودیت‌ها](#محدودیت‌ها) یک پیام کاربر
  حساب می‌شود؛ گروه فروشگاه از اولین امتیاز، یا امتیازی که عوض شده، خبردار می‌شود. درخواست
  `POST /tickets/{id}/rating`:
  ```json
  { "rating": 5, "note": "سریع جواب دادید." }
  ```

هر پیام با تغییری که ایجاد می‌کند یکجا ثبت می‌شود: اگر پشتیبانی درست وقتی کاربر دارد می‌نویسد تیکت را ببندد، بستن قبل یا
بعد از پیام ثبت می‌شود، هرگز وسط آن — هیچ پیامی روی تیکت بسته دیده‌نشده نمی‌ماند.

## محدودیت‌ها

| کاری که کاربر می‌کند | حداکثر | بیشتر از آن، `429` با `Retry-After` |
|---|---|---|
| باز کردن تیکت | ۱۰ در ساعت | `تیکت زیادی باز کرده‌اید؛ …` |
| نوشتن پیام — اولین پیام هر تیکت و هر امتیاز هم شمرده می‌شود | ۳۰ در ۱۰ دقیقه | `پیام زیادی فرستاده‌اید؛ …` |
| آپلود تصویر — رسیدها ([رسید](Store-API-Buying.md#کارت-به-کارت-و-رسید)) و تصویرهای تیکت‌ها با هم، از یک سهمیه | ۱۰ در ساعت | `تصویر زیادی فرستاده‌اید؛ …` |
| خواندن تصویر ([گفتگو](#گفتگو)) | ۱۲۰ در ساعت | `تصویر زیادی خواسته‌اید؛ …` |

هر سهمیه مال خود کاربر است، از همه دستگاه‌هایش با هم. تیکت، پیام یا آپلود وقتی شمرده می‌شود که فیلدهایش از بررسی گذشته
باشند — درخواستی که به خاطر فیلدها رد شود چیزی از سهمیه کم نمی‌کند —؛ خواندن تصویر، پاسخش هر چه باشد، شمرده می‌شود.
علاوه بر این‌ها: ۲۰۰ پیام در هر تیکت و ۲۰ تصویر از کاربر ([نوشتن، بستن، امتیاز دادن](#نوشتن-بستن-امتیاز-دادن))، و هیچ
تصویری پذیرفته نمی‌شود وقتی دیسک سرور بیش از حد پر است یا فروشگاه سهم یک گیگابایتی امروزش را گرفته (`503`،
[باز کردن تیکت](#باز-کردن-تیکت)).

## پاسخ‌ها چطور به کاربر می‌رسند

پاسخ پشتیبانی تیکت را `answered` و `unread` می‌کند و مثل هر اعلان دیگری خبر داده می‌شود
([اعلان‌ها](Store-API-Notifications.md)): اعلان `ticket_answered` با `subject` برابر
<code dir="ltr">{ "type": "ticket", "id": … }</code> و متنی که همان پاسخ است، کوتاه‌شده تا اندازه یک پیام تلگرام — متن
کامل در تیکت است —، که به چت تلگرامش فرستاده می‌شود (همراه تصویر پشتیبانی و دکمه‌هایی برای پاسخ دادن یا باز کردن تیکت در
ربات) یا — اگر حساب تلگرام ندارد یا ربات را بلاک کرده — با ایمیل، تا وقتی ایمیل فروشگاه فرستاده می‌شود. بستن تیکت به دست
پشتیبانی یک اعلان `ticket_closed` است. باز کردن دوباره تیکت به دست پشتیبانی، و کارهایی که خود کاربر می‌کند، خبری برای
کاربر ندارند.

در سایت: تیکت‌های `unread` را در فهرست مشخص کنید و `meta.unread` را به شکل عدد کنار لینک پشتیبانی نشان دهید؛ وقتی
`unread_notifications` در `GET /me` بیشتر شد، فهرست را دوباره بخوانید؛ اعلان هر تیکت را به همان تیکت لینک کنید — و وقتی
صفحه تیکت آن را نشان داد، `POST /tickets/{id}/read` بفرستید: تیکت و اعلان‌هایش با هم خوانده‌شده می‌شوند (به
`POST /notifications/read` نیازی نیست).
